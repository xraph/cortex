title: Custom Store
description: Implement a custom persistence backend by satisfying the composite store.Store interface.

Every Cortex persistence operation goes through the composite `store.Store` interface. This guide shows how to implement your own backend, whether that's MySQL, DynamoDB, or an in-memory store for tests.

## The composite interface

`store.Store` embeds thirteen domain-specific sub-interfaces plus three lifecycle methods:

```go
import "github.com/xraph/cortex/store"

type Store interface {
    agent.Store               // 7 methods
    run.Store                 // 9 methods
    memory.Store              // 8 methods
    checkpoint.Store          // 5 methods
    skill.Store               // 7 methods
    trait.Store               // 7 methods
    behavior.Store            // 7 methods
    persona.Store             // 7 methods
    prompt.Store              // 7 methods
    session.Store             // 6 methods
    suspension.Store          // 7 methods
    orchestration.ConfigStore // 7 methods
    orchestration.RunStore    // 5 methods

    Migrate(ctx context.Context, opts ...cortex.MigrateOption) error
    Ping(ctx context.Context) error
    Close() error
}
```

**Total: 89 methods** across the thirteen sub-interfaces, plus the three lifecycle
methods.

That number grows. `session.Store` arrived in v1.9.0 and `suspension.Store` in
v1.11.0, and each time a backend that satisfied the interface last release stopped
satisfying it until it implemented the new methods. Check this page against the
version you are on, and run `store/storetest`'s conformance suite against your
backend rather than trusting a compile.

## Sub-interface breakdown

Types are shown the way you will write them from outside cortex, so `agent`'s own
file says `*Config` where this says `*agent.Config`. Method names and order are as
declared.

### agent.Store (7 methods)

`Get` and `GetByName` both resolve against the scope on the context, so neither takes one.

```go
type Store interface {
    Create(ctx context.Context, cfg *agent.Config) error
    Get(ctx context.Context, agentID id.AgentID) (*agent.Config, error)
    GetByName(ctx context.Context, name string) (*agent.Config, error)
    Update(ctx context.Context, cfg *agent.Config) error
    Delete(ctx context.Context, agentID id.AgentID) error
    List(ctx context.Context, filter *agent.ListFilter) ([]*agent.Config, error)
    CountAgents(ctx context.Context, filter *agent.ListFilter) (int64, error)
}
```

### run.Store (9 methods)

Steps and tool calls have no by-name lookup and no scope of their own. They are always created inside the request that created the parent run, so they inherit its scope.

```go
type Store interface {
    CreateRun(ctx context.Context, r *run.Run) error
    GetRun(ctx context.Context, runID id.AgentRunID) (*run.Run, error)
    UpdateRun(ctx context.Context, r *run.Run) error
    ListRuns(ctx context.Context, filter *run.ListFilter) ([]*run.Run, error)
    CountRuns(ctx context.Context, filter *run.ListFilter) (int64, error)
    CreateStep(ctx context.Context, step *run.Step) error
    ListSteps(ctx context.Context, runID id.AgentRunID) ([]*run.Step, error)
    CreateToolCall(ctx context.Context, tc *run.ToolCall) error
    ListToolCalls(ctx context.Context, stepID id.StepID) ([]*run.ToolCall, error)
}
```

### memory.Store (8 methods)

Conversation methods carry a `SessionID` as well as an agent: messages belong to a thread, not to the agent directly. Working memory is keyed by run instead, and `LoadWorking` returns `cortex.ErrWorkingMemoryNotFound` when the key is absent.

```go
type Store interface {
    SaveConversation(ctx context.Context, agentID id.AgentID, sessionID id.SessionID, messages []memory.Message) error
    LoadConversation(ctx context.Context, agentID id.AgentID, sessionID id.SessionID, limit int) ([]memory.Message, error)
    ClearConversation(ctx context.Context, agentID id.AgentID, sessionID id.SessionID) error
    SaveWorking(ctx context.Context, runID id.AgentRunID, key string, value any) error
    LoadWorking(ctx context.Context, runID id.AgentRunID, key string) (any, error)
    ClearWorking(ctx context.Context, runID id.AgentRunID) error
    SaveSummary(ctx context.Context, agentID id.AgentID, summary string) error
    LoadSummaries(ctx context.Context, agentID id.AgentID) ([]string, error)
}
```

### prompt.Store (7 methods)

`GetOverlayForAgent` matches the caller's scope exactly, and `GetOverlayForAgentAt` matches a named ancestor of it exactly. Neither one prefix-matches, and that is the whole point: prefix matching widens downward, so a workspace-level list returns every project's overlay beneath it. Feed those into one run's prompt and you have mixed a sibling project's instructions into it.

```go
type Store interface {
    CreateOverlay(ctx context.Context, o *prompt.Overlay) error
    GetOverlay(ctx context.Context, overlayID id.OverlayID) (*prompt.Overlay, error)
    GetOverlayForAgent(ctx context.Context, agentID id.AgentID) (*prompt.Overlay, error)
    GetOverlayForAgentAt(ctx context.Context, agentID id.AgentID, scope cortex.Scope) (*prompt.Overlay, error)
    UpdateOverlay(ctx context.Context, o *prompt.Overlay) error
    DeleteOverlay(ctx context.Context, overlayID id.OverlayID) error
    ListOverlays(ctx context.Context, filter *prompt.ListFilter) ([]*prompt.Overlay, error)
}
```

### session.Store (6 methods)

Exactly one session per agent per scope carries `IsDefault`. Enforce that in your backend, because a run that names no session lands in whichever one you return.

```go
type Store interface {
    CreateSession(ctx context.Context, sess *session.Session) error
    GetSession(ctx context.Context, sessionID id.SessionID) (*session.Session, error)
    UpdateSession(ctx context.Context, sess *session.Session) error
    DeleteSession(ctx context.Context, sessionID id.SessionID) error
    ListSessions(ctx context.Context, filter *session.ListFilter) ([]*session.Session, error)
    CountSessions(ctx context.Context, filter *session.ListFilter) (int64, error)

```

### suspension.Store (7 methods)

The two `Claim` methods are the hard part. Each has to do the run's paused-to-running transition and the suspension read as one atomic operation, not a read followed by a write, because that gap is the race two concurrent resumes would otherwise both win. `ListExpiredAcrossScopes` is the one read here that deliberately ignores scope; it exists for the engine's expiry sweeper, which runs with no request scope on its context.

```go
type Store interface {
    CreateSuspension(ctx context.Context, susp *suspension.Suspension) error
    GetSuspension(ctx context.Context, runID id.AgentRunID) (*suspension.Suspension, error)
    ClaimSuspension(ctx context.Context, runID id.AgentRunID) (*suspension.Suspension, error)
    DeleteSuspension(ctx context.Context, runID id.AgentRunID) error
    ListExpired(ctx context.Context, now time.Time, limit int) ([]*suspension.Suspension, error)
    ListExpiredAcrossScopes(ctx context.Context, now time.Time, limit int) ([]*suspension.Suspension, error)
    ClaimExpiredSuspension(ctx context.Context, runID id.AgentRunID, now time.Time) (*suspension.Suspension, error)
}
```

Scope never appears in a signature. It arrives on the context and you read it with
`cortex.ScopeFromContext`, on every method above without exception.

## Key implementation notes

1. **Scope isolation.** Every query must filter by the caller's scope and reject a zero scope with `cortex.ErrNoScope`. Use `cortex.ScopeFromContext(ctx)`. There is no separate app dimension to read: a host that wants one declares an `app` level on the same `cortex.Scope`.

2. **A cross-scope read is a not-found.** Do not return an empty result and do not return a permission error. A caller who can tell that a row exists in a scope they cannot read has already learned something they should not know.

3. **ID generation.** Use `id.NewAgentID()`, `id.NewSkillID()`, etc. to generate TypeID-based identifiers in your `Create` methods.

4. **JSONB columns.** Complex nested structures (tools, dimensions, triggers, etc.) should be serialized as JSON. The bundled stores use grove models and annotate those columns `grove:"name,type:jsonb"`.

5. **Migrate().** Should be idempotent. Create tables if they don't exist, add columns if missing.

6. **Compile-time check.** Always include `var _ store.Store = (*MyStore)(nil)` to catch missing methods at compile time.

7. **Run the conformance suite.** `store/storetest` exercises scope isolation, the suspension claim races, and the counter invariants against a live backend. A store that compiles and passes its own tests can still leak across scopes, and that suite is what catches it.
