---
title: Host-Defined Scope
description: How Cortex scopes agents, runs, and every other entity using a hierarchy the host defines.
---

Cortex has no built-in notion of tenant, workspace, or organization. Every entity it
manages, agents, skills, traits, behaviors, personas, orchestration configs and
orchestration runs, agent runs, checkpoints, conversations, working memory, steps,
and tool calls, is scoped by a `cortex.Scope` that **the host declares and attaches
to the context**.
Cortex never interprets what a scope level means; it only matches on the `Key` you
give it. This is enforced at the store layer for every entity in that list: a
zero-scope context is rejected outright with `cortex.ErrNoScope`, and cross-scope
access to any of them is structurally impossible, not merely filtered out by a
parameter a caller could omit.

That guarantee applies uniformly, but not every entity resolves its scope the same
way. Agents, skills, traits, behaviors, personas, and orchestration configs are each
independently addressable by name: `GetByName`, `GetSkillByName`, and so on all take
just `(ctx, name)` and resolve against whatever scope is on the context. Runs and
checkpoints work the same way, resolved directly from context on every call.

Steps and tool calls are different. They carry scope columns and are filtered by them
in every `ListSteps`/`ListToolCalls` call, the same `cortex.ErrNoScope` guard as
everything else, but they have no by-name lookup of their own and no independent way
to acquire a scope: a step or tool call is only ever created inside the same request
that created its parent run, using that run's own context, so its scope is always the
run's scope. There is no separate "step scope" concept to reason about. This matters
most during the [v1.8.0 rescope of legacy rows](/docs/guides/v1.8-rescope): a step or
tool call from before this release never resolves its own scope through a host's
`Rescoper`. It inherits whatever its parent run resolves to.

Working memory (`SaveWorking`/`LoadWorking`/`ClearWorking`) is scope-guarded like
everything else and, unlike steps and tool calls, does carry its own legacy `tenant_id`
column, so a pre-v1.8.0 working memory row resolves directly through a `Rescoper`
rather than inheriting from its run.

## Scope and Level

```go
type Level struct {
    Key   string
    Value string
}

type Scope struct {
    Levels []Level
}
```

A `Scope` is an ordered hierarchy. TwinOS, for example, uses workspace then project;
another host might use org, team, then environment. Order is significant — it
determines which indexed column each level lands in, so a host must keep its ordering
stable across releases.

## Attaching a scope

The host is responsible for calling `cortex.WithScope` — typically from middleware —
**before** any call into the engine or the store. There is no default and no fallback:

```go
import "github.com/xraph/cortex"

ctx = cortex.WithScope(ctx, cortex.Scope{
    Levels: []cortex.Level{{Key: "tenant", Value: "org-123"}},
})
```

A host that also wants an application dimension declares it as another level, the
same way:

```go
ctx = cortex.WithScope(ctx, cortex.Scope{
    Levels: []cortex.Level{
        {Key: "tenant", Value: "org-123"},
        {Key: "app", Value: "myapp"},
    },
})
```

A host with a deeper hierarchy attaches every level it needs, in order:

```go
ctx = cortex.WithScope(ctx, cortex.Scope{
    Levels: []cortex.Level{
        {Key: "workspace", Value: "ws-123"},
        {Key: "project", Value: "proj-456"},
    },
})
```

## Reading a scope back

```go
scope := cortex.ScopeFromContext(ctx)
if scope.IsZero() {
    // no scope was attached — every scope-guarded store call will fail
}

tenant, ok := scope.Get("tenant") // "org-123", true
canon := scope.Canonical()        // "tenant=org-123"
```

`ScopeFromContext` returns the zero `Scope` if nothing was attached — callers must
treat that as an error condition, not as "match everything."

## One scoping model, not two

Before v1.8.0, domain entities (agents, skills, traits, behaviors, personas) carried
a separate `AppID` field, injected with `cortex.WithApp` and unrelated to
`cortex.Scope`. That axis is gone. There is one mechanism now: every entity carries a
`Scope`, populated from `cortex.WithScope` on create, and a host that used to rely on
`AppID` as an application boundary declares an `app` level on that same `Scope`
instead. `cortex.WithApp` and `cortex.AppFromContext` no longer exist.

## Store enforcement

Every store implementation enforces scope on every query:

- **Agent, Skill, Trait, Behavior, Persona, Orchestration Config**: `GetByName` and
  `List`/`Count` queries filter by the caller's scope, read from the context, the same
  as every other entity
- **Run, Orchestration Run, Memory, Checkpoint, Step, Tool Call**: every query
  filters by the caller's scope, read from the context
- **No scope, no query**: a zero scope is rejected with `cortex.ErrNoScope` before
  the store touches the database, rather than silently matching every row
- **Cross-scope access**: returns `ErrNotFound` even if the entity exists under a
  different scope
- **Scope is immutable after creation**: an entity's stored scope is set once and
  never rewritten by a later update

## Upgrading: rows from before v1.7.0/v1.8.0 carry no scope

The migrations that added `scope_l0`/`scope_l1`/`scope_l2`/`scope_canon` do **not**
backfill them for existing rows. An earlier draft tried synthesizing a scope from the
old `tenant_id`/`app_id` columns (`scope_l0 = 'tenant=' || tenant_id`), but that
invents a key vocabulary ("tenant=", "app=") distinct from whatever keys your own
scope actually uses (e.g. "workspace="), and every row predating scope had
`tenant_id = ''` or `app_id = ''`. Backfilling those into a literal `tenant=` bucket
would have silently orphaned all of that history into a bucket nothing could ever
reach again.

So instead: **rows created before scope existed are left with empty scope columns.**
Since every scoped query requires a non-zero `cortex.Scope` on the context and
filters by it, a row with `scope_canon = ''` simply never matches. It is invisible to
every scoped read, not deleted, and not silently misattributed to whichever scope
happens to query first.

As of v1.8.0, cortex will do the mapping for you, but only if you tell it how: pass a
`cortex.Rescoper` to `Migrate`, and it maps each distinct legacy `(appID, tenantID)`
pair onto a real `cortex.Scope` before writing anything. Without one, `Migrate`
returns `cortex.ErrNoRescoper` and leaves the database untouched rather than
guessing. See the [rescope guide](/docs/guides/v1.8-rescope) for the interface, a
worked implementation, and how to resolve a collision when two legacy rows map onto
the same scope and name. `tenant_id` and `app_id` are not dropped this release; they
stay around as read-only columns specifically so this kind of rescope is still
possible even if you skip it at upgrade time.

## API integration

The REST API does **not** manufacture a scope on the caller's behalf. Cortex ships no
scope middleware of its own for `api.API` — every guarded endpoint returns
`412 Precondition Failed` (not a raw 500) until a host installs one. Installing it is
not optional in a real deployment; without it, none of `api.API`'s run, conversation,
or checkpoint endpoints work.

`forge.Router.Use` takes an ordinary `func(http.Handler) http.Handler`, so a scope
middleware is standard Go HTTP middleware — nothing Cortex-specific about its shape,
just what it does with the request. Register it on the router **before** calling
`api.New(...).RegisterRoutes(router)`, so it runs ahead of every Cortex handler:

```go
package main

import (
    "net/http"

    "github.com/xraph/forge"

    "github.com/xraph/cortex"
    "github.com/xraph/cortex/api"
    "github.com/xraph/cortex/engine"
)

// scopeMiddleware reads workspace/project off request headers set by an
// upstream auth gateway and attaches them as the request's scope. A real
// deployment would more likely derive these from a validated JWT or
// session, not raw headers. The shape of WithScope is what matters
// here, not the header lookup.
func scopeMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        ctx := r.Context()

        workspace := r.Header.Get("X-Workspace-ID")
        if workspace == "" {
            http.Error(w, "missing X-Workspace-ID", http.StatusPreconditionFailed)
            return
        }
        levels := []cortex.Level{{Key: "workspace", Value: workspace}}
        if project := r.Header.Get("X-Project-ID"); project != "" {
            levels = append(levels, cortex.Level{Key: "project", Value: project})
        }
        ctx = cortex.WithScope(ctx, cortex.Scope{Levels: levels})

        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func main() {
    eng, err := engine.New( /* ... */ )
    if err != nil {
        panic(err)
    }

    router := forge.NewRouter()
    router.Use(scopeMiddleware)

    a := api.New(eng, router)
    if err := a.RegisterRoutes(router); err != nil {
        panic(err)
    }

    http.ListenAndServe(":8080", router.Handler())
}
```

A request missing `X-Workspace-ID` never reaches a Cortex handler at all in this
example — it's rejected by the middleware itself. A request that clears the
middleware but still ends up with a zero scope (a bug in the middleware, not a
missing header) is instead caught one layer in, at the store guard, and surfaces as
the `412` described above.

## Example: two tenants under one host-defined hierarchy

```go
// Caller 1 creates an agent under "myapp", tenant-1
ctx1 := cortex.WithScope(context.Background(), cortex.Scope{
    Levels: []cortex.Level{
        {Key: "tenant", Value: "tenant-1"},
        {Key: "app", Value: "myapp"},
    },
})
eng.CreateAgent(ctx1, agent1Config)

// Caller 2 creates a different agent under the same app, a different tenant
ctx2 := cortex.WithScope(context.Background(), cortex.Scope{
    Levels: []cortex.Level{
        {Key: "tenant", Value: "tenant-2"},
        {Key: "app", Value: "myapp"},
    },
})
eng.CreateAgent(ctx2, agent2Config)

// Caller 1's context scopes every read to tenant-1 — tenant-2's runs are
// invisible, not merely filtered out by a parameter caller 1 could omit.
runs, _ := eng.ListRuns(ctx1, &run.ListFilter{})
// runs contains only tenant-1's runs
```
