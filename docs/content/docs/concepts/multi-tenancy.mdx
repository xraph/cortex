---
title: Host-Defined Scope
description: How Cortex scopes agents, runs, and every other entity using a hierarchy the host defines.
---

Cortex has no built-in notion of tenant, workspace, or organization. Instead, every
scope-guarded entity (runs, conversations, checkpoints, and — via `AppID` — agents,
skills, traits, behaviors, and personas) is scoped by a `cortex.Scope` that **the host
declares and attaches to the context**. Cortex never interprets what a scope level
means; it only matches on the `Key` you give it. This is enforced at the store layer
for the entities listed above — cross-scope access to a run, conversation, or
checkpoint is structurally impossible, not merely filtered out by a parameter a caller
could omit.

That guarantee does **not** extend to everything a run touches. Steps, tool calls, and
working memory carry no scope of their own:

- **Steps and tool calls** are read through `ListSteps`/`ListToolCalls`, keyed by
  `run_id` with no scope predicate. They're safe in practice because every reader
  path goes through a scoped `GetRun` first — you can't reach a step or tool call
  without already having resolved its parent run inside your own scope — but a direct
  `run_id` (guessed or leaked) issued straight against `ListSteps`/`ListToolCalls`
  without that upstream check is not rejected by the store itself.
- **Working memory** (`SaveWorking`/`LoadWorking`/`ClearWorking`) is unscoped
  entirely; it is not covered by this document's enforcement guarantees.

Both are pre-existing gaps, not something this release introduced, and are called out
here rather than left implicit.

## Scope and Level

```go
type Level struct {
    Key   string
    Value string
}

type Scope struct {
    Levels []Level
}
```

A `Scope` is an ordered hierarchy. TwinOS, for example, uses workspace then project;
another host might use org, team, then environment. Order is significant — it
determines which indexed column each level lands in, so a host must keep its ordering
stable across releases.

## Attaching a scope

The host is responsible for calling `cortex.WithScope` — typically from middleware —
**before** any call into the engine or the store. There is no default and no fallback:

```go
import "github.com/xraph/cortex"

ctx = cortex.WithScope(ctx, cortex.Scope{
    Levels: []cortex.Level{{Key: "tenant", Value: "org-123"}},
})
ctx = cortex.WithApp(ctx, "myapp")
```

A host with a deeper hierarchy attaches every level it needs, in order:

```go
ctx = cortex.WithScope(ctx, cortex.Scope{
    Levels: []cortex.Level{
        {Key: "workspace", Value: "ws-123"},
        {Key: "project", Value: "proj-456"},
    },
})
```

## Reading a scope back

```go
scope := cortex.ScopeFromContext(ctx)
if scope.IsZero() {
    // no scope was attached — every scope-guarded store call will fail
}

tenant, ok := scope.Get("tenant") // "org-123", true
canon := scope.Canonical()        // "tenant=org-123"
```

`ScopeFromContext` returns the zero `Scope` if nothing was attached — callers must
treat that as an error condition, not as "match everything."

## AppID vs Scope

| Concept | Purpose | Required | Example |
|---------|---------|----------|---------|
| **AppID** | Logical application boundary. All domain entities (agents, skills, traits, behaviors, personas) carry an `AppID` field, injected with `cortex.WithApp`. | Yes | `"myapp"`, `"staging"` |
| **Scope** | The host's own hierarchy — tenant, workspace, org, whatever it needs. Used for execution entities (runs, conversations, checkpoints) to isolate per-host data, injected with `cortex.WithScope`. | Yes, for any scope-guarded operation | `tenant=org-123`, `workspace=ws-123/project=proj-456` |

## Store enforcement

Every store implementation enforces scope on every query:

- **Agent, Skill, Trait, Behavior, Persona** — all `GetByName` and `List` queries filter by `app_id`
- **Run, Memory, Checkpoint** — every query filters by the caller's scope, read from the context
- **No scope, no query** — a zero scope is rejected with `cortex.ErrNoScope` before the store touches the database, rather than silently matching every row
- **Cross-scope access** — returns `ErrNotFound` even if the entity exists under a different app or scope
- **Scope is immutable after creation** — a run's or checkpoint's stored scope is set once and never rewritten by a later update

## Upgrading to v2: rows from before this release carry no scope

The migration that adds `scope_l0`/`scope_l1`/`scope_l2`/`scope_canon` does **not**
backfill them for existing rows. An earlier draft of the migration tried to
synthesize a scope from the old `tenant_id`/`app_id` columns (e.g.
`scope_l0 = 'tenant=' || tenant_id`), but that invents a key vocabulary
("tenant=", "app=") distinct from whatever keys your own scope actually uses (e.g.
"workspace="), and every pre-v2 conversation row had `tenant_id = ''` — backfilling
those into a literal `tenant=` bucket would have silently orphaned all v1 history
into a bucket nothing could ever reach again.

So instead: **rows created before v2 are left with empty scope columns.** Since every
scoped query requires a non-zero `cortex.Scope` on the context and filters by it, a
row with `scope_l0 = ''` simply never matches — it is invisible to every scoped read,
not deleted, and not silently misattributed to whichever scope happens to query first.

If that old data matters to you, you are responsible for re-scoping it yourself before
your hosts start relying on it being reachable — for example, a one-off script that
reads each pre-v2 row's old `tenant_id`/`app_id` value, maps it to your own scope
keys, and issues an `UPDATE` (or the equivalent through your store) to populate
`scope_l0`/`scope_l1`/`scope_l2`/`scope_canon` accordingly. `tenant_id` and `app_id`
themselves are not dropped this release — they stay around as read-only columns
specifically so this kind of backfill is still possible after upgrading.

## API integration

The REST API does **not** manufacture a scope on the caller's behalf. Cortex ships no
scope middleware of its own for `api.API` — every guarded endpoint returns
`412 Precondition Failed` (not a raw 500) until a host installs one. Installing it is
not optional in a real deployment; without it, none of `api.API`'s run, conversation,
or checkpoint endpoints work.

`forge.Router.Use` takes an ordinary `func(http.Handler) http.Handler`, so a scope
middleware is standard Go HTTP middleware — nothing Cortex-specific about its shape,
just what it does with the request. Register it on the router **before** calling
`api.New(...).RegisterRoutes(router)`, so it runs ahead of every Cortex handler:

```go
package main

import (
    "net/http"

    "github.com/xraph/forge"

    "github.com/xraph/cortex"
    "github.com/xraph/cortex/api"
    "github.com/xraph/cortex/engine"
)

// scopeMiddleware reads workspace/project off request headers set by an
// upstream auth gateway and attaches them as the request's scope. A real
// deployment would more likely derive these from a validated JWT or
// session, not raw headers — the shape of WithScope/WithApp is what
// matters here, not the header lookup.
func scopeMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        ctx := r.Context()

        workspace := r.Header.Get("X-Workspace-ID")
        if workspace == "" {
            http.Error(w, "missing X-Workspace-ID", http.StatusPreconditionFailed)
            return
        }
        levels := []cortex.Level{{Key: "workspace", Value: workspace}}
        if project := r.Header.Get("X-Project-ID"); project != "" {
            levels = append(levels, cortex.Level{Key: "project", Value: project})
        }
        ctx = cortex.WithScope(ctx, cortex.Scope{Levels: levels})
        ctx = cortex.WithApp(ctx, "myapp")

        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func main() {
    eng, err := engine.New( /* ... */ )
    if err != nil {
        panic(err)
    }

    router := forge.NewRouter()
    router.Use(scopeMiddleware)

    a := api.New(eng, router)
    if err := a.RegisterRoutes(router); err != nil {
        panic(err)
    }

    http.ListenAndServe(":8080", router.Handler())
}
```

A request missing `X-Workspace-ID` never reaches a Cortex handler at all in this
example — it's rejected by the middleware itself. A request that clears the
middleware but still ends up with a zero scope (a bug in the middleware, not a
missing header) is instead caught one layer in, at the store guard, and surfaces as
the `412` described above.

## Example: two tenants under one host-defined hierarchy

```go
// Caller 1 creates an agent
ctx1 := cortex.WithApp(context.Background(), "myapp")
ctx1 = cortex.WithScope(ctx1, cortex.Scope{
    Levels: []cortex.Level{{Key: "tenant", Value: "tenant-1"}},
})
eng.CreateAgent(ctx1, agent1Config)

// Caller 2 creates a different agent under the same app, a different tenant
ctx2 := cortex.WithApp(context.Background(), "myapp")
ctx2 = cortex.WithScope(ctx2, cortex.Scope{
    Levels: []cortex.Level{{Key: "tenant", Value: "tenant-2"}},
})
eng.CreateAgent(ctx2, agent2Config)

// Caller 1's context scopes every read to tenant-1 — tenant-2's runs are
// invisible, not merely filtered out by a parameter caller 1 could omit.
runs, _ := eng.ListRuns(ctx1, &run.ListFilter{})
// runs contains only tenant-1's runs
```
