---
title: Cognitive Style
description: Inspect runtime capabilities and configure descriptive cognitive styles.
---

A cognitive style describes thinking as a chain of phases. Instead of picking a single strategy, you define several phases that hand over to each other when a condition is met.

The style is a value object on a persona. It's stored and returned with the persona, but the engine doesn't apply it yet: every run uses the ReAct loop, no phase transitions happen, and the `OnCognitivePhaseChanged` plugin hook never fires. The tables below describe what each value is meant for.

## Operational observations

Register the capability inspection tool when you want a model to inspect its
current tools and remaining execution limits:

```go
eng, err := engine.New(
    engine.WithStore(store),
    engine.WithLLM(client),
    engine.WithToolAuthorizer(authorizer),
    engine.WithOperationalAwareness(),
)
```

The tool is named `cortex_capabilities` and takes an empty object, `{}`. Include
`engine.ToolOperationalCapabilities` in any explicit agent or run tool allowlist.
It is registered with implementation revision `cortex.capabilities/v1`, so a
prepared run pins it like other registered tools.

The response contains a versioned `cognitive.Snapshot`, the prepared digest,
model identity and configured revision. Tools come from the frozen allowlist,
current registrations and a fresh `ToolAuthorizer.Visible` check. Hidden names
are omitted. A persona claiming an ability cannot add it to this list.

| Value | Meaning |
| --- | --- |
| `requestable` | Registered, currently visible, and within the observed tool budget. Call authorization and approval still apply. |
| `unavailable` | The frozen tool has no current executor registration. |
| `budget_exhausted` | A token, tool-call or deadline limit prevents another tool call. |
| `health: unknown` | No service-health observation was collected. |
| `reliability: unknown` | No compatible measured cohort is attached. |

The lower-level `cognitive.BuildSnapshot` also distinguishes permission denial
and an observed service outage when a trusted host supplies those observations.
The runtime tool does not probe services and never reports hidden tools as denied
entries. External tools are identified as external; registration does not prove
that a host worker is available to execute them.

Remaining allowances include the inspection call itself and the model step that
requested it. A `null` allowance means that limit was not configured; zero means
it is exhausted. Reported token use and conservative charges remain separate in
`usage`. These values are observations at `observed_at`, so a saved response
cannot authorize a later action or reserve resources.

The inspection uses normal tool authorization, approvals, accounting and output
checks. On a verified run its result is captured in the private execution
transcript. Approved calls can resume on a fresh engine with the same registration
and configuration. The tool reads only the executing run and accepts no run,
principal or scope arguments. It does not change the prepared prompt or start
reflection, replanning or learning.

## Context budgets

Register a context budget when you want the engine to select initial history
and check each complete provider request against a finite context window:

```go
engine.WithContextBudget(engine.ContextBudgetConfig{
    Policy: cognitive.ContextPolicy{
        Revision:        "history/v1",
        CounterRevision: "provider-counter/v1",
        MaxTokens:       32768,
        ReservedTokens:  2048,
    },
    CountTokens:     countProviderRequest,
    OptionalHistory: classifyOptionalHistory,
})
```

You supply both functions. `CountTokens` takes a context and `*llm.Request`, and
returns the input token count or an error. It receives a detached request, including
system text, tools and messages. Its implementation must account for the chosen
provider's framing and tokenizer. Local fixture counters do not qualify a live
provider, and this policy is separate from cumulative execution budgets or billing.

`OptionalHistory` takes a context, `cortex.Subject` and chronological
`[][]llm.Message` turns. It returns optional turn indices. Omit the callback to
keep all history required. The engine starts a turn at each user message and
never splits a selected turn; system text, tool definitions, the current task
and every message generated during the current run stay pinned. Callback errors
stop execution, and a callback cannot mutate the engine's messages.

The engine checks up to 4096 stored history messages and rejects a longer history
instead of silently taking its tail. History is the existing text projection;
tool execution traces are separate. System, developer and tool roles in that
projection are rejected. Conversation-store read or decode failures stop the run.
Automatic summaries and compaction during an active run are not implemented.

Selection records retain original and selected history digests, optional-item
decisions, source references and counter revisions in run provenance, without
copying conversation text into metadata. Required-verification input artifacts
also retain the original and selected history privately, within the existing
one-MiB artifact limit. For ordinary runs, your conversation retention policy
determines whether omitted source text remains available later.

The complete request is counted again before each sync or streaming provider
call, and output is capped by the reserved allowance. If required context grows
beyond the allowance, execution stops incomplete before another provider call.
That local rejection does not charge a model attempt. Initial selection failures
occur before run creation; errors from host counters and classifiers expose only
`cortex.ErrContextUnavailable`.

Context-enabled prepared snapshots use schema 7, or schema 8 when verification
is required. The policy and counter revisions are frozen. A fresh engine must
install the identical policy to resume, and history, task and selection records
are checked before claiming a pause and again before execution. Change revisions
when classification or counting semantics change. Older workers reject these
schemas. Existing schema-2/6 artifacts remain usable without a context budget;
prepare new artifacts to opt in, and drain older pauses on their compatible host.

## Context selection core

You can use `cognitive.ContextPolicy.Select` to select atomic context items within
a token allowance outside the engine as well.

Supply a policy revision, a token-counter revision, a finite `MaxTokens` and
`ReservedTokens` for output. `ContextInput.FixedTokens` accounts for system
instructions, tool definitions and framing. Items are ordered oldest first, and
each carries a source reference, digest, origin and measured token cost.

Every item is required by default. Objectives, constraints, acceptance criteria,
the current plan and unresolved blockers must come from trusted host
classification and cannot be optional. Once those items fit, the selector tries
optional history, observations and summaries from newest to oldest, keeping each
item whole and preserving the original order. Group dependent messages into one
item so a tool request and its result cannot be split.

The result includes detached retained and omitted items with their source
references. A summary must include its source references and an explicit
uncertainty statement; selection preserves both, but does not verify that the
summary faithfully represents those sources. Conflicting required observations
remain separate. Retrieved or generated material cannot declare itself a task
constraint through this API.

Required context that does not fit returns `cognitive.ErrContextBudgetExceeded`
with no partial selection. You must resolve that failure before dispatch. Count
the complete assembled request again with the pinned provider counter because
item costs alone do not account for every framing or tokenization interaction.
Source access, freshness, publication screening and persistence remain host
responsibilities. Never populate trusted classifications or omission flags
directly from model output.

## Structure

```go
type Style struct {
    Phases              []Phase
    DepthPreference     float64 // 0.0 = shallow, 1.0 = deep
    FocusPreference     float64 // 0.0 = broad, 1.0 = narrow
    ReflectionFrequency float64 // how often to self-reflect
}
```

## Phases

A phase represents one stage in a cognitive strategy chain:

```go
type Phase struct {
    Strategy   Strategy
    MaxSteps   int
    Transition TransitionCondition
}
```

### Strategies

| Strategy | Description |
|----------|-------------|
| `analytical` | Structured, step-by-step analysis |
| `creative` | Exploratory, lateral thinking |
| `methodical` | Systematic, exhaustive approach |
| `reactive` | Quick response, minimal deliberation |
| `reflective` | Self-evaluating, iterative refinement |
| `collaborative` | Seeks input, considers multiple perspectives |

### Transition conditions

| Condition | Description |
|-----------|-------------|
| `after_steps` | Transition after `MaxSteps` reasoning steps |
| `on_stuck` | Transition when progress stalls |
| `on_plan_complete` | Transition when the current plan is finished |
| `on_error` | Transition when an error occurs |

## Multi-phase example

A three-phase cognitive style for a code reviewer:

```go
cognitive.Style{
    Phases: []cognitive.Phase{
        {
            Strategy:   cognitive.StrategyAnalytical,
            MaxSteps:   5,
            Transition: cognitive.TransitionAfterSteps,
        },
        {
            Strategy:   cognitive.StrategyReflective,
            MaxSteps:   3,
            Transition: cognitive.TransitionAfterSteps,
        },
        {
            Strategy:   cognitive.StrategyMethodical,
            MaxSteps:   10,
            Transition: cognitive.TransitionOnPlanComplete,
        },
    },
    DepthPreference:     0.8,
    FocusPreference:     0.6,
    ReflectionFrequency: 0.5,
}
```

This records the intended sequence. The current runtime does not execute it.

## Embedding in a persona

Cognitive style is a value object embedded directly in the persona:

```go
persona := &persona.Persona{
    CognitiveStyle: cognitive.Style{
        Phases: []cognitive.Phase{
            {Strategy: cognitive.StrategyAnalytical},
        },
    },
}
```
