description: Read execution state, verification and content screening separately, and inspect the mechanisms installed in your host.

A completed run means the engine reached a final answer. It does not establish that the answer is correct. Read three fields together:

| Field | What it tells you |
| --- | --- |
| `state` and `stop_reason` | Whether execution completed, stopped at a limit, failed or was cancelled |
| `verification_status` | Whether explicit result checks have passed; historical runs default to `unchecked` |
| `provenance.publication_status` | Whether published content was screened, redacted, flagged or left unscanned |

Synchronous REST execution returns `stop_reason`, `verification_status`, `publication_status` and an optional `result_ref` alongside its existing fields. Saved run responses retain publication status inside `provenance`. Terminal stream events carry the same outcome categories. A closed, expired or disconnected feed does not prove completion; load the saved run when events are missing.

A2A projects incomplete runs as the protocol's existing failed task state. Its task and status-update metadata includes `cortex.assurance` with the execution state, stop reason, verification status and publication status. This metadata also survives the gRPC binding.

## Publication policy

Configure the boundary with `engine.WithPublicationPolicy` and install a checker with `engine.WithPublicationGate`, or use the existing `WithSafety` scanner adapter. Buffered publication is the default. The engine holds candidate content until the configured checker accepts it. A required but unavailable checker, checker error, invalid decision or exceeded byte limit prevents publication.

Checked-segment streaming requires an explicit `safety.IncrementalGate`. An accepted prefix cannot be retracted, so use buffered mode when a rule needs the complete response. Explicitly disabled scanning reports `unscanned`; it does not remove byte limits.

Content screening covers input, output, retrieved content, tool results and public error text. If screening would rewrite tool arguments, execution stops instead of issuing a changed command. A scanner decision describes content screening only. It cannot certify the answer's factual accuracy.

## Installed capabilities

`Engine.RuntimeCapabilities()` and the dashboard's `runtime.detail.assurance` describe process configuration. They report prepared-execution support, publication mode, whether a gate is installed and whether that gate advertises incremental checking. Presence does not certify provider health or effectiveness.

Automatic contextual verification at publication remains unavailable. The explicit
`VerifyRun` worker below can verify saved candidates. Default preparation freezes collected inputs and checks its source read set for observed changes. Those independent reads are not one transaction.

## Atomic preparation

Use `engine.WithAtomicPreparation()` when collection must read one consistent database snapshot. This requires the optional `store.PreparationSnapshotter` capability. The built-in PostgreSQL, SQLite and MongoDB stores implement it. PostgreSQL uses a read-only repeatable-read transaction, SQLite uses a read-only transaction request with serializable isolation, and MongoDB uses explicit snapshot read concern with majority commit concern. MongoDB needs transaction support, such as a replica set. Configure SQLite with WAL and a busy timeout when writers need to proceed during capture.

The capture includes the agent, persona, inline skills, inline traits and ancestor overlays, including missing overlays. It returns a scope-bound `provenance.source_snapshot` receipt and `source_validation=atomic_store_snapshot` only after collection and transaction completion succeed. The receipt ID identifies the capture; it is not a reusable database revision. Captured readers expire when collection returns, and publication checks run after the transaction closes.

Unsupported stores, failed transactions and any nonempty skill knowledge reference fail preparation. A database transaction cannot qualify live external retrieval, even when a knowledge provider is installed. There is no silent fallback to ordinary reads. Existing prepared artifacts retain their original provenance.

An atomic store receipt covers source collection only. Model and tool revisions, contextual correctness, authorization, external state and evaluation isolation still need their own checks. Keep reproducibility-required evaluation disabled whenever any required guarantee is missing.

## Observe failures

`plugin.RunTerminated` receives a content-free summary after the terminal store update succeeds. It includes incomplete and cancelled runs. `plugin.PublicationRejected` reports a bounded policy reason, including rejection before a run exists. Its run ID is then empty.

The audit extension records these events. Metrics count incomplete runs, cancellations, terminal policy failures and rejected checks without using prompts, evidence IDs or arbitrary provider values as labels. Hooks remain best effort. They do not provide durable exactly-once delivery or replace a required audit transaction.

## Rollout checks

Prepared snapshots and continuations use schema 2. Drain or cancel older schema-1 pauses on compatible workers. Re-prepare stored schema-1 harnesses as new versions and evaluate them again; changing a schema number cannot recreate the missing policy or preserve prior acceptance.

Scopes support at most three ordered, unique levels. Listing can use an ancestor prefix, while mutation and execution require the exact resource scope. Invalid or inconsistent historical rows fail closed. Use the administrative `store.ScopeInspector` inventory before an operator-approved migration; the engine never truncates or repairs stored identity automatically.

Qualify your installed provider, scanner, authorization and storage paths before rollout. Passing fixture tests or the deterministic local demo does not establish live-model quality, effective scanning or sandbox isolation.


## Evidence and acceptance contracts

You can build independent evaluators with the `evidence` and `verification` packages. Engine verification is still disabled; saving a report does not change a run's status or authorize publication.

Seal captured bytes with `evidence.Seal`. The reference binds their SHA-256 digest, exact scope, version, producer, sensitivity and retention deadline. Wrap a built-in storage capability with `evidence.NewRepository` and your host authorizer before serving content. Reads check both bytes and metadata, then recheck source access. Built-in storage limits content to one MiB; inject a separate repository for larger artifacts. The authorizer must enforce current grants, sensitivity and retention.

Create an ordered `verification.Contract` with at least one required criterion. Each criterion names a verifier revision and a host-registered manifest. `verification.NewVerifier` accepts typed schema, test, state and human adapters, a host authorizer and a clock. Test adapters still need a qualified execution environment; registering one does not provide isolation.

`verification.Aggregate` requires every required criterion to pass for the same run and captured context. Optional scores cannot compensate for a failed check. Missing checks are inconclusive. Expired reports, source observations or human approvals are stale. A human verdict must name its actor and decision revision and match the complete evidence binding.

Before acting on a result, reauthorize the resources and compare a trusted current binding with `verification.CheckFreshness`. A report digest checks integrity, not authorship or current permission. Only trusted host paths may create or persist reports. The built-in stores expose `verification.Store` as an optional capability and retain immutable history for audit.

Evidence deletion retains an audit tombstone. Set the authenticated actor with `evidence.WithDeletionActor` before deleting through the authorized repository. The first deletion records the reference, actor, time and reason; retries cannot rewrite that history or restore the bytes. Tombstone reads are a separate storage capability and require host audit authorization.


### Check current external state

Use `verification.NewStateVerifier` with `verification.RegisterState` when a
criterion needs to confirm that captured resources still have the same revision
and digest. You register sealed `StateManifest` values for exact bindings and
criteria. Each manifest names a nonempty subset of captured sources, a positive
source-age limit and a read window of at most 30 seconds.

Your `StateObserver` authenticates each resource in its captured scope and reads
its current revision and digest without repeating task effects. It returns the
manifest and binding digests, the resource identity, and the start, finish and
source-observation times. Configure the observer independently of candidate
content. Cortex supplies the checker, not your service's authenticated reader.

The checker reauthorizes around each read. A changed revision or digest fails the
check; wrong identities, source outages, revoked grants and invalid read windows
return errors. An observer cannot choose its expiry. The checker derives that
from the request deadline and criterion limits, with a separate context deadline
for each probe. Set `MaxConcurrent` between one and 64 to bound admission.

Reports retain these windows in `Outcome.StateObservations`. Freshness checks
reject future or expired observations, and contract validation prevents a state
observation from extending its permitted age. SQLite, PostgreSQL and MongoDB
retain the complete records. Existing reports without observations keep their
encoding and do not acquire an external-state guarantee.
Fresh reads do not renew the original captured source timestamps. If that capture
is stale, collect a new binding and evaluate it again.

A passing state check establishes that the registered source versions matched
within the recorded windows. It does not establish objective coverage, schema or
unit correctness, lock a remote resource, or authorize an export. Register those
acceptance checks separately and retain the publication fence below.

### Export an approved artifact

`verification.ArtifactExporter` is a separate host command. Reserve an operation
ID with `PrefixExport` durably, then submit the exact artifact reference, committed
result identity, actor, approval reference and logical destination revision.
The artifact must belong to that result's captured binding. A sandbox job cannot
grant export permission or select a filesystem path through this request.

Configure current export authorization, an `ArtifactExportFence`, content
screening, an authorized evidence repository, result storage and an idempotent
sink. The fence must hold approval, destination, policy, evidence and run-revision
guards through delivery. Every relevant writer must participate. External
destinations need conditional writes or a qualified observation window.

The command checks a fresh result snapshot, reads and hashes at most one MiB,
screens the complete bytes, and checks freshness and authority again before
delivery. Screening must approve the exact digest. Changed or redacted bytes need
a new artifact and approval. Successful export of supporting evidence does not
assert that it was the verified candidate. Admission is bounded by `MaxConcurrent`
(one through 64), and each attempt has a 30-second context deadline.

On Linux and macOS, `grading.NewFileExporter` in the sandbox module supplies a
local file sink. You provision a private operation journal and private destination
directories, each mode 0700. The adapter reserves the full request before writing
an artifact, uses operation IDs as filenames, rejects links and directory changes,
and never replaces existing content. Identical retries verify the same files.

`ErrExportUncertain` means delivery may have occurred. Preserve the operation ID
and complete request. An identical retry rechecks current approval and result
freshness; it cannot move to another destination or use a renewed approval under
the old ID. If those checks have expired, inspect the retained journal through
your host's authorized audit process before taking another action.

This command does not install API routes, dashboard actions or a production
deployment target. Configure and qualify those integrations separately.

## Commit a verified result

Built-in stores expose optional `verification.CommitStore`. A commit consumes
saved contracts and reports, checks the exact run revision and retained evidence,
and saves the receipt, metadata-only outbox entry and run update in one
transaction. The run must contain a completed final answer pending verification,
with the same prepared digest and acceptance contract. Failed or missing required
checks cannot pass this operation.

Use `verification.NewCommitter(storage, hostFence, hostAuthorizer)` at your host
boundary. Its `Commit(ctx, request)` method checks current grants inside the host
fence, calls storage while that fence is held and validates the returned receipt.
Every retry passes through the same authorization check. The request contains
saved record IDs and a trusted binding, never model-authored evaluators or
permission claims.

Your `verification.CommitFence` must hold authorization and revision guards
through the entire callback. Capture the current binding from authoritative
state, invoke the callback once and synchronously, and require every relevant
policy or revision writer to use the same guards. That includes writers in other
processes. A permission lookup followed by an unlocked database write leaves a
revocation gap. Cortex supplies no permissive default fence.

For an external resource, use a version-conditional operation or define and
check an observation window appropriate to the contract. A local guard cannot
freeze a remote service. Keep captured provenance timestamps intact when
checking that its resource versions still match; any changed binding requires
fresh reports.

Retry the same request and result ID after an ambiguous acknowledgement.
Storage returns the original historical receipt and event ID, even if evidence
has since expired or been deleted. The guarded API still requires current access.
A receipt does not renew evidence freshness or grant permission to publish.
`GetCommittedResult` is a raw storage read, so protect audit access separately.

Built-in stores also expose the optional `verification.ResultSnapshotStore`.
Use `ReadResultSnapshot` when trusted host code needs the saved output with a
fresh check of its stored verification material. Supply a `ResultReadRequest`
with schema version 1, the exact run and result IDs, and the receipt digest.
The digest binds the request to a receipt. It grants no access.

The read uses one run transaction to check the current passed run revision,
receipt, contract, report freshness, candidate bytes and all supporting evidence,
including captured execution inputs and transcripts. Deleted evidence, changed
runs and expired reports return an error with no snapshot. Freshness and context
cancellation are checked again after the transaction finishes. Reads preserve
run state and public events, and still work after metadata replay retention
removes the corresponding events.

Keep this capability inside trusted host code. `ResultSnapshot.Output` is omitted
from JSON, but the receipt, contract and reports still contain private metadata.
Do not expose the snapshot directly. You must enforce current content access,
check current external source revisions and apply the current publication policy
before returning any bytes. `snapshot.Validate(request, now)` lets you recheck
integrity and time-based freshness after I/O; it cannot discover deleted evidence
or changed grants and resources. Use the guarded content reader below when you
need a screened answer for the current reader.

SQLite uses a write transaction; PostgreSQL locks the run and evidence records.
MongoDB requires a transaction-capable deployment and fences evidence against
concurrent deletion. A standalone MongoDB server returns
`verification.ErrCommitUnavailable`. Requests and receipts are limited to one
MiB, with at most 256 report IDs and eight MiB of report JSON and evidence bytes
processed in one attempt.

The required runtime gate and scoped recovery loop below consume this storage
boundary. Durable public outbox dispatch remains open. Storage alone does not
change `RunCompleted` hooks or enable contextual verification in capabilities.


## Read screened result content

Configure `engine.WithResultContent` with a `ResultContentAuthorizer`, a
`verification.CommitFence` and a trusted clock. You also need a snapshot-capable
store and an enabled publication gate, supplied with `WithPublicationGate` or
`WithSafety`. Missing services and typed-nil ports are refused at construction.
Metadata replay permission does not grant content access.

Call `Engine.ReadResultContent` with a `verification.ResultContentRequest`
containing schema version 1 and the exact run and result IDs. The result ID is
available in the durable `result_committed` event. The engine resolves the private
receipt itself, so your client does not need its digest or evidence references.

The reader checks content permission before storage, then enters the host fence
with the committed binding. That fence must capture current authoritative state
and guard relevant source, grant and policy writers, including the current
agent safety profile. A changed binding refuses the read. The reader checks
permission again, loads a fresh snapshot and screens the entire answer through
the engine's current publication policy. Screening holds no database transaction.
Before returning, it reads another fresh snapshot, rechecks permission and checks
freshness again after the fence returns. Deletion, expiry or a run change during
screening discards the answer.

`verification.PublishedResult` contains the screened content, identities and
observation times. It excludes private receipts, contracts, reports and bindings.
`VerificationStatus` and `VerifiedAt` describe the original committed candidate.
If screening changes the text, `ContentChanged` is true and that projection has
not itself been verified. Empty redactions are valid. A checker must explicitly
mark changed text as `redacted`; approved or flagged decisions cannot silently
rewrite the answer. Unscanned or unknown decisions and invalid UTF-8 output are
refused, so JSON encoding cannot silently replace bytes after screening.

Reads have a five-second deadline and a one-MiB output ceiling. Host callbacks
must honor cancellation. Calls return only static error categories, never private
provider diagnostics, and do not regenerate, reevaluate or update the stored run.
The existing publication hooks and metrics observe screening with source
`result_replay`.

HTTP exposes this reader at `GET /v1/runs/:id/results/:result_id`. The dashboard
query `runs.result` v1 accepts `id` and `result_id`; it requires `cortex.read` as
well as the engine's separate current content grant. Both use the same parser,
reader and static failure vocabulary. `run_revision` is a decimal string in the
JSON response, so browser clients preserve revisions above JavaScript's exact
integer range. Go callers retain the `int64` field.

The HTTP route sets `Cache-Control: no-store`, admits at most 64 concurrent reads
per API instance and requires response-writer deadline support before reading
private material. It bounds response writes to ten seconds, with an earlier
caller deadline taking precedence. Content length lets clients detect truncated
responses; a failed write never appends another error body. Dashboard hosts must
bound their own dispatcher response delivery and prevent shared caching of these
private responses.

| Failure code | HTTP status | Meaning |
| --- | --- | --- |
| `result_invalid` | 400 | Invalid run or result identity |
| `result_denied`, `result_blocked` | 403 | Current access or publication policy refuses content |
| `result_not_found` | 404 | No result in the authorized scope |
| `result_stale` | 409 | Verification no longer matches |
| `result_limit` | 413 | Publication size limit exceeded |
| `result_unavailable`, `result_interrupted`, `result_busy` | 503 | Unavailable service, interrupted read or exhausted HTTP capacity |

Metadata SSE continues to carry no answer text. A returned observation is not a
permission lease: reauthorize each subsequent read and bound delivery in your
transport. Direct engine and store access remains a trusted host capability and
requires separate authorization. Historical transport reads use the protection
rules below. Installed browser, proxy and dashboard-host behavior still needs
qualification.

### Read content through A2A

Enable `a2aremote.Options.ResultContent` on a service backed by
`a2aremote.EngineGateway(eng)`. Construction refuses an unavailable guarded
reader. The agent card advertises this Cortex extension only when the service
has enabled it:

```http
A2A-Extensions: https://cortex.xraph.dev/a2a/extensions/result-content/v1
Cortex-Result-ID: vresult_...
```

Use `GetTask` with the run ID or its delivery ID. This works through REST,
JSON-RPC and gRPC. The service checks the routed agent, calls the engine's guarded
reader and reauthenticates the peer before returning. Your content authorizer
can inspect `a2aremote.PeerFromContext` for the resolved node and scope.

The task's `cortex.result` metadata contains `ResultContentResponse`, including
screened `content`, decimal-string `run_revision` and `content_changed`. Task
artifacts, history and status messages carry no stored answer or diagnostics.
The response acknowledges the extension in `A2A-Extensions`. This is a Cortex
extension using the [A2A 1.0 activation mechanism](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/topics/extensions.md#extension-activation),
not an official A2A extension.

Supply exactly one result header. A content request cannot also activate
metadata replay, start work, cancel a task or subscribe to a stream. Invalid
requests and unavailable readers fail without falling back to the legacy raw
projection. Failures use the shared `result_*` codes in protocol error data;
REST follows A2A status mappings, which differ from the Cortex HTTP table above.

The service admits 64 guarded reads and bounds each to five seconds. HTTP also
holds one of 64 delivery slots through the response, requires writer deadlines
before reading content, sets `Cache-Control: no-store`, and limits writes to ten
seconds within a fifteen-second request bound. Earlier caller deadlines win.
gRPC clients must send a deadline no more than fifteen seconds away; the server
acknowledges private-cache metadata and uses that deadline to bound delivery.
Host callbacks must honor cancellation, and your gRPC server still needs its
own connection and stream limits.

For protected runs, requests without this extension return task metadata only.
The terminal update includes `cortex.content_withheld` and, when one exists, a
valid `cortex.result_ref` for your client to request guarded content separately.
Historical projections do not return answer artifacts or private diagnostics.
Installed proxies, clients and host policy fences still need qualification.

### Protected historical reads

A historical run is protected when it requires verification, has a saved result
reference, or its transport has a guarded reader configured. The saved requirement
and result reference keep it protected even if the current host removes that
reader. No content-read grant means no answer bytes.

HTTP run detail/list, dashboard run detail/list and agent statistics use
`run.PublicView` for protected runs. It copies an explicit metadata allowlist:
identities, scope, revision, state, assurance statuses, budget/usage and timestamps.
Input, output, errors, arbitrary metadata and private provenance are withheld.
The returned metadata marks `content_withheld: true` and retains a valid committed
result reference. Stored records remain unchanged, and direct engine/store calls
still expose trusted host data.

Protected dashboard detail omits step and tool-call bodies and private pending
calls. Its cached `runs.events` query returns a conflict with code
`protected_replay_requires_guarded_reads`; use `runs.replay` for durable metadata
and `runs.result` for screened content. This prevents an older live-cache entry
from bypassing current grants. Host access controls still govern metadata reads,
configuration and private administrative operations.

Ordinary historical runs without a saved result, verification requirement or
configured guarded reader retain their legacy projections. First delivery from
an executing engine remains governed by its execution publication policy.
Consumers of protected historical views must fetch content through the guarded
reader instead of expecting the old inline answer or cached token stream.



## Durable verification work

Built-in stores expose `verification.JobStore` for checks on a saved candidate.
`EnqueueVerificationJob` validates the captured run, contract and retained
evidence, then saves the job and moves the run to pending verification in one
transaction. Supply the exact run revision. A retry with the same job ID and
request returns the saved job; changed input under that ID conflicts.

A job pins the candidate binding, contract, deadline and ownership-attempt limit.
It does not run generation or tools. Each claim has an owner, unique claim ID,
expiry and increasing generation. Retry the same claim ID after a lost
acknowledgement to recover its current lease. An expired lease needs a new claim
ID. Previously consumed claim IDs cannot acquire later generations.

| Operation | Storage behavior |
| --- | --- |
| `GetVerificationJob`, `ListVerificationJobs` | Read exact-scope snapshots with bounded ID pagination |
| `ClaimVerificationJob` | Acquire unclaimed work or replace an expired lease, subject to deadline and attempt limits |
| `RenewVerificationJob` | Extend a live lease, capped by the job deadline; never revive expired ownership |
| `SaveVerificationJobReport` | Save the report and accepted progress together under the current lease |
| `ExpireVerificationJob` | Finish overdue work or work with exhausted ownership attempts as inconclusive |
| `CancelVerificationJob` | Retire unfinished verification and clear its lease without retracting a committed result |

Accepted reports survive takeover and database restart. Workers inspect those
report IDs before dispatching another check. A later report cannot replace an
accepted criterion with a more favorable verdict. Failed or inconclusive
required outcomes finish the job and update the run's verification status; the
execution state still describes the original generation. Contract requirements
apply even when a verifier reports a pass: missing proof or a required human
verdict makes the check inconclusive. Expired accepted reports end the job as
inconclusive and record stale verification on the run. A retry of those checks
needs a new host-approved job under the current run revision and remaining budget.
`MaxAttempts` limits ownership generations, not individual evaluator calls.

Set `JobRequest.EvaluationBudget` when workers will dispatch evaluators. This
pins a call limit and token allowance, plus either a money allowance with a
pricing revision or explicit `TokenOnly` accounting. Zero tokens permits only
calls whose host-calculated token bound is zero. There is no implicit unlimited
budget.

Built-in stores expose `verification.CallStore` for these jobs:

1. Call `BeginVerificationCall` with the current lease, a new call ID, the exact
   verifier name/revision and conservative token/money bounds. The transaction
   reserves the allowance and records every criterion assigned to that verifier.
2. Invoke the evaluator only after a successful begin. A repeated call ID or
   verifier group returns `ErrCallUncertain`, including after worker takeover.
   Read the saved call and reconcile its provider outcome. A new ID does not
   grant permission to repeat that group in the same job.
3. Call `CompleteVerificationCall` with the current lease, an authenticated usage
   observation and the report covering exactly those criteria. Usage, report and
   job progress commit together. An explicit evaluator failure with no report
   ends the job as inconclusive.

Unknown usage retains the full reserved amount. Known zero needs a receipt.
Reported overruns are preserved, even when they exceed the allowance, and block
further dispatch. You must enforce provider limits and validate usage receipts in
your host adapter; a receipt string alone proves neither its origin nor a billing
ceiling. Pricing revisions identify the host's pricing inputs, not a live quote.

Budgeted jobs reject direct `SaveVerificationJobReport` calls. Already dispatched
optional checks must settle before the job becomes ready. If cancellation,
expiry or another failed check ends a job with unresolved calls, their reserved
charges remain in its snapshot. This API does not settle late receipts after a
terminal job; host accounting reconciliation still needs integration. Keep those
charges when allocating budgets to later jobs. Concrete provider reconciliation
adapters and cross-job budget reservations remain separate work.

### Persist capture intent before dispatch

`verification.CaptureIntentStore` stores immutable capture policy before a host
starts generation. `CreateCaptureIntent` requires a pristine saved running run:
the exact registration revision, no output or completion, no consumed steps,
tokens or tools, and the pinned preparation and acceptance contract. Your host
must register it before dispatch. Empty counters cannot prove that an external
call has not already happened.

Seal the intent with `verification.SealCaptureIntent`. Its `Template` is a
budgeted `JobRequest` with a stable job ID and the run's registration revision.
The candidate reference has zero bytes and `evidence.Digest(nil)` as placeholders.
Its other metadata is fixed, including sensitivity and retention. `CreatedAt`
records when you reserved the future artifact identity. Supply a stable result ID
and an explicit positive `MaxCandidateBytes`; built-in stores allow at most one
MiB. The host must reserve the evaluation budget separately from generation.

Registration validates the contract and retained supporting evidence, rejects
existing or tombstoned candidate IDs, and limits the verification deadline to the
saved run deadline when one exists. A run, job ID and result ID can each belong
to one immutable intent in that exact scope. Changed policy cannot overwrite it.
The registration and identity indexes share a transaction.

After a restart, `GetRunCaptureIntent` discovers the intent by run ID. Once the
run has saved a completed final answer, `CaptureFromIntent` derives its job from
the current saved run revision and output. Only the candidate hash, byte count
and completed run revision replace template values. Capture and enqueue happen
in one transaction. Pass the returned job request and the intent's result ID to
`Engine.VerifyRun`; use a fresh claim ID only when acquiring new ownership.
Capture rechecks the saved run deadline. If you shortened it after registration,
an intent with a later deadline cannot enqueue work or create candidate evidence.
MongoDB stores an exact deadline alongside its millisecond BSON date so equal
run and job deadlines remain equal after a read. Existing documents keep their
stored precision; see the writer-upgrade notes in `MIGRATION.md`.

Normal enqueue and result commit also check saved intents. They reject a changed
job policy or result identity. A same-request registration retry remains valid
after execution, but it does not authorize another generation call. Capture
retries return the saved job, including terminal states, without recreating
removed evidence. Authorize every read and capture through your host policy.
When your store exposes `GetRunCaptureIntent`, the engine checks its sealed
scope, run and result identity after authorization and before enqueue, estimation
or evaluation. A read failure stops the worker. Custom stores without that
optional capability retain the explicit worker API; commit-time identity checks
remain necessary in every store that supports intents.

The storage interfaces alone do not gate execution. The experimental runtime
option below connects them for supported prepared and resumed runs. It is off by default.

### Capture privately before publication

Use the optional `run.CandidateStore` when the answer must stay private during
verification. Register the capture intent before generation, then pass the final
candidate and cumulative usage to `CaptureCandidate` while the saved run is
still running:

```go
job, err := candidates.CaptureCandidate(ctx, run.CandidateCapture{
    SchemaVersion:       1,
    IntentID:            intent.ID,
    ExpectedRunRevision: currentRun.Revision,
    Output:              approvedCandidate,
    FinishReason:        "stop",
    Usage:               cumulativeUsage,
})
```

The built-in stores save bounded candidate evidence, a capture receipt, execution
completion and the queued verification job in one transaction. `run.Output`
stays empty. The run is execution-completed with verification pending, so consumers
must read both fields. Capture rejects changed preparation, consumed accounting
that goes backwards, exceeded generation limits and a verification deadline
beyond the saved run deadline.

Pass the returned job request and intent result ID to `Engine.VerifyRun` with
your configured worker. Claims, evaluator settlement and guarded commit use the
existing protocol. Passing reports alone leave the answer private. The commit
copies the exact candidate bytes into `run.Output` atomically with the receipt,
outbox and passed status. Failed, inconclusive, cancelled or revoked checks do
not publish. The raw commit store still requires the host fence and authorization
provided by `verification.NewCommitter` or the engine worker.

Retry an uncertain capture with the identical request. A changed candidate,
revision, finish reason or usage conflicts with the stored capture. Retries
return the saved job without restoring deleted evidence; `CaptureFromIntent`
also discovers that job after restart. This storage capability does not register
intents or intercept normal engine streams, conversation history, steps or hooks.
Use the runtime option below for its supported execution paths. When you call
this storage operation directly, your host must authorize capture and keep
candidate text out of public transports.

### Capture an already saved candidate

Use the optional `verification.CaptureStore` when candidate evidence has not yet
been saved. Its `CaptureVerificationJob(ctx, request)` takes the same `JobRequest`
as enqueue. It copies bytes from the completed run's saved output and creates the
candidate artifact, job and pending run update in one transaction. The reference
must match that output's digest and byte count. Caller-supplied bytes are never
used by this operation.

Authorize the run read, evidence write and verification binding before capture.
Evidence policy must cover the requested sensitivity and retention. This is a
raw storage capability, so it cannot infer your host's grants. Supporting evidence
and the acceptance contract must already exist. The built-in stores limit the
candidate to one MiB and require real transactions, including on MongoDB.

Persist the request identity before calling capture. A failed transaction leaves
no new candidate artifact or job and does not change the run. After an ambiguous
acknowledgement, retry the same request. An identical existing artifact is reused;
a different reference under its ID or a deletion tombstone rejects capture. Once
a job exists, a same-request retry returns its historical snapshot without
restoring subsequently deleted bytes. Reauthorize any later use of that snapshot.

You can pass the same request to `Engine.VerifyRun` after capture; its enqueue
step recovers the existing job. This closes the artifact/enqueue write gap for a
saved run. Automatic finalization, intent registration before generation and
recovery of a crash before capture is requested remain separate integration work.

### Execute or recover a verifier group

Use `verification.NewExecutor` to connect budgeted jobs to a host evaluator. It
requires an `ExecutorStore`, `EvaluationAdapter`, `BindingAuthorizer` and trusted
`Clock`. Built-in stores implement the storage capability. There is no default
evaluator or authorization policy.

```go
executor, err := verification.NewExecutor(verification.ExecutorConfig{
    Store:      storage,
    Adapter:    hostEvaluator,
    Authorizer: currentAuthority,
    Clock:      hostClock,
})
if err != nil {
    return err
}
job, err := executor.Execute(ctx, verification.ExecutorRequest{
    Lease:            *claimed.Lease,
    Verifier:         "tests",
    VerifierRevision: "v1",
})
```

Each call advances one verifier name/revision group from the saved acceptance
contract. Fresh work passes through `Estimate`, durable dispatch and `Evaluate`.
An unresolved saved call goes directly to `Reconcile`, with its original call
ID, criteria and allowance. A completed call returns its saved job after current
authorization checks. Neither retry path invokes the evaluator again.

`Estimate` must calculate a conservative bound from trusted manifests and pricing
without billable provider work. Its pricing revision must match the job.
`Evaluate` must enforce those limits, retain a recoverable result under the call
ID and supply authenticated usage. `Reconcile` reads that original result. It
must not restart generation, tools or the evaluator when the provider cannot
confirm an outcome; return `ErrCallUncertain` instead. A usable reconciliation
returns the original report identity and usage receipt, not a newly scored copy.
Reconciliation must not perform billable work. If recovery itself requires a
charged operation, the host needs a separate reservation before invoking it.

Provider errors never authorize partial reports or refunds. Return a definitive
evaluator failure through `CallResult.Failure` with a nil error. Errors after
dispatch leave its conservative charge outstanding. Settlement validates the
exact call, candidate binding, contract and criterion set, then saves the report
with usage in one transaction. A storage acknowledgement can be lost after that
transaction commits, so retry through the executor or inspect the saved job.

The executor detaches callback inputs, rechecks authority around adapter access,
and checks lease expiry after host callbacks. Without renewal, its context deadline
is the earliest of the caller deadline, lease expiry and job deadline. The immutable
request keeps the original job deadline for recovery. Adapters must honor
cancellation and reauthorize their actual resource reads; an in-process callback
cannot forcibly stop a remote effect or uncooperative code. The scoped recovery
loop below schedules saved jobs through this executor. Production provider
qualification remains required.

For checks that may outlast their initial lease, set `LeaseRenewal` on
`ExecutorConfig` or `engine.VerificationWorkerConfig`:

```go
LeaseRenewal: &verification.LeaseRenewalPolicy{
    Duration: 30 * time.Second,
    Interval: 10 * time.Second,
},
```

Both durations must be positive. `Duration` cannot exceed one hour and `Interval`
cannot exceed half that duration. Leave the policy nil to retain fixed-lease
behavior. Your store must implement `verification.LeaseRenewer`; built-in stores
already do. The worker also applies this policy during required verification and
scoped recovery.

Renewal runs during `Estimate`, `Evaluate` and `Reconcile`. It checks current
authority, preserves the claim generation and cannot extend the job or caller
deadline. The callback context carries those deadlines; a separate watchdog
cancels it at the last acknowledged lease expiry. Your host ports must support
concurrent authorization, reads and renewal, and honor context cancellation.

A failed, malformed, late or lost renewal reply stops the callback. A paid call
already recorded remains unresolved for reconciliation, even if the provider
returns a report after cancellation. The executor stops and joins renewal before
advancing storage state. Each storage transition still checks live ownership.
This policy does not renew idle jobs or grant permission to repeat an effect.

Passing every required criterion makes the job ready. It does not publish a
result. Build `verification.CommitRequest` from the saved job's run revision,
binding, contract, accepted report IDs and current `JobLease`, then use the guarded
committer. The result receipt, outbox, run update and committed job state share
one transaction. Job-bound runs reject commits with missing or stale leases.
Historical result retries retain the same receipt and do not revive the lease.

Leases use trusted storage-adapter time. Workers cannot extend ownership by
changing a token's expiry. Configure host clocks consistently across writers and
keep every writer upgraded before enabling jobs; older binaries do not enforce
this protocol. Queue access also needs host authorization. There is no implicit
cross-scope worker discovery.

### Verify a saved run through the engine

Install `engine.WithVerificationWorker` to advance a captured candidate through
job creation, ownership, evaluation and guarded result commit:

```go
e, err := engine.New(
    engine.WithStore(storage),
    engine.WithVerificationWorker(engine.VerificationWorkerConfig{
        Adapter:    hostEvaluator,
        Authorizer: currentAuthority,
        Fence:      hostCommitFence,
        Clock:      hostClock,
    }),
)
if err != nil {
    return err
}
result, err := e.VerifyRun(ctx, engine.VerifyRunRequest{
    Job:      capturedJob,
    Claim:    workerClaim,
    ResultID: stableResultID,
})
```

`capturedJob` must identify saved evidence for a completed final-answer run and
its saved acceptance contract. Its evaluation budget must already be reserved
from the remaining run allowance. `workerClaim.JobID` must match the job, and
`stableResultID` uses `verification.PrefixResult`. Persist these identities before
calling the worker. Built-in stores supply the required capabilities; custom
stores must implement `JobStore`, `ExecutorStore` and `CommitStore`.

The worker runs each verifier name/revision group once, in contract order. It
stops when the job becomes ready or reaches a failed, inconclusive or cancelled
state. Optional groups that follow readiness are skipped; already dispatched
optional checks must settle. Failed, inconclusive and cancelled outcomes return
the saved job with a nil receipt. Inspect the state even when the error is nil.

After an error, retry with the same job, claim and result identities. Uncertain
evaluator calls reconcile their original operation. A lost commit acknowledgement
recovers the original request and receipt through fresh authorization under the
host fence. A changed result ID is rejected once the job has committed. The
worker never calls generation or tools, including during database restart recovery.

A claim can only be recovered while its stored lease is live. After expiry, use
a new claim ID to take over eligible work, keeping the job and result IDs stable.
The worker renews evaluator callbacks only when configured. It does not sweep
expired jobs or discover other scopes.

This is an explicit host operation. It does not change synchronous, streaming,
prepared or resumed run publication, install completion hooks or deliver outbox
events. `WithRequiredVerification` separately installs the limited runtime gate
below. `RuntimeCapabilities.ContextualVerification` remains false: tests use host
doubles and do not qualify a production evaluator or commit fence.


### Recover captured jobs in a scoped worker

Run `Engine.RunVerificationRecovery` from your host's supervised worker with an
authorized service context containing one exact scope and principal. The loop
uses the existing verification worker, capture intents and stored leases. It
doesn't start from `Engine.Start`, enumerate tenants or infer their grants.

```go
err := e.RunVerificationRecovery(ctx, engine.VerificationRecoveryLoop{
    Request: engine.VerificationRecoveryRequest{
        Owner:         "verification-recovery-1",
        LeaseDuration: time.Minute,
        Limit:         32,
    },
    Interval: 5 * time.Second,
    Observe: func(page engine.VerificationRecoveryPage) {
        // Send safe status metadata to your worker monitor.
    },
})
```

The first scan runs immediately. Later scans advance by job ID, including past
terminal, busy and unavailable jobs, and wrap after the last page. Each page has
at most 256 records and runs sequentially. Set a positive interval up to one
hour. `Observe` runs synchronously and must return promptly; it receives IDs,
observed states and recovery statuses without candidate text or private errors.
A discovery failure stops the loop so your supervisor can report it and back off.
Cancellation stops the loop and reaches active evaluator contexts.

For a host scheduler that already controls polling, call
`RecoverVerificationPage(ctx, request)` and retain its `NextAfter`. Zero means
start another scan. If cancellation interrupts a page, its cursor covers only
the processed records. Discovery validates and detaches the entire page before
any paid work, and each job passes current binding authorization.

A live lease is busy even when its owner string matches this worker. After
expiry, recovery claims a new generation and reconciles any saved evaluator call
under its original call ID. It never repeats agent generation or tool effects.
The capture intent supplies the result ID; jobs without one report `unmanaged`
and need explicit `VerifyRun` recovery. Overdue or exhausted work becomes
inconclusive through the store's existing atomic expiry operation. Unknown
provider charges stay reserved.

A lost claim acknowledgement waits for lease expiry. A lost commit
acknowledgement is observed as terminal on a later scan. `terminal` does not
promise a passed result or authorize delivery, and `unavailable` can follow a
durable write. Inspect saved state before taking any manual action. Callback
renewal follows the worker policy. This loop does not renew idle leases or publish
history, completion hooks or outbox events.
Production evaluator/fence qualification and host deployment remain required.


### Record ordinary terminal outcomes

Enable atomic lifecycle recording on the engine that executes ordinary runs:

```go
e, err := engine.New(
    engine.WithStore(storage),
    engine.WithPublicEventRecording(),
    engine.WithPublicEventReplay(subscriberPolicy),
)
```

Recording and reading are separate options. Recording requires
`event.TerminalStore`; the SQLite, PostgreSQL and MongoDB stores implement it.
MongoDB needs transactions, so use a replica set or sharded deployment. Without
the recording option, ordinary run updates retain their existing behavior.
Verification transactions already record their lifecycle events.

With recording enabled, completion, incomplete outcomes, failures and cancellation
commit their run snapshot and `execution_finished` event in one transaction.
Synchronous, streaming and mock execution use the same persistence helper, as do
`Engine.CancelRun` and terminal `Engine.UpdateRun` calls. A failed transaction
does not fall back to an unrecorded update or publish a completion hook. The
recording option does not publish output or grant replay access.

The storage request carries the exact scope, expected revision, full terminal
snapshot and a stable event ID. Its encoded snapshot is limited to 8 MiB. The
receipt contains a digest and identifiers, without private output or metadata.
Reuse the identical `event.TerminalUpdate` when a storage acknowledgement is
lost. It returns the original receipt, even after replay retention has pruned the
event. Changed contents or competing terminal writes are refused. A receipt
acknowledges that historical write; read the current run before acting on it.

Required-verification success continues through private candidate capture and
guarded result commit. The ordinary recording method rejects verification
results and required candidates. Direct store updates and imported terminal rows
do not produce these events, and enabling recording does not backfill history.
Verified-result commits also announce their result artifact. Arbitrary artifact
producers, approved-content replay and durable hook delivery remain open.

### Replay verification lifecycle metadata

Configure `engine.WithPublicEventReplay` with your current subscriber authorizer.
Then read a bounded page using the exact authorized scope and a cursor for one run:

```go
page, err := e.ReadPublicEvents(ctx, event.ReadRequest{
    After: event.Cursor{SchemaVersion: 1, RunID: runID, Sequence: 0},
    Limit: 64,
})
```

The authorizer implements `event.Authorizer.AuthorizePublicReplay(ctx, runID)`.
It must check the current subscriber's grant in the context's exact scope. The
reader calls it before and after storage, including when a cursor has expired.
Missing authority or storage fails construction. Ordinary engines keep replay
unavailable until you opt in.

Use each event ID to deduplicate delivery. Save `page.Next` after consuming a
page and use it to reconnect. Sequence numbers increase within a run; they do
not order different runs. These events contain typed lifecycle metadata and
stable identifiers, without candidate text, tool arguments, principal references
or provider errors. A historical `result_committed` event does not prove that
the result is still fresh or authorize access to its content.

For HTTP clients, use `GET /v1/runs/{id}/events?limit=64`. Pass the returned
`next_cursor` unchanged as `after` on the next request. The dashboard exposes the
same envelope through the `runs.replay` version 1 query:

```json
{"id": "<run-id>", "after": "<next_cursor>", "limit": 64}
```

Both transports return `{page, next_cursor, gap}`. Limits are 1 through 128;
omitting the limit or setting it to zero selects 128. Cursors are versioned,
run-bound strings. Use `next_cursor` instead of rebuilding a cursor from JSON
sequence numbers, which can exceed JavaScript's exact integer range. A cursor
never grants access, and every request rechecks the current subscriber.

REST returns HTTP 410 with `gap: true` and the authorized retained boundary when
history has expired. The dashboard returns that envelope as a successful query
so the dispatcher preserves the recovery cursor. In either case, fetch a current
authorized run snapshot before resuming. No event bodies accompany a gap.

Invalid cursors and limits return 400, denied access returns 403, a missing run in
the authorized scope returns 404, and unavailable replay returns 503. Errors use
static diagnostics rather than storage or authorization-provider messages. The
dashboard maps these to its corresponding typed errors. A malformed storage page
is unavailable, not an invalid client request. HTTP replay pages disable caching.

The existing `runs.events` query keeps its process-local integer offsets and
payload. You cannot reuse those offsets with `runs.replay`. Paged replay does not
start execution, rerun evaluators or create a live subscription.

#### Subscribe over SSE

Use `GET /v1/runs/{id}/events/stream` with the same `after` and `limit` query
parameters. On reconnect, `Last-Event-ID` takes precedence over `after`, so a
browser can keep its original URL while resuming from the last received page.
The header still has to contain a valid cursor for the requested run.

| Frame | Meaning | Browser event ID |
| --- | --- | --- |
| `page` | One authorized metadata page | `next_cursor` |
| `heartbeat` | An authorized empty page and current watermark | `next_cursor` |
| `gap` | Retention removed requested history; subscription closes | None |
| `error` | Static failure details after streaming started; subscription closes | None |

On `gap`, close your EventSource, fetch a current authorized run snapshot, and
create a new subscription using the returned `next_cursor`. Gap frames omit
`id:` so the browser cannot advance past missing history automatically. On a
non-retryable `error`, close the EventSource. A historical passed or committed
event still grants no permission to fetch result content.

The API admits up to 64 replay subscriptions per `API` instance. Excess requests
receive 503 with `replay_busy`. Each subscription lasts at most five minutes,
polls idle runs every second, bounds each read to five seconds and each write to
ten seconds or the remaining lifetime. Writers must support response-controller
deadlines, directly or through `Unwrap`; unsupported writers fail before SSE
headers are sent. Socket disconnects, observable write/flush failures, revocation
and retention gaps stop the subscription. Proxies must allow streaming and retain
these deadline capabilities. Installed proxy and browser qualification remains
open.

Each page is read and sent synchronously, with no queue or background producer.
`event.FollowReplay` exposes the same bounded loop for host adapters. It checks
authority through the configured engine on every read, including idle polls;
custom readers and consumers must honor context cancellation. It drains retained
backlogs before polling and never treats an execution-finished event as proof that
verification is finished. Reconnects can redeliver a page after a lost network
acknowledgement, so deduplicate by event ID and advance the cursor after consuming
the whole page. Browser EventSource advances its internal ID when it receives a
frame, before asynchronous application processing finishes. Durable consumers must
persist their own processed cursor and explicitly reconnect from it, using a new
EventSource or a streaming HTTP client. No exactly-once network delivery is implied.

Every new verified result commit writes `verification_passed`, `artifact_created`
and `result_committed`, in that order, in the same transaction as the receipt,
job and run update.
The committed-result event reuses the receipt's outbox ID. A crash or
lost acknowledgement cannot leave a committed result without this event, and
retrying the commit preserves its sequence. Existing historical receipts are
not backfilled automatically.

`artifact_created` announces the logical verified result artifact using only
`result_id`. You still need current authorization to read its content. Private
candidate and transcript capture do not emit artifact announcements, and the
public event contains no evidence ID, digest, filename, media type or bytes.
Storage checks that the receipt belongs to the exact run and current revision.
Ordinary terminal recording emits only `execution_finished`; arbitrary tool files
and external artifacts have no public artifact producer yet.

This adds an event type to schema 1 without changing its envelope or cursor.
Upgrade replay readers before enabling writers that emit it. If the same
deployment serves both, pause result commits until every reader has been upgraded.
Older readers reject unknown event types and cannot read a page containing the
new announcement. Keep compatible readers available if you roll back the writers.

Built-in stores expose optional `event.Store` operations for trusted host code:
`AppendPublicEvents`, `ReadPublicEvents`, `ReadEventWatermark` and
`PrunePublicEvents`. Appends require an expected run revision and last sequence,
validate lifecycle metadata against stored state, and commit a batch atomically.
Reuse the exact request after an uncertain write. A changed batch cannot reuse
one of its event IDs, even after retention removes the original envelope.
Raw storage reads do not authorize subscribers; use the engine reader or
`event.NewReader` at the public boundary.

Each run retains at most 256 envelopes. Appends evict the oldest envelopes when
needed; a host retention job can prune through an earlier cursor explicitly.
The ID, batch digest and sequence-range tombstones remain to fence delayed writes.
An expired cursor returns `event.ErrCursorGap`, no events, and a watermark with
the current run revision, result ID and retained range. Fetch a fresh authorized
snapshot before continuing at `page.Next`. Never treat a gap as an empty success.
Page sizes are limited to 128 and append batches to 32 events.

Verification storage produces these events inside its state-change transactions:

| Transition | Ordered metadata events |
| --- | --- |
| Private candidate capture and enqueue | `execution_finished`, `verification_pending` |
| Enqueue an already captured candidate | `verification_pending` |
| A required check fails or cannot establish a verdict | `verification_failed` or `verification_inconclusive` |
| Accepted report evidence expires before the remaining checks settle | `verification_stale` |
| Expire or cancel the current verification job | `verification_inconclusive` |
| Guarded verified result commit | `verification_passed`, `artifact_created`, `result_committed` |

Passing evaluator checks only makes a job ready. It emits no passed event until
commit rechecks authority and freshness. Retiring a superseded job does not emit
a new verdict for its replacement run. Retried capture, enqueue, cancellation
and result commits preserve the recorded IDs and sequence; failed transactions
leave neither state changes nor events behind.

Approved answer-content replay, arbitrary artifact producers and durable
completion-hook delivery remain open. Remote subscriptions use the same log; see
[remote messaging](/docs/execution/remote-messaging#follow-durable-metadata). Installed
browser/proxy reconnect and revocation checks also remain unqualified.


### Require verification before publishing an answer

`engine.WithRequiredVerification` connects preparation, generation, private
capture and the explicit worker, including authorized tools and suspension/resume.
This experimental option is
off by default. Complete the roadmap's G1 qualification before a production
rollout; the tests do not qualify a live provider, scanner or sandbox.

Configure it alongside `WithVerificationWorker`:

```go
engine.WithRequiredVerification(engine.RequiredVerificationConfig{
    Revision:          "policy-1",
    ContractID:        contract.ID,
    EvaluationBudget: evaluationBudget,
    Builder:           hostIntentBuilder,
    CaptureAuthorizer: hostEvidenceAuthorizer,
    WorkerOwner:       "verification-worker-1",
    LeaseDuration:     time.Minute,
})
```

Your builder implements `BuildVerificationIntent(ctx, input)`. It receives the
reserved run ID, exact scope, prepared digest, effective deadline and detached
`verification.ExecutionInputs`. These inputs contain the scanned task, initial
conversation, session and host model/tool revision pins. Return a
sealed schema-2 `verification.CaptureIntent` for run revision 1 with the configured
contract, policy revision and evaluation budget. Bind current host context and
allocate stable evidence, job and result IDs. The builder must not dispatch
billable work.

Encode `input.Inputs` with `Encode()`, seal an evidence reference for those bytes,
and include that exact reference in both `Binding.Context.ExecutionInputs` and
`Binding.Evidence`. Your host chooses its stable ID, sensitivity and retention.
Cortex checks the digest and size against its original inputs, authorizes
`ActionPut`, and saves the bytes before creating the run and registering its
intent. The artifact is limited to one MiB and 100 initial messages. A failed
start can leave an authorized artifact for your retention cleanup to remove.

Reserve a separate empty-content `CaptureIntent.Transcript` reference with zero
bytes and `evidence.Digest(nil)`, plus a positive `MaxTranscriptBytes` no greater
than one MiB. Keep this reservation outside `Template.Binding.Evidence`; capture
appends the final reference there and sets `Binding.Context.ExecutionTranscript`.
Its ID must differ from the candidate and supporting evidence IDs, and its
retention must cover the verification deadline.

The evidence authorizer receives `ActionPut` for both empty reservations before
generation and again for their final references before capture. Resume requires
`ActionRead` on input evidence. Missing history, deleted input evidence or a
changed initial conversation prevents required execution. Capture, evaluator
claims and result commit recheck the saved run against the input artifact.

The private `verification.ExecutionTranscript` records this run's checked
assistant/tool messages, cumulative usage and one host outcome per tool call.
It links to the initial inputs by digest. `completed`, `failed` and `denied`
come from runtime dispatch, with `local` or `external` recording who supplied
the result. External results are assertions by the authorized resumer. They do
not prove that an effect happened exactly once.

Candidate bytes, transcript bytes, completion metadata and the verification job
share one transaction. Capture rejects missing or duplicate results, mismatched
usage, changed inputs and a final message that differs from the candidate.
Deleting either artifact prevents later evaluator claims and result commit.
Resume retains prior outcomes across restart; if rescanning changes any retained
message, the required run stops before further effects or generation.

Pin the model with `WithModelRevision` and every available tool with
`WithToolRevision`. Required preparation rejects missing pins. These are your
host's implementation revisions; they do not attest which model a provider ran.

Supply a positive total token budget and a deadline through `RunOverrides.Budget`.
Preparation reserves the evaluator's maximum tokens and freezes the remainder
as the generation budget. For example, 1,000 total tokens with a 30-token
verification allowance gives generation 970 tokens. Evaluation money limits
remain separate from generation pricing. Provider-reported usage is never
clamped; an overrun prevents evaluation.

Required snapshots and continuations use schema 6. Re-prepare earlier required
snapshots; changing their schema number cannot supply missing evidence.
Schema 2 remains unchanged for ordinary runs.
A worker without the matching required configuration rejects required execution;
a required worker also rejects ordinary prepared snapshots. Contract, revision,
allowance and prepared identity cannot be replaced through run options. The
engine registers the intent before invoking the model.

`RunAgent`, `RunPrepared`, `StreamAgent` and `StreamPrepared` use the same gate.
Streaming emits progress metadata, then the final answer only after guarded
commit. It emits no candidate tokens. Generation steps retain timing and usage
but omit input/output text, and required runs do not save new conversation
history, including after success. Legacy `RunCompleted` fires only after the
required result commits. The execution-termination hook still describes execution
completion independently of verification.

A failed or inconclusive check returns `cortex.ErrRunUnverified`; an uncertain
worker or capture failure returns a static error without private diagnostics.
Neither path releases an answer or a `done` event. The saved run can be execution
`completed` while its verification is pending or failed, so read both fields.
A2A projects pending required verification as working and rejects unverified
completion artifacts.

REST maps `ErrRunUnverified` to HTTP 409 and `ErrVerificationUnavailable` to
HTTP 503. Both retain the standard `error` and numeric `code` fields and add
safe `details` with a stable `code` (`run_unverified` or
`verification_unavailable`), `message` and `retryable: false`. If the engine
returns a run, the details include `run_id`, `state` and `verification_status`.
Dashboard commands return the same details under `CONFLICT` or `UNAVAILABLE`.
SSE `error` events carry those fields directly.

Inspect the saved run before deciding what to do next. An unavailable verifier
can already have a running evaluation or committed work, so a new run may repeat
generation or tool effects. Recover through the saved intent/job identities and
the authorized verification worker. A missing run ID does not prove that no work
was saved. These errors omit candidate text and wrapped diagnostics.

The REST streaming handler sets SSE headers after startup succeeds. A failed
write cancels its provider context; this asks in-flight work to stop but cannot
undo an external effect or guarantee that a provider honors cancellation.

Checked-segment publication remains unsupported: required answers must wait for
whole-result verification. Tool-free snapshots reject unexpected tool calls;
tool-enabled snapshots enforce their frozen allowlist and current tool authority.
History publication, durable completion-hook replay, repairs and
recovery before candidate capture remain open. The scoped recovery loop can
schedule jobs after capture.
After a lost evaluator response, recover the saved intent/job through `VerifyRun`
with its stable identities and lease rules. That operation reconciles the
recorded call without generating again; it does not replay completion hooks.


### Authorize private tool handoffs

For required runs with tools, supply both `WithToolAuthorizer` and
`RequiredVerificationConfig.HandoffAuthorizer`. The latter implements
`AuthorizeToolHandoff(context.Context, cortex.Subject) error`. Check the current
principal's permission to inspect pending calls and supply their outcomes, using
the exact scope and run identity. It is a separate decision from permission to
execute a tool.

Preparation freezes schema 6 for required runs. Resume restores the
verification policy from that prepared payload rather than maintaining a second
policy copy in continuation configuration. Before claiming a suspension, Cortex
checks the saved budget, provenance, capture intent, policy revision, host ports,
current model/tool pins, initial conversation, handoff grant and evidence grants.
It repeats the checks after claim
and rechecks tool dispatch authority before effects. An older worker rejects the
new schema instead of resuming without the verification requirement.

Ordinary stream and dashboard responses omit private pending call IDs and
arguments. Use `Engine.PendingVerificationTools(ctx, runID)` from an authorized
host path to obtain them. That read does not claim the suspension or authorize
executing the tool. Pass the returned call IDs into the existing `Resume` or
`ResumeStream` API; approval checkpoints still use `ResolveCheckpoint`.

Tool arguments and results remain available to the authorized handler and model.
Public tool rows and lifecycle hooks omit their bodies; unknown model-supplied
tool names and private failure details are replaced with fixed metadata. Required
runs still do not publish conversation history. The continuation retains private
messages under the store's existing scope boundary until resume or cleanup.
Direct `Store()` access is a trusted host capability, so authorize it separately.

Result verification does not undo tool effects. Your tool authorizer must govern
writes, messages and other effects before dispatch. Verification controls whether
the final answer can be published. The restart tests prove that completed tool
steps are not replayed by normal continuation; a crash during an external effect
requires an explicit effect executor and provider reconciliation adapter.

### Recover an ambiguous external effect

Use `execution.NewEffectExecutor` from a trusted host handler when you need to
record a logical operation before calling an external service. The built-in
SQLite, PostgreSQL and MongoDB stores expose the optional `execution.EffectStore`
capability. Configure registered adapters and a current authorizer explicitly.
Ordinary engine tools do not use this executor automatically.

Keep the original `EffectRequest` for recovery. It binds an operation key,
original attempt ID, exact scope, run, argument digest, principal, authority
reference, deadline and trusted handler revision. Keys are unique across tools
within a scope. Reusing a key with different arguments or authority fails. The
journal stores the digest of the arguments, not their bytes.

Only a confirmed first reservation permits dispatch. An identical retry reads
the terminal receipt or calls the adapter's read-only `Reconcile` method. If the
provider cannot establish the result, Cortex returns `ErrEffectUncertain` and
retains the reservation. It does not repeat the mutation, including a declared
idempotent mutation. A database error while reserving or saving the receipt also
leaves the caller uncertain. Keep the same request and inspect it before acting.

Call `Reconcile` explicitly when the original dispatch deadline has expired.
Recovery requires fresh authorization but can read an older operation. Each
executor call has a 30-second upper bound and local admission control. Execution
also respects the request deadline. Your adapter must honor cancellation and
enforce current grants at the external write boundary; a permission check in
Cortex cannot make another service's write atomic with revocation.

An `applied` receipt records the provider's external identity, version and
retained evidence reference. It does not verify the task result. A `not_applied`
receipt must establish that the original attempt cannot later take effect.
Finding no object in an eventually consistent read is insufficient. Conflicting
terminal receipts fail without overwriting history.

Retain journal rows for as long as delayed deliveries or provider effects remain
possible. The host must retain its operation-to-run mapping, protect direct store
access and supply the pinned provider adapter. Automatic retries, compensation,
scheduler fencing and atomic task/event updates remain open work. The crash fixture checks a durable local file write followed by a
killed process and SQLite recovery; it does not qualify a production provider.


### Connect effect recovery to engine tools

Build an `execution.EffectExecutor` with your durable store, registered provider
adapters and current authorizer. Pass it to `engine.NewEffectToolHandler` with an
`EffectRequestResolver`, then register the returned handler through `WithTool`.
Pin the implementation with `WithToolRevision`, using the revision registered in
the executor. Existing publication checks still screen the tool's arguments and
result.

Your resolver owns the durable operation-to-run mapping. Return the original
complete request when a worker retries or resumes the same logical operation.
A model-provided call ID does not authorize another action, and an uncertain
outcome must never cause the resolver to allocate a replacement key. The helper
checks the exact scope, run, tool and argument digest before dispatch. It requires
an agent/run identity, so `Dispatch`, which has neither, cannot execute it.
Resolution and execution share the executor's 30-second bound.

Successful handler responses contain `effect_status`, `external_id` and
`external_version`. Provider evidence references and authority bindings stay in
the journal. `applied` means the provider acknowledged the action; `not_applied`
means its adapter established that the original attempt cannot later apply.
Neither status is an acceptance check.

A handler error matching `cortex.ErrEffectUncertain` stops synchronous, streamed
and approved execution before remaining sibling tools or another model request. The run
records `incomplete` with `tool_error` and the fixed uncertainty error, unless an
existing cancellation or deadline determines its terminal state. Private provider
errors and unfinished tool messages are not published as results. Required
verification does not evaluate or publish a candidate from this stop.

Approval remains a separate fact. When an approved action becomes uncertain,
the engine records the approval after confirming the durable stop, then returns
the uncertainty error. Repeating the checkpoint decision cannot run the action
again. If the terminal write fails, the checkpoint remains pending for host audit;
the claimed suspension still prevents repeated dispatch.

Reconcile the retained request through `EffectExecutor.Reconcile` with current
host authorization. Saving a recovered provider receipt does not resume the run,
mark its task correct or publish an answer. Governed continuation after
reconciliation and scheduler ownership are still required for automatic recovery. The SQLite-backed engine fixture verifies journal reopen and
zero duplicate dispatch; you still need to qualify your installed provider.


### Discover retained effects after a worker restart

You can call `EffectExecutor.RecoverPage` from a supervised host worker to find
operations in the executor's durable journal. SQLite, PostgreSQL and MongoDB
provide the optional `execution.EffectDiscoveryStore` capability. Authorize the
worker to discover one exact scope before calling this host-only API. It does
not enumerate tenants or expose a model tool or public route.

```go
request := execution.EffectListRequest{Limit: 32}
page, err := executor.RecoverPage(scopedWorkerContext, request)
// Retain page.NextAfter for the next pass, including after partial cancellation.
// An empty cursor starts another complete scan.
```

`RunID` optionally restricts discovery to one run. Each page reads at most 256
operation records, including terminal records, in operation-key digest order.
`After` is the last digest inspected. A full final page needs one empty read to
wrap; a shorter page wraps immediately. New inserts can sort before your cursor,
so keep scanning from the beginning after each wrap. Pages are observations and
do not provide a database snapshot or claim ownership of an operation.

The executor validates and detaches the whole page before probing any provider.
It then calls the existing `Reconcile` path for each original request, which
checks current authorization and rereads the journal. Retained terminal receipts
need no provider call. Denied, unsupported and uncertain operations still advance
the cursor so one unresolved operation cannot block the rest of the scope. A
later full scan revisits them with current grants and provider knowledge.

Each page has a 30-second deadline, including discovery. `MaxConcurrent` limits
active recovery pages separately from the executor's shared operation limit.
Callbacks and adapters must honor cancellation. On interruption, the returned
cursor covers only inspected operations; discovery errors return no progress.
Schedule passes and backoff in your host supervisor. Cortex does not start a
background recovery worker automatically.

Page items contain the operation digest, run ID and one of `terminal`,
`uncertain` or `unavailable`. Only an authorized terminal receipt supplies an
`applied` or `not_applied` outcome. No item contains arguments, authority
references, provider evidence or private errors. These are trusted worker
observations, not task acceptance or permission to publish a result. Recovery
cannot reserve another attempt, retry a mutation, compensate or resume a run.


### Carry structured task handoffs

Use `coordination.Handoff` for an assignment proposal. It binds the exact scope,
plan revision and digest, task, parent run, assignment ID, fence generation,
sender and receiver identities, grant reference, criteria, input artifact refs
and deadline. Seal it with `coordination.SealHandoff` before sending. The digest
protects the proposal's contents; it does not authenticate its sender or grant
permission to execute.

The receiving host supplies two callbacks to `NewHandoffReceiver`. `Resolve`
loads the current local plan, authenticated endpoint/principal mappings, parent
run and assignment ownership, and current grant ceiling. `Accept` records the
assignment with conditional ownership and grant checks. It must deduplicate the
assignment/fence/digest and preserve uncertainty after a lost database response.
Do not start an agent directly from this callback before reserving its work.

```go
receiver, err := coordination.NewHandoffReceiver(coordination.HandoffReceiverConfig{
    Resolve:       host.ResolveHandoff,
    Accept:        host.AcceptAssignment,
    MaxConcurrent: 8,
})
// Check err before constructing the transport handler.
handler, err := coordination.NewA2AHandoffHandler("worker-cluster", receiver, nil)
// Check err, then pass handler through engine.WithA2AHandoffHandler(handler).
// Configure engine.WithA2A separately to enable messaging.
```

`ValidateHandoff` compares the proposal with that current local context.
`planning.Authority.Within` checks resource revisions, access levels, complete
handler declarations, finite budgets and deadlines using the planner's existing
rules. A child cannot broaden the plan's task authority or its current host grant.
A mutation declaration requires a writable resource. The receiver detaches the
proposal before calling the resolver and bounds resolution plus acceptance to
30 seconds or the proposal's remaining lifetime, whichever is shorter.

For review assignments, set `Purpose` to `HandoffReview`. These grants allow read
access and no effect tools. The host must resolve `ProducerPrincipal` from local
provenance; a receiver with that same principal is rejected. This prepares a
restricted review context. It does not evaluate the artifact, establish reviewer
independence beyond principal identity or accept a peer's success claim. Input
refs still need authorized reads and current trusted verification before they
can satisfy dependencies.

`coordination.HandoffSendParams` encodes the sealed proposal for the existing A2A
bus. The host's canonical node name maps to empty local routing; remote names
must match the authenticated peer resolver's configured aliases. The bus's
`HandoffHandler` interface keeps assignment policy in `coordination`. Configure
its typed adapter on both sending and receiving hosts. A nil receiver in that
adapter permits outbound validation only.

The bus rejects unknown handoff versions, changed transport bindings and missing
handlers before persistence. It rechecks the proposal and conversation before
delivery. Structured handoffs never fall through to ordinary agent execution,
including when admission fails or the conversation has closed. Legacy text
messages keep their existing behavior. Handoffs use explicit host sends, with no
`ReplyWith` or `InReplyTo` token for an ordinary agent question.

The remote REST, JSON-RPC and SSE paths retain the body, parent run and full
fractional-second deadline. They derive the sender's node from authentication.
Their `queued` acknowledgement means that the bus retained the proposal, not
that the host accepted the assignment or that a task succeeded. Host errors are
reported without private provider details.

Durable assignment transitions, submission and review evidence, task acceptance,
shared reservations and scheduler fencing still need their runtime integration.
The HTTP/SSE tests use SQLite plan/message storage and fixture grant resolution
and acceptance callbacks. They do not qualify an installed multi-agent worker.

### Retain assignment progress

The built-in stores implement `coordination.AssignmentStore`. Use
`ProposeAssignment` to retain a sealed handoff, then `AdvanceAssignment` to append
host-observed progress. Every change carries the expected journal revision,
original handoff digest, fence generation, actor and reason. You can read the
latest observation with `GetAssignment`, page a plan's assignments with
`ListAssignments`, or inspect immutable revisions with `AssignmentHistory`.
All methods use the exact context scope.

The journal supports `proposed`, `accepted`, `working`, `blocked`, `submitted`,
`rejected` and `cancelled`. The receiver principal records progress; either endpoint principal
can record cancellation. Your host must authenticate that principal and authorize
the call. These methods preserve observations without reserving a worker,
authorizing dispatch or establishing task success. A `submitted` transition requires the stored evidence checks below. Independent
review admission remains separate.

A new proposal or progress transition checks the current sealed plan while
holding the same database lock used by `CommitRevision`. SQLite and PostgreSQL
lock the initial plan row. MongoDB performs a real write on that document inside
a transaction, so a concurrent replan conflicts even though revisions live in
separate documents. MongoDB requires transaction support. No fallback uses
unprotected reads.

Identical retries return the original immutable observation, including after a
later transition, expiry or replan. A changed request for an occupied revision
fails. This lets you recover a lost commit response without appending duplicate
history. A historical acknowledgment gives you no permission to run the task.
Fresh progress against a superseded plan fails; rejection and cancellation remain
available after expiry or replan. Cancellation records intent and does not prove
an external effect stopped. Reconcile retained effects separately.

Each revision stores its audit fields and predecessor digest in the same row.
Failed transactions leave no partial observation. Reads validate snapshot digests
and adjacent history bindings. History pages contain at most 256 revisions;
assignment lists return each identity's latest observation and are not a snapshot
across concurrent updates.

The journal alone does not satisfy `HandoffReceiverConfig.Accept`. Your host still
needs atomic current-grant and scheduler-ownership fences, work reservations and
verified evidence acceptance. Keep those checks in the acceptance integration.

### Submit retained task evidence

Before you execute an assigned child, pass the sealed handoff digest and parent
run ID through `PreparedRunOptions.Provenance.AssignmentDigest` and `ParentRunID`.
The engine validates their shape, stores them with the execution and preserves
them through prepared suspension and resume. The host supplies these fields;
model output cannot choose them. The digest binds the plan, task, assignment,
fence and identities already sealed into the handoff.

Capture the candidate through the existing verification job path. Its producer
must be `planning.ArtifactProducer(plan, taskID)`, with the task's output media
type and byte limit. The binding must use the task's pinned sources and tool
revisions. `planning.ValidateTaskBinding` shares those checks with dependency
readiness; passing it establishes structure, not verifier approval.

To move a working assignment to `submitted`, attach a `coordination.Submission`
to `AssignmentChange`. It pins the verification job ID and request digest, child
run ID and revision, and complete verification binding digest. A text answer or
peer success flag cannot substitute for these references. Submission adds no
public output and does not change the run's verification status.

Storage locks the current plan, then the child run, then reads the retained
evidence under transaction fences. It checks the handoff lineage, exact scope,
principal, prepared digest, contract, task sources/tools and candidate shape.
The job and run must agree on their current state and revision. Committed jobs
also need the matching stored result receipt. Failed and inconclusive jobs can
be submitted for review while retaining their actual verdicts.

Every referenced artifact must still exist and match its complete metadata and
bytes. Submission admits at most 64 references, including the candidate, with
at most 1 MiB per artifact and 8 MiB in total. It checks deadlines and retention
again after the reads. Missing, revoked, expired or oversized evidence rejects
the transition. PostgreSQL holds row locks, MongoDB performs transactional fence
writes, and SQLite retains its write transaction. No remote call runs under
these locks.

The journal preserves submission pins through later rejection or cancellation.
Identical retries acknowledge the original observation even if evidence was
subsequently removed; they never restore bytes or authorize a content read.
A database client timeout can leave a write that executes after a held lock is
released, so reconcile uncertain outcomes by reading retained state.

You still need current host authorization, scheduler ownership and grant fences.
Submission storage does not provide those external checks, establish reviewer
independence or mark a task successful. Dependent tasks continue to require fresh
trusted verification through the planning acceptance rules.

### Retain independent review findings

Use `coordination.ReviewStore` to record a review of an exact submitted assignment.
Prepare a separate reviewer run with its own handoff digest and prepared context.
Its handoff must use `HandoffReview`, cover the task's criteria, include the complete
submitted candidate and supporting references, and declare read-only resource
access with no effects. The reviewer must have a different principal and agent
endpoint from the producer. The host still authenticates those identities and
enforces the grant when executing tools.

The reviewer produces a `coordination.ReviewOutput` JSON document containing the
review handoff digest, subject assignment digest, binding digest and findings.
Each assigned criterion needs one finding: `supported`, `contradicted` or
`missing_evidence`. Include a reason and cite input artifact IDs for support or a
contradiction. Missing evidence may have no references. These findings are
advisory; they cannot replace a deterministic verifier result or satisfy the
acceptance contract by themselves.

`RecordAssignmentReview` requires the review assignment to be working and the
producer assignment to remain submitted. It checks the current plan, fences both
runs and verifies the review output against the completed reviewer run. Ordinary
run output and protected candidate storage are supported. Recording a review
leaves protected run output empty; authorize review queries separately because
findings can contain sensitive content. Unknown JSON fields, trailing documents
and changed findings are rejected.

The store reloads retained evidence under deletion fences, with at most 64 input
references, 1 MiB per input and 8 MiB total. The complete review record is bounded
to 384 KiB. Expiry and deadlines are checked after reads too. A producer's
verification may finish during review: admission checks the newer run revision
against the original job and binding, and preserves the resulting verdict.

Reviews are immutable observations. Use `GetAssignmentReview` or bounded
`ListAssignmentReviews` to inspect every finding, including contradictions.
An identical retry acknowledges the stored observation even after evidence is
removed; it does not restore access to those bytes. A changed retry conflicts.
No review count or majority vote marks a task successful.

You still need current host authorization, scheduler ownership checks and a
review completion policy. The storage capability does not dispatch the reviewer,
close its assignment or grant access to artifact content. Human adjudication and
verified task acceptance remain separate operations.

### Reserve durable task ownership

`coordination.ClaimStore` retains one owner for a task under the plan transaction.
A `ClaimRequest` pins the plan revision and digest, task, worker identity, grant
reference and expected ownership revision. Lease duration is positive and at most
30 minutes, capped by both plan and task deadlines. The store authenticates
neither the worker nor the grant; your scheduler must do that before admission.

Use `AcquireTaskClaim` to reserve ownership and `RenewTaskClaim` to extend a live
lease. Tokens include the claim ID, plan, task, worker, generation fence and
revision. A renewal advances the revision while keeping the fence. A new attempt
increments the fence. Stale tokens cannot renew or begin dispatch, and a plan
revision blocks both operations until the scheduler reassesses the work.

Before invoking an agent, reserve its child run ID with `BeginTaskDispatch`.
The same run cannot belong to another dispatch in the scope. Only a confirmed
first write returns `Fresh=true`. An identical retry returns the historical claim
with `Fresh=false`, including after a lost response. Never invoke the runtime from
that historical acknowledgment. Check the lease is still live when acting on a
fresh result, and retain ambiguous outcomes for reconciliation.

`ExpireTaskClaim` handles two different cases. An expired `held` reservation
becomes `released`, allowing a new attempt. An expired `dispatching` claim becomes
`recovering` and retains its child run and fence. It cannot be reacquired or
renewed. Recovery must establish what the run and its effects did before a later
protocol can release it; this capability provides no force-release shortcut.

Use `ListTaskClaims` for bounded discovery and `TaskClaimHistory` for immutable
revisions. Discovery includes tasks removed by replanning so their dispatches
remain recoverable. The list is not a snapshot; restart a sweep from the beginning
after its last page. Reads and historical retries do not establish current
ownership or permission to execute.

This is the ownership storage layer. `ClaimReadyTask`, aggregate budget admission,
current-grant fencing, parent cancellation, runtime dispatch and recovery
settlement still need scheduler integration. Acquiring a claim alone does not
prove that dependencies passed, that a worker may use a tool, or that budget is
available. No database transaction spans an agent or external tool call.

### Share capacity across workers

Create one `execution.ReservationPolicy` for the plan, then use the optional
`execution.BudgetStore` to reserve capacity before dispatch. The immutable policy
sets explicit allowances for steps, tokens, tool calls, fan-out attempts, replans
and USD micros. A zero allowance permits no consumption in that dimension.
This differs from the optional zero limits in a single-run `execution.Budget`.
The existing per-run budget remains unchanged.

A monetary policy needs a pinned pricing revision and requests with a trusted
upper bound. Set `TokenOnly` when you cannot establish that bound; the account
then advertises no money ceiling and rejects monetary allocations. A reservation
cannot make a provider obey its estimate. Enforce limits in the adapter and retain
reported overruns in settlement.

`Reserve` pins the current plan digest, task, host-owned attempt reference, parent
reservation, allocation and deadline. Storage checks the task's limits and the
remaining plan capacity in one plan transaction. Replanning can narrow the
account's effective limits but cannot reset its charges or replace its policy.
Identical retries return the original reservation and do not allocate twice.
Reservations grant no tool permissions and do not start a worker.

Use a `leaf` reservation for execution and a `branch` to delegate capacity to
children. Children spend from their parent's allocation without charging that
allocation twice at the root. A branch keeps its full reservation until it
closes. Child overruns propagate immediately through open ancestors, preventing
new work from using capacity that has already been consumed.

`Settle` records final usage once. Mark each known dimension in `ReservationUsage`
and supply a trusted receipt reference; known zero can release unused capacity.
Unknown dimensions keep their full allocation. A lease timeout or deadline never
turns missing usage into zero. Changed settlement retries conflict. A branch
closes only after all children have final accounting, and its charge is derived
from those children rather than a caller-supplied total.

Each reservation permanently consumes at least one fan-out attempt, including an
attempt that never dispatched. Accounts support at most 1,024 retained reservations
and 16 levels, bounding transactional reads and recursive accounting. Aggregate
integer overflow blocks admission and reports `Overflow=true`; individual usage
receipts retain their original amounts.

`GetBudgetSnapshot` reads a consistent charge under the plan transaction and shows
limits narrowed by the current plan. `GetReservationPolicy` returns the original
policy. `ListReservations` provides bounded discovery, while `GetReservation`
returns allocation and final settlement. Protect these host APIs with current
authorization. Binding reservations to claims, provider accounting, reviewer and
verification dispatch still requires scheduler/runtime integration.
