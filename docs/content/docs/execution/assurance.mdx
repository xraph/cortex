title: Execution outcomes and safety
description: Read execution state, verification and content screening separately, and inspect the mechanisms installed in your host.
---

A completed run means the engine reached a final answer. It does not establish that the answer is correct. Read three fields together:

| Field | What it tells you |
| --- | --- |
| `state` and `stop_reason` | Whether execution completed, stopped at a limit, failed or was cancelled |
| `verification_status` | Whether explicit result checks have passed; historical runs default to `unchecked` |
| `provenance.publication_status` | Whether published content was screened, redacted, flagged or left unscanned |

Synchronous REST execution returns `stop_reason`, `verification_status`, `publication_status` and an optional `result_ref` alongside its existing fields. Saved run responses retain publication status inside `provenance`. Terminal stream events carry the same outcome categories. A closed, expired or disconnected feed does not prove completion; load the saved run when events are missing.

A2A projects incomplete runs as the protocol's existing failed task state. Its task and status-update metadata includes `cortex.assurance` with the execution state, stop reason, verification status and publication status. This metadata also survives the gRPC binding.

## Publication policy

Configure the boundary with `engine.WithPublicationPolicy` and install a checker with `engine.WithPublicationGate`, or use the existing `WithSafety` scanner adapter. Buffered publication is the default. The engine holds candidate content until the configured checker accepts it. A required but unavailable checker, checker error, invalid decision or exceeded byte limit prevents publication.

Checked-segment streaming requires an explicit `safety.IncrementalGate`. An accepted prefix cannot be retracted, so use buffered mode when a rule needs the complete response. Explicitly disabled scanning reports `unscanned`; it does not remove byte limits.

Content screening covers input, output, retrieved content, tool results and public error text. If screening would rewrite tool arguments, execution stops instead of issuing a changed command. A scanner decision describes content screening only. It cannot certify the answer's factual accuracy.

## Installed capabilities

`Engine.RuntimeCapabilities()` and the dashboard's `runtime.detail.assurance` describe process configuration. They report prepared-execution support, publication mode, whether a gate is installed and whether that gate advertises incremental checking. Presence does not certify provider health or effectiveness.

Automatic contextual verification at publication remains unavailable. The explicit
`VerifyRun` worker below can verify saved candidates. Default preparation freezes collected inputs and checks its source read set for observed changes. Those independent reads are not one transaction.

## Atomic preparation

Use `engine.WithAtomicPreparation()` when collection must read one consistent database snapshot. This requires the optional `store.PreparationSnapshotter` capability. The built-in PostgreSQL, SQLite and MongoDB stores implement it. PostgreSQL uses a read-only repeatable-read transaction, SQLite uses a read-only transaction request with serializable isolation, and MongoDB uses explicit snapshot read concern with majority commit concern. MongoDB needs transaction support, such as a replica set. Configure SQLite with WAL and a busy timeout when writers need to proceed during capture.

The capture includes the agent, persona, inline skills, inline traits and ancestor overlays, including missing overlays. It returns a scope-bound `provenance.source_snapshot` receipt and `source_validation=atomic_store_snapshot` only after collection and transaction completion succeed. The receipt ID identifies the capture; it is not a reusable database revision. Captured readers expire when collection returns, and publication checks run after the transaction closes.

Unsupported stores, failed transactions and any nonempty skill knowledge reference fail preparation. A database transaction cannot qualify live external retrieval, even when a knowledge provider is installed. There is no silent fallback to ordinary reads. Existing prepared artifacts retain their original provenance.

An atomic store receipt covers source collection only. Model and tool revisions, contextual correctness, authorization, external state and evaluation isolation still need their own checks. Keep reproducibility-required evaluation disabled whenever any required guarantee is missing.

## Observe failures

`plugin.RunTerminated` receives a content-free summary after the terminal store update succeeds. It includes incomplete and cancelled runs. `plugin.PublicationRejected` reports a bounded policy reason, including rejection before a run exists. Its run ID is then empty.

The audit extension records these events. Metrics count incomplete runs, cancellations, terminal policy failures and rejected checks without using prompts, evidence IDs or arbitrary provider values as labels. Hooks remain best effort. They do not provide durable exactly-once delivery or replace a required audit transaction.

## Rollout checks

Prepared snapshots and continuations use schema 2. Drain or cancel older schema-1 pauses on compatible workers. Re-prepare stored schema-1 harnesses as new versions and evaluate them again; changing a schema number cannot recreate the missing policy or preserve prior acceptance.

Scopes support at most three ordered, unique levels. Listing can use an ancestor prefix, while mutation and execution require the exact resource scope. Invalid or inconsistent historical rows fail closed. Use the administrative `store.ScopeInspector` inventory before an operator-approved migration; the engine never truncates or repairs stored identity automatically.

Qualify your installed provider, scanner, authorization and storage paths before rollout. Passing fixture tests or the deterministic local demo does not establish live-model quality, effective scanning or sandbox isolation.


## Evidence and acceptance contracts

You can build independent evaluators with the `evidence` and `verification` packages. Engine verification is still disabled; saving a report does not change a run's status or authorize publication.

Seal captured bytes with `evidence.Seal`. The reference binds their SHA-256 digest, exact scope, version, producer, sensitivity and retention deadline. Wrap a built-in storage capability with `evidence.NewRepository` and your host authorizer before serving content. Reads check both bytes and metadata, then recheck source access. Built-in storage limits content to one MiB; inject a separate repository for larger artifacts. The authorizer must enforce current grants, sensitivity and retention.

Create an ordered `verification.Contract` with at least one required criterion. Each criterion names a verifier revision and a host-registered manifest. `verification.NewVerifier` accepts typed schema, test, state and human adapters, a host authorizer and a clock. Test adapters still need a qualified execution environment; registering one does not provide isolation.

`verification.Aggregate` requires every required criterion to pass for the same run and captured context. Optional scores cannot compensate for a failed check. Missing checks are inconclusive. Expired reports, source observations or human approvals are stale. A human verdict must name its actor and decision revision and match the complete evidence binding.

Before acting on a result, reauthorize the resources and compare a trusted current binding with `verification.CheckFreshness`. A report digest checks integrity, not authorship or current permission. Only trusted host paths may create or persist reports. The built-in stores expose `verification.Store` as an optional capability and retain immutable history for audit.

Evidence deletion retains an audit tombstone. Set the authenticated actor with `evidence.WithDeletionActor` before deleting through the authorized repository. The first deletion records the reference, actor, time and reason; retries cannot rewrite that history or restore the bytes. Tombstone reads are a separate storage capability and require host audit authorization.


## Commit a verified result

Built-in stores expose optional `verification.CommitStore`. A commit consumes
saved contracts and reports, checks the exact run revision and retained evidence,
and saves the receipt, metadata-only outbox entry and run update in one
transaction. The run must contain a completed final answer pending verification,
with the same prepared digest and acceptance contract. Failed or missing required
checks cannot pass this operation.

Use `verification.NewCommitter(storage, hostFence, hostAuthorizer)` at your host
boundary. Its `Commit(ctx, request)` method checks current grants inside the host
fence, calls storage while that fence is held and validates the returned receipt.
Every retry passes through the same authorization check. The request contains
saved record IDs and a trusted binding, never model-authored evaluators or
permission claims.

Your `verification.CommitFence` must hold authorization and revision guards
through the entire callback. Capture the current binding from authoritative
state, invoke the callback once and synchronously, and require every relevant
policy or revision writer to use the same guards. That includes writers in other
processes. A permission lookup followed by an unlocked database write leaves a
revocation gap. Cortex supplies no permissive default fence.

For an external resource, use a version-conditional operation or define and
check an observation window appropriate to the contract. A local guard cannot
freeze a remote service. Keep captured provenance timestamps intact when
checking that its resource versions still match; any changed binding requires
fresh reports.

Retry the same request and result ID after an ambiguous acknowledgement.
Storage returns the original historical receipt and event ID, even if evidence
has since expired or been deleted. The guarded API still requires current access.
A receipt does not renew evidence freshness or grant permission to publish.
`GetCommittedResult` is a raw storage read, so protect audit access separately.

SQLite uses a write transaction; PostgreSQL locks the run and evidence records.
MongoDB requires a transaction-capable deployment and fences evidence against
concurrent deletion. A standalone MongoDB server returns
`verification.ErrCommitUnavailable`. Requests and receipts are limited to one
MiB, with at most 256 report IDs and eight MiB of report JSON and evidence bytes
processed in one attempt.

Engine verification gates, verification-job scheduling and public outbox dispatch
are not connected yet. This storage and host boundary does not change existing
`RunCompleted` hooks or enable contextual verification in runtime capabilities.


## Durable verification work

Built-in stores expose `verification.JobStore` for checks on a saved candidate.
`EnqueueVerificationJob` validates the captured run, contract and retained
evidence, then saves the job and moves the run to pending verification in one
transaction. Supply the exact run revision. A retry with the same job ID and
request returns the saved job; changed input under that ID conflicts.

A job pins the candidate binding, contract, deadline and ownership-attempt limit.
It does not run generation or tools. Each claim has an owner, unique claim ID,
expiry and increasing generation. Retry the same claim ID after a lost
acknowledgement to recover its current lease. An expired lease needs a new claim
ID. Previously consumed claim IDs cannot acquire later generations.

| Operation | Storage behavior |
| --- | --- |
| `GetVerificationJob`, `ListVerificationJobs` | Read exact-scope snapshots with bounded ID pagination |
| `ClaimVerificationJob` | Acquire unclaimed work or replace an expired lease, subject to deadline and attempt limits |
| `RenewVerificationJob` | Extend a live lease, capped by the job deadline; never revive expired ownership |
| `SaveVerificationJobReport` | Save the report and accepted progress together under the current lease |
| `ExpireVerificationJob` | Finish overdue work or work with exhausted ownership attempts as inconclusive |
| `CancelVerificationJob` | Retire unfinished verification and clear its lease without retracting a committed result |

Accepted reports survive takeover and database restart. Workers inspect those
report IDs before dispatching another check. A later report cannot replace an
accepted criterion with a more favorable verdict. Failed or inconclusive
required outcomes finish the job and update the run's verification status; the
execution state still describes the original generation. Contract requirements
apply even when a verifier reports a pass: missing proof or a required human
verdict makes the check inconclusive. Expired accepted reports end the job as
inconclusive and record stale verification on the run. A retry of those checks
needs a new host-approved job under the current run revision and remaining budget.
`MaxAttempts` limits ownership generations, not individual evaluator calls.

Set `JobRequest.EvaluationBudget` when workers will dispatch evaluators. This
pins a call limit and token allowance, plus either a money allowance with a
pricing revision or explicit `TokenOnly` accounting. Zero tokens permits only
calls whose host-calculated token bound is zero. There is no implicit unlimited
budget.

Built-in stores expose `verification.CallStore` for these jobs:

1. Call `BeginVerificationCall` with the current lease, a new call ID, the exact
   verifier name/revision and conservative token/money bounds. The transaction
   reserves the allowance and records every criterion assigned to that verifier.
2. Invoke the evaluator only after a successful begin. A repeated call ID or
   verifier group returns `ErrCallUncertain`, including after worker takeover.
   Read the saved call and reconcile its provider outcome. A new ID does not
   grant permission to repeat that group in the same job.
3. Call `CompleteVerificationCall` with the current lease, an authenticated usage
   observation and the report covering exactly those criteria. Usage, report and
   job progress commit together. An explicit evaluator failure with no report
   ends the job as inconclusive.

Unknown usage retains the full reserved amount. Known zero needs a receipt.
Reported overruns are preserved, even when they exceed the allowance, and block
further dispatch. You must enforce provider limits and validate usage receipts in
your host adapter; a receipt string alone proves neither its origin nor a billing
ceiling. Pricing revisions identify the host's pricing inputs, not a live quote.

Budgeted jobs reject direct `SaveVerificationJobReport` calls. Already dispatched
optional checks must settle before the job becomes ready. If cancellation,
expiry or another failed check ends a job with unresolved calls, their reserved
charges remain in its snapshot. This API does not settle late receipts after a
terminal job; host accounting reconciliation still needs integration. Keep those
charges when allocating budgets to later jobs. Concrete provider reconciliation
adapters and cross-job budget reservations remain separate work.

### Persist capture intent before dispatch

`verification.CaptureIntentStore` stores immutable capture policy before a host
starts generation. `CreateCaptureIntent` requires a pristine saved running run:
the exact registration revision, no output or completion, no consumed steps,
tokens or tools, and the pinned preparation and acceptance contract. Your host
must register it before dispatch. Empty counters cannot prove that an external
call has not already happened.

Seal the intent with `verification.SealCaptureIntent`. Its `Template` is a
budgeted `JobRequest` with a stable job ID and the run's registration revision.
The candidate reference has zero bytes and `evidence.Digest(nil)` as placeholders.
Its other metadata is fixed, including sensitivity and retention. `CreatedAt`
records when you reserved the future artifact identity. Supply a stable result ID
and an explicit positive `MaxCandidateBytes`; built-in stores allow at most one
MiB. The host must reserve the evaluation budget separately from generation.

Registration validates the contract and retained supporting evidence, rejects
existing or tombstoned candidate IDs, and limits the verification deadline to the
saved run deadline when one exists. A run, job ID and result ID can each belong
to one immutable intent in that exact scope. Changed policy cannot overwrite it.
The registration and identity indexes share a transaction.

After a restart, `GetRunCaptureIntent` discovers the intent by run ID. Once the
run has saved a completed final answer, `CaptureFromIntent` derives its job from
the current saved run revision and output. Only the candidate hash, byte count
and completed run revision replace template values. Capture and enqueue happen
in one transaction. Pass the returned job request and the intent's result ID to
`Engine.VerifyRun`; use a fresh claim ID only when acquiring new ownership.
Capture rechecks the saved run deadline. If you shortened it after registration,
an intent with a later deadline cannot enqueue work or create candidate evidence.
MongoDB stores an exact deadline alongside its millisecond BSON date so equal
run and job deadlines remain equal after a read. Existing documents keep their
stored precision; see the writer-upgrade notes in `MIGRATION.md`.

Normal enqueue and result commit also check saved intents. They reject a changed
job policy or result identity. A same-request registration retry remains valid
after execution, but it does not authorize another generation call. Capture
retries return the saved job, including terminal states, without recreating
removed evidence. Authorize every read and capture through your host policy.
When your store exposes `GetRunCaptureIntent`, the engine checks its sealed
scope, run and result identity after authorization and before enqueue, estimation
or evaluation. A read failure stops the worker. Custom stores without that
optional capability retain the explicit worker API; commit-time identity checks
remain necessary in every store that supports intents.

The storage interfaces alone do not gate execution. The experimental runtime
option below connects them for supported prepared and resumed runs. It is off by default.

### Capture privately before publication

Use the optional `run.CandidateStore` when the answer must stay private during
verification. Register the capture intent before generation, then pass the final
candidate and cumulative usage to `CaptureCandidate` while the saved run is
still running:

```go
job, err := candidates.CaptureCandidate(ctx, run.CandidateCapture{
    SchemaVersion:       1,
    IntentID:            intent.ID,
    ExpectedRunRevision: currentRun.Revision,
    Output:              approvedCandidate,
    FinishReason:        "stop",
    Usage:               cumulativeUsage,
})
```

The built-in stores save bounded candidate evidence, a capture receipt, execution
completion and the queued verification job in one transaction. `run.Output`
stays empty. The run is execution-completed with verification pending, so consumers
must read both fields. Capture rejects changed preparation, consumed accounting
that goes backwards, exceeded generation limits and a verification deadline
beyond the saved run deadline.

Pass the returned job request and intent result ID to `Engine.VerifyRun` with
your configured worker. Claims, evaluator settlement and guarded commit use the
existing protocol. Passing reports alone leave the answer private. The commit
copies the exact candidate bytes into `run.Output` atomically with the receipt,
outbox and passed status. Failed, inconclusive, cancelled or revoked checks do
not publish. The raw commit store still requires the host fence and authorization
provided by `verification.NewCommitter` or the engine worker.

Retry an uncertain capture with the identical request. A changed candidate,
revision, finish reason or usage conflicts with the stored capture. Retries
return the saved job without restoring deleted evidence; `CaptureFromIntent`
also discovers that job after restart. This storage capability does not register
intents or intercept normal engine streams, conversation history, steps or hooks.
Use the runtime option below for its supported execution paths. When you call
this storage operation directly, your host must authorize capture and keep
candidate text out of public transports.

### Capture an already saved candidate

Use the optional `verification.CaptureStore` when candidate evidence has not yet
been saved. Its `CaptureVerificationJob(ctx, request)` takes the same `JobRequest`
as enqueue. It copies bytes from the completed run's saved output and creates the
candidate artifact, job and pending run update in one transaction. The reference
must match that output's digest and byte count. Caller-supplied bytes are never
used by this operation.

Authorize the run read, evidence write and verification binding before capture.
Evidence policy must cover the requested sensitivity and retention. This is a
raw storage capability, so it cannot infer your host's grants. Supporting evidence
and the acceptance contract must already exist. The built-in stores limit the
candidate to one MiB and require real transactions, including on MongoDB.

Persist the request identity before calling capture. A failed transaction leaves
no new candidate artifact or job and does not change the run. After an ambiguous
acknowledgement, retry the same request. An identical existing artifact is reused;
a different reference under its ID or a deletion tombstone rejects capture. Once
a job exists, a same-request retry returns its historical snapshot without
restoring subsequently deleted bytes. Reauthorize any later use of that snapshot.

You can pass the same request to `Engine.VerifyRun` after capture; its enqueue
step recovers the existing job. This closes the artifact/enqueue write gap for a
saved run. Automatic finalization, intent registration before generation and
recovery of a crash before capture is requested remain separate integration work.

### Execute or recover a verifier group

Use `verification.NewExecutor` to connect budgeted jobs to a host evaluator. It
requires an `ExecutorStore`, `EvaluationAdapter`, `BindingAuthorizer` and trusted
`Clock`. Built-in stores implement the storage capability. There is no default
evaluator or authorization policy.

```go
executor, err := verification.NewExecutor(verification.ExecutorConfig{
    Store:      storage,
    Adapter:    hostEvaluator,
    Authorizer: currentAuthority,
    Clock:      hostClock,
})
if err != nil {
    return err
}
job, err := executor.Execute(ctx, verification.ExecutorRequest{
    Lease:            *claimed.Lease,
    Verifier:         "tests",
    VerifierRevision: "v1",
})
```

Each call advances one verifier name/revision group from the saved acceptance
contract. Fresh work passes through `Estimate`, durable dispatch and `Evaluate`.
An unresolved saved call goes directly to `Reconcile`, with its original call
ID, criteria and allowance. A completed call returns its saved job after current
authorization checks. Neither retry path invokes the evaluator again.

`Estimate` must calculate a conservative bound from trusted manifests and pricing
without billable provider work. Its pricing revision must match the job.
`Evaluate` must enforce those limits, retain a recoverable result under the call
ID and supply authenticated usage. `Reconcile` reads that original result. It
must not restart generation, tools or the evaluator when the provider cannot
confirm an outcome; return `ErrCallUncertain` instead. A usable reconciliation
returns the original report identity and usage receipt, not a newly scored copy.
Reconciliation must not perform billable work. If recovery itself requires a
charged operation, the host needs a separate reservation before invoking it.

Provider errors never authorize partial reports or refunds. Return a definitive
evaluator failure through `CallResult.Failure` with a nil error. Errors after
dispatch leave its conservative charge outstanding. Settlement validates the
exact call, candidate binding, contract and criterion set, then saves the report
with usage in one transaction. A storage acknowledgement can be lost after that
transaction commits, so retry through the executor or inspect the saved job.

The executor detaches callback inputs, rechecks authority around adapter access,
and checks lease expiry after host callbacks. Its context deadline is the earliest
of the caller deadline, lease expiry and job deadline. The immutable request keeps
the original job deadline for recovery. Adapters must honor cancellation and
reauthorize their actual resource reads; an in-process callback cannot forcibly
stop a remote effect or uncooperative code. Lease renewal, worker scheduling,
provider qualification and engine finalization remain separate integration work.

Passing every required criterion makes the job ready. It does not publish a
result. Build `verification.CommitRequest` from the saved job's run revision,
binding, contract, accepted report IDs and current `JobLease`, then use the guarded
committer. The result receipt, outbox, run update and committed job state share
one transaction. Job-bound runs reject commits with missing or stale leases.
Historical result retries retain the same receipt and do not revive the lease.

Leases use trusted storage-adapter time. Workers cannot extend ownership by
changing a token's expiry. Configure host clocks consistently across writers and
keep every writer upgraded before enabling jobs; older binaries do not enforce
this protocol. Queue access also needs host authorization. There is no implicit
cross-scope worker discovery.

### Verify a saved run through the engine

Install `engine.WithVerificationWorker` to advance a captured candidate through
job creation, ownership, evaluation and guarded result commit:

```go
e, err := engine.New(
    engine.WithStore(storage),
    engine.WithVerificationWorker(engine.VerificationWorkerConfig{
        Adapter:    hostEvaluator,
        Authorizer: currentAuthority,
        Fence:      hostCommitFence,
        Clock:      hostClock,
    }),
)
if err != nil {
    return err
}
result, err := e.VerifyRun(ctx, engine.VerifyRunRequest{
    Job:      capturedJob,
    Claim:    workerClaim,
    ResultID: stableResultID,
})
```

`capturedJob` must identify saved evidence for a completed final-answer run and
its saved acceptance contract. Its evaluation budget must already be reserved
from the remaining run allowance. `workerClaim.JobID` must match the job, and
`stableResultID` uses `verification.PrefixResult`. Persist these identities before
calling the worker. Built-in stores supply the required capabilities; custom
stores must implement `JobStore`, `ExecutorStore` and `CommitStore`.

The worker runs each verifier name/revision group once, in contract order. It
stops when the job becomes ready or reaches a failed, inconclusive or cancelled
state. Optional groups that follow readiness are skipped; already dispatched
optional checks must settle. Failed, inconclusive and cancelled outcomes return
the saved job with a nil receipt. Inspect the state even when the error is nil.

After an error, retry with the same job, claim and result identities. Uncertain
evaluator calls reconcile their original operation. A lost commit acknowledgement
recovers the original request and receipt through fresh authorization under the
host fence. A changed result ID is rejected once the job has committed. The
worker never calls generation or tools, including during database restart recovery.

A claim can only be recovered while its stored lease is live. After expiry, use
a new claim ID to take over eligible work, keeping the job and result IDs stable.
This worker does not renew leases, sweep expired jobs or discover other scopes.

This is an explicit host operation. It does not change synchronous, streaming,
prepared or resumed run publication, install completion hooks or deliver outbox
events. `WithRequiredVerification` separately installs the limited runtime gate
below. `RuntimeCapabilities.ContextualVerification` remains false: tests use host
doubles and do not qualify a production evaluator or commit fence.


### Require verification before publishing an answer

`engine.WithRequiredVerification` connects preparation, generation, private
capture and the explicit worker, including authorized tools and suspension/resume.
This experimental option is
off by default. Complete the roadmap's G1 qualification before a production
rollout; the tests do not qualify a live provider, scanner or sandbox.

Configure it alongside `WithVerificationWorker`:

```go
engine.WithRequiredVerification(engine.RequiredVerificationConfig{
    Revision:          "policy-1",
    ContractID:        contract.ID,
    EvaluationBudget: evaluationBudget,
    Builder:           hostIntentBuilder,
    CaptureAuthorizer: hostEvidenceAuthorizer,
    WorkerOwner:       "verification-worker-1",
    LeaseDuration:     time.Minute,
})
```

Your builder implements `BuildVerificationIntent(ctx, input)`. It receives the
reserved run ID, exact scope, prepared digest, effective deadline and detached
`verification.ExecutionInputs`. These inputs contain the scanned task, initial
conversation, session and host model/tool revision pins. Return a
sealed schema-2 `verification.CaptureIntent` for run revision 1 with the configured
contract, policy revision and evaluation budget. Bind current host context and
allocate stable evidence, job and result IDs. The builder must not dispatch
billable work.

Encode `input.Inputs` with `Encode()`, seal an evidence reference for those bytes,
and include that exact reference in both `Binding.Context.ExecutionInputs` and
`Binding.Evidence`. Your host chooses its stable ID, sensitivity and retention.
Cortex checks the digest and size against its original inputs, authorizes
`ActionPut`, and saves the bytes before creating the run and registering its
intent. The artifact is limited to one MiB and 100 initial messages. A failed
start can leave an authorized artifact for your retention cleanup to remove.

Reserve a separate empty-content `CaptureIntent.Transcript` reference with zero
bytes and `evidence.Digest(nil)`, plus a positive `MaxTranscriptBytes` no greater
than one MiB. Keep this reservation outside `Template.Binding.Evidence`; capture
appends the final reference there and sets `Binding.Context.ExecutionTranscript`.
Its ID must differ from the candidate and supporting evidence IDs, and its
retention must cover the verification deadline.

The evidence authorizer receives `ActionPut` for both empty reservations before
generation and again for their final references before capture. Resume requires
`ActionRead` on input evidence. Missing history, deleted input evidence or a
changed initial conversation prevents required execution. Capture, evaluator
claims and result commit recheck the saved run against the input artifact.

The private `verification.ExecutionTranscript` records this run's checked
assistant/tool messages, cumulative usage and one host outcome per tool call.
It links to the initial inputs by digest. `completed`, `failed` and `denied`
come from runtime dispatch, with `local` or `external` recording who supplied
the result. External results are assertions by the authorized resumer. They do
not prove that an effect happened exactly once.

Candidate bytes, transcript bytes, completion metadata and the verification job
share one transaction. Capture rejects missing or duplicate results, mismatched
usage, changed inputs and a final message that differs from the candidate.
Deleting either artifact prevents later evaluator claims and result commit.
Resume retains prior outcomes across restart; if rescanning changes any retained
message, the required run stops before further effects or generation.

Pin the model with `WithModelRevision` and every available tool with
`WithToolRevision`. Required preparation rejects missing pins. These are your
host's implementation revisions; they do not attest which model a provider ran.

Supply a positive total token budget and a deadline through `RunOverrides.Budget`.
Preparation reserves the evaluator's maximum tokens and freezes the remainder
as the generation budget. For example, 1,000 total tokens with a 30-token
verification allowance gives generation 970 tokens. Evaluation money limits
remain separate from generation pricing. Provider-reported usage is never
clamped; an overrun prevents evaluation.

Required snapshots and continuations use schema 6. Re-prepare earlier required
snapshots; changing their schema number cannot supply missing evidence.
Schema 2 remains unchanged for ordinary runs.
A worker without the matching required configuration rejects required execution;
a required worker also rejects ordinary prepared snapshots. Contract, revision,
allowance and prepared identity cannot be replaced through run options. The
engine registers the intent before invoking the model.

`RunAgent`, `RunPrepared`, `StreamAgent` and `StreamPrepared` use the same gate.
Streaming emits progress metadata, then the final answer only after guarded
commit. It emits no candidate tokens. Generation steps retain timing and usage
but omit input/output text, and required runs do not save new conversation
history, including after success. Legacy `RunCompleted` fires only after the
required result commits. The execution-termination hook still describes execution
completion independently of verification.

A failed or inconclusive check returns `cortex.ErrRunUnverified`; an uncertain
worker or capture failure returns a static error without private diagnostics.
Neither path releases an answer or a `done` event. The saved run can be execution
`completed` while its verification is pending or failed, so read both fields.
A2A projects pending required verification as working and rejects unverified
completion artifacts.

REST maps `ErrRunUnverified` to HTTP 409 and `ErrVerificationUnavailable` to
HTTP 503. Both retain the standard `error` and numeric `code` fields and add
safe `details` with a stable `code` (`run_unverified` or
`verification_unavailable`), `message` and `retryable: false`. If the engine
returns a run, the details include `run_id`, `state` and `verification_status`.
Dashboard commands return the same details under `CONFLICT` or `UNAVAILABLE`.
SSE `error` events carry those fields directly.

Inspect the saved run before deciding what to do next. An unavailable verifier
can already have a running evaluation or committed work, so a new run may repeat
generation or tool effects. Recover through the saved intent/job identities and
the authorized verification worker. A missing run ID does not prove that no work
was saved. These errors omit candidate text and wrapped diagnostics.

The REST streaming handler sets SSE headers after startup succeeds. A failed
write cancels its provider context; this asks in-flight work to stop but cannot
undo an external effect or guarantee that a provider honors cancellation.

Checked-segment publication remains unsupported: required answers must wait for
whole-result verification. Tool-free snapshots reject unexpected tool calls;
tool-enabled snapshots enforce their frozen allowlist and current tool authority.
History publication, durable completion-hook replay, automatic job scheduling,
lease renewal, repairs and recovery before candidate capture remain open.
After a lost evaluator response, recover the saved intent/job through `VerifyRun`
with its stable identities and lease rules. That operation reconciles the
recorded call without generating again; it does not replay completion hooks.


### Authorize private tool handoffs

For required runs with tools, supply both `WithToolAuthorizer` and
`RequiredVerificationConfig.HandoffAuthorizer`. The latter implements
`AuthorizeToolHandoff(context.Context, cortex.Subject) error`. Check the current
principal's permission to inspect pending calls and supply their outcomes, using
the exact scope and run identity. It is a separate decision from permission to
execute a tool.

Preparation freezes schema 6 for required runs. Resume restores the
verification policy from that prepared payload rather than maintaining a second
policy copy in continuation configuration. Before claiming a suspension, Cortex
checks the saved budget, provenance, capture intent, policy revision, host ports,
current model/tool pins, initial conversation, handoff grant and evidence grants.
It repeats the checks after claim
and rechecks tool dispatch authority before effects. An older worker rejects the
new schema instead of resuming without the verification requirement.

Ordinary stream and dashboard responses omit private pending call IDs and
arguments. Use `Engine.PendingVerificationTools(ctx, runID)` from an authorized
host path to obtain them. That read does not claim the suspension or authorize
executing the tool. Pass the returned call IDs into the existing `Resume` or
`ResumeStream` API; approval checkpoints still use `ResolveCheckpoint`.

Tool arguments and results remain available to the authorized handler and model.
Public tool rows and lifecycle hooks omit their bodies; unknown model-supplied
tool names and private failure details are replaced with fixed metadata. Required
runs still do not publish conversation history. The continuation retains private
messages under the store's existing scope boundary until resume or cleanup.
Direct `Store()` access is a trusted host capability, so authorize it separately.

Result verification does not undo tool effects. Your tool authorizer must govern
writes, messages and other effects before dispatch. Verification controls whether
the final answer can be published. The restart tests prove that completed tool
steps are not replayed by normal continuation; a crash during an external effect
still needs the planned durable effect-receipt protocol.
