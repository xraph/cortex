---
title: Orchestration
description: Run multiple agents together with sequential, parallel, router, hierarchical and debate strategies, a shared blackboard and handoffs.
---

Cortex orchestration coordinates several agents working together. An
orchestration is a stored config (a strategy plus the participant agents and
their settings) that you run by name. During a run, agents share a blackboard
(the roster and prior contributions) and pass work through recorded handoffs.

## Strategies

| Strategy | Behavior |
|----------|----------|
| `sequential` | Agents run in order; each sees the prior outputs and the final answer is the last agent's. |
| `parallel` | All agents run concurrently on the same input; an optional aggregator agent synthesizes one answer. |
| `router` | A static rule map or a router agent picks one agent to handle the input. |
| `hierarchical` | A manager agent delegates subtasks to workers (JSON plan), then synthesizes the result. |
| `debate` | Debater agents argue over N rounds, then a judge agent renders a verdict. |

## Hierarchical plan validation

The manager must return one JSON array assigning every non-manager participant exactly one nonempty task. Unknown or duplicate workers, extra fields, malformed JSON and partial plans fail before workers start. There is no broadcast fallback. Plans are limited to 256 KiB, each task to 64 KiB and the worker roster to 64 agents.

`plan_repair_attempts` accepts zero or one. A repair is an additional manager run with ordinary runner budgets and a retained run ID. It receives validation diagnostics as JSON data. This setting does not create a shared token budget across agents. Worker errors or missing outputs fail the orchestration and prevent synthesis from concealing partial work.

## Awareness and communication

Every participant sees a roster of the others (name and role) and the running
log of contributions via the blackboard snapshot prepended to its input. When one
agent hands off to another, an `AgentHandoff` plugin hook fires (and is recorded
on the run), so audit and metrics extensions observe the collaboration.

## Settings

```json
{
  "max_concurrency": 4,
  "plan_repair_attempts": 0,
  "rounds": 2,
  "manager": "lead",
  "judge": "referee",
  "aggregator": "summarizer",
  "router_agent": "dispatcher",
  "router_rules": { "refund": "billing", "bug": "support" },
  "model": "smart"
}
```

Each strategy reads only the settings it needs; the rest are ignored.

## Create and run over HTTP

These routes exist when you mount the `api` module through `extension.WithRoutes`. The paths use the default `/cortex` base path, and your scope middleware has to run first.

```bash
# Create a debate orchestration
curl -X POST http://localhost:8080/cortex/v1/orchestrations -H 'Content-Type: application/json' -d '{
  "name": "should-we-ship",
  "strategy": "debate",
  "participants": [
    {"agent_name": "optimist", "role": "debater"},
    {"agent_name": "skeptic", "role": "debater"},
    {"agent_name": "referee", "role": "judge"}
  ],
  "settings": {"rounds": 2, "judge": "referee"}
}'

# Run it
curl -X POST http://localhost:8080/cortex/v1/orchestrations/should-we-ship/run \
  -H 'Content-Type: application/json' \
  -d '{"input": "Should we ship the feature this week?"}'
```

The run returns a summary:

```json
{
  "run_id": "orch_01...",
  "status": "completed",
  "strategy": "debate",
  "output": "...the judge's verdict...",
  "duration_ms": 4213
}
```

Run history is available at `GET /cortex/v1/orchestration-runs` (with `limit` and `offset`) and
`GET /cortex/v1/orchestration-runs/:id`.

## In Go

```go
// Persist a config once...
cfg := &orchestration.Config{
    ID:       id.NewOrchestrationConfigID(),
    Name:     "research-team",
    Strategy: orchestration.StrategySequential,
    Participants: []orchestration.Participant{
        {AgentName: "researcher", Role: "worker"},
        {AgentName: "writer", Role: "worker"},
    },
}
if err := eng.CreateOrchestration(ctx, cfg); err != nil {
    return err
}

// ...then run it by name. The scope comes from ctx.
orun, err := eng.RunOrchestration(ctx, "research-team", "Summarize CRDTs")
```

`RunOrchestration` returns an `*orchestration.Run` with the result. `eng.ListOrchestrationRuns` and `eng.GetOrchestrationRun` read the history.
