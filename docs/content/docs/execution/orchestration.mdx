---
title: Orchestration
description: Run multiple agents together with sequential, parallel, router, hierarchical and debate strategies, a shared blackboard and handoffs.
---

Cortex orchestration coordinates several agents working together. An
orchestration is a stored config (a strategy plus the participant agents and
their settings) that you run by name. During a run, agents share a blackboard
(the roster and prior contributions) and pass work through recorded handoffs.

## Strategies

| Strategy | Behavior |
|----------|----------|
| `sequential` | Agents run in order; each sees the prior outputs and the final answer is the last agent's. |
| `parallel` | All agents run concurrently on the same input; an optional aggregator agent synthesizes one answer. |
| `router` | A static rule map or a router agent picks one agent to handle the input. |
| `hierarchical` | A manager agent delegates subtasks to workers (JSON plan), then synthesizes the result. |
| `debate` | Debater agents argue over N rounds, then a judge agent renders a verdict. |

## Hierarchical plan validation

The manager must return one JSON array assigning every non-manager participant exactly one nonempty task. Unknown or duplicate workers, extra fields, malformed JSON and partial plans fail before workers start. There is no broadcast fallback. Plans are limited to 256 KiB, each task to 64 KiB and the worker roster to 64 agents.

`plan_repair_attempts` accepts zero or one. A repair is an additional manager run with ordinary runner budgets and a retained run ID. It receives validation diagnostics as JSON data. This setting does not create a shared token budget across agents. Worker errors or missing outputs fail the orchestration and prevent synthesis from concealing partial work.

## Awareness and communication

Every participant sees a roster of the others (name and role) and the running
log of contributions via the blackboard snapshot prepended to its input. When one
agent hands off to another, an `AgentHandoff` plugin hook fires (and is recorded
on the run), so audit and metrics extensions observe the collaboration.

## Settings

```json
{
  "max_concurrency": 4,
  "plan_repair_attempts": 0,
  "rounds": 2,
  "manager": "lead",
  "judge": "referee",
  "aggregator": "summarizer",
  "router_agent": "dispatcher",
  "router_rules": { "refund": "billing", "bug": "support" },
  "model": "smart"
}
```

Each strategy reads only the settings it needs; the rest are ignored.

## Create and run over HTTP

These routes exist when you mount the `api` module through `extension.WithRoutes`. The paths use the default `/cortex` base path, and your scope middleware has to run first.

```bash
# Create a debate orchestration
curl -X POST http://localhost:8080/cortex/v1/orchestrations -H 'Content-Type: application/json' -d '{
  "name": "should-we-ship",
  "strategy": "debate",
  "participants": [
    {"agent_name": "optimist", "role": "debater"},
    {"agent_name": "skeptic", "role": "debater"},
    {"agent_name": "referee", "role": "judge"}
  ],
  "settings": {"rounds": 2, "judge": "referee"}
}'

# Run it
curl -X POST http://localhost:8080/cortex/v1/orchestrations/should-we-ship/run \
  -H 'Content-Type: application/json' \
  -d '{"input": "Should we ship the feature this week?"}'
```

The run returns a summary:

```json
{
  "run_id": "orch_01...",
  "status": "completed",
  "strategy": "debate",
  "output": "...the judge's verdict...",
  "duration_ms": 4213
}
```

Run history is available at `GET /cortex/v1/orchestration-runs` (with `limit` and `offset`) and
`GET /cortex/v1/orchestration-runs/:id`.

## In Go

```go
// Persist a config once...
cfg := &orchestration.Config{
    ID:       id.NewOrchestrationConfigID(),
    Name:     "research-team",
    Strategy: orchestration.StrategySequential,
    Participants: []orchestration.Participant{
        {AgentName: "researcher", Role: "worker"},
        {AgentName: "writer", Role: "worker"},
    },
}
if err := eng.CreateOrchestration(ctx, cfg); err != nil {
    return err
}

// ...then run it by name. The scope comes from ctx.
orun, err := eng.RunOrchestration(ctx, "research-team", "Summarize CRDTs")
```

`RunOrchestration` returns an `*orchestration.Run` with the result. `eng.ListOrchestrationRuns` and `eng.GetOrchestrationRun` read the history.

## Bounded replanning proposals

Use `planning.ProposeReplan(snapshot, policy)` to choose a response to stalled
work. It returns `continue`, `wait`, `reconcile`, `propose` or `stop`, with a
bounded reason and digests of the exact graph, snapshot and normalized policy.
The helper performs no I/O and never declares a task complete.

Build a schema-version-one `planning.ProgressSnapshot` from the current sealed
plan, retained progress observations and `execution.BudgetStore.GetBudgetSnapshot`.
Every attempt and conflict binds the current plan digest. An older graph's
observations are rejected. Failure fingerprints should group equivalent failures
using host-defined categories, without retaining private error messages. Set
`Advanced` only for new accepted artifacts or retained checks; a model's claim
that it made progress is insufficient.

The default policy allows two replanning attempts. Equivalent failures trigger
a proposal after two attempts; three attempts without progress also trigger one.
Idle or waiting work triggers after five minutes, and thirty seconds of deadline
reserve triggers an earlier proposal. You can configure these thresholds within
the finite bounds exposed by `ReplanPolicy.Normalize`: at most sixteen replans,
256 observations and twenty-four hours for either duration setting.

The account's replan allowance must not exceed the policy's `MaxReplans`.
Outstanding holds count against that allowance. If you raise the policy limit,
the existing immutable account still constrains it. Unknown usage and graph
revisions cannot reset the account. See [shared capacity](/docs/execution/assurance#share-capacity-across-workers)
for reservation and settlement rules.

Unresolved effects take priority over new work, including after a deadline.
Other decisions check conservative shared capacity and absolute deadlines before
requesting another proposal. A paused task's deadline keeps advancing. Contradictory
evidence, repeated failures and stalled progress can request a revised graph,
but they do not authorize retries, bypass approval or cancel running work.

Automatic execution still needs scheduler integration. Under current host
authorization, reserve one replan unit and the estimated proposal resources
before invoking a model. Retain the charge when a proposal fails or is rejected;
refund only usage that trusted evidence establishes was unused. A reservation
alone does not grant fresh invocation permission. Apply any resulting graph
through `planning.ApplyRevision` and the existing expected-revision store commit,
which preserve acceptance criteria and reject expanded authority or budgets.
The helper does not wire these execution steps into `RunOrchestration`.

## Schedule durable task admissions

Use `coordination.NewScheduler` when your host supplies the current plan state,
worker resolution, guarded claim admission and a claimed-task worker. Each
`Tick(ctx, planID)` attempts at most one ready task, in plan definition order.
Your context must carry the exact scope. The scheduler reloads the plan and
current verification state after local capacity becomes available, then resolves
the worker and asks `TaskClaimAdmitter` to reserve ownership and shared capacity.

The local queue admits scopes in round-robin order and keeps FIFO order within
each scope. Defaults are four concurrent ticks, one per exact scope and 64 queued
ticks. `MaxConcurrent` can be at most 256, `MaxPerScope` cannot exceed it, and
`MaxQueued` can be at most 4096. These are process limits. Durable admission still
controls shared capacity across scheduler instances.

`TickTimeout` defaults to one minute and covers queueing, preparation and worker
execution together. It cannot exceed thirty minutes. The worker context is also
bounded by the plan and task deadlines. Without `Renewal`, the original claim
expiry also bounds it. With renewal, a watchdog cancels at the last confirmed
expiry. Cancellation
propagates from the caller, so attach the parent run's cancellation to that context.
You must still fence the parent's persisted state and current grants at dispatch
and at each provider or tool call.

A worker is called only after a confirmed fresh, validated claim receipt. An
ambiguous write or historical receipt returns `ErrSchedulerReconciliationRequired`
without invoking it. Preserve and reconcile the durable request and receipt before
trying to dispatch; a scheduler restart does not grant permission to repeat work.
The source must reconstruct task states from retained records and current authorized
bindings. Missing states mean pending, but the claim transaction rechecks prerequisites
and ownership even when the source snapshot is stale.

Your `ClaimedTaskWorker` must use guarded dispatch and the prepared task runtime.
Return when a task suspends or enters asynchronous verification so its local worker
slot becomes available. This does not settle its shared allocation, extend its
deadline or mark it successful. Only verified task acceptance establishes success.
A nil `Tick` result may also mean that no task was ready.

You can use `eng.NewTaskWorker(engine.TaskWorkerConfig{Resolver: resolver,
Dispatch: dispatchAdmitter})` as the claimed-task worker. Configure the engine's
`TaskRunAdmitter` and `TaskCallGuard` first. Your resolver supplies an immutable
prepared agent, private input, accepted assignment, current parent revision and
stable reserved child identity. It resolves definitions only; provider and tool
calls belong to the engine runtime.

The adapter checks that dispatch names the exact admitted claim, then requires a
fresh guarded dispatch receipt. It calls `PrepareTaskRun` and `RunPreparedTask`,
so scanning, private input capture, guarded child creation, call journaling and
verification follow the existing runtime path. An old `Fresh` flag cannot replay
dispatch. If preparation or child creation fails after dispatch was recorded,
reconcile the retained identities before continuing. The adapter does not accept
the task output or settle shared usage when the run verifies successfully.

Call `Shutdown(ctx)` before closing the stores or worker services. Shutdown rejects
new ticks, cancels queued and owned work, then waits for callbacks to return. If your
shutdown context expires, the scheduler stays stopped and you can call `Shutdown`
again to wait for drainage. A callback that ignores cancellation keeps its slot
until it returns. The scheduler never releases durable ownership or refunds an
uncertain allocation just to finish shutdown.

The scheduler does not install itself into `RunOrchestration` or the sweeper.
Concrete host adapters, recovery settlement and installed
worker crash/restart qualification remain separate integrations.

### Renew dispatched ownership

Use `coordination.NewTaskClaimRenewer` with a `TaskRenewalStore`, current grant
fence and authorizer when you need to extend ownership of a task-bound child.
`TaskRenewalRequest` binds the exact claim, parent and child revisions, current
assignment, complete prerequisite chain, worker actor and reason. Keep the request
for recovery if the call fails.

`RenewTaskExecution` locks the execution records and checks the current plan,
assignment, capture provenance and shared reservation before extending the claim.
The renewal cannot exceed the parent, child, assignment or verification deadline.
Cancelled, failed or incomplete children are rejected. Paused children and completed
runs awaiting acceptance can retain ownership under current host authorization;
this does not grant permission to resume, repeat a call or accept an output.

The renewed claim and metadata event intent commit together. Only a confirmed
first write returns `Fresh: true`. An identical retry returns the original receipt
with `Fresh: false`, including after a lost acknowledgement. That historical
receipt may already be expired. Preserve the last acknowledged local expiry and
stop work when renewal is uncertain; reconcile before continuing. Renewal does
not replenish shared capacity or reset any deadline.

To renew while a scheduler worker runs, set `SchedulerConfig.Renewal` to a
`TaskRenewalConfig` with your source, guarded renewer, duration and interval.
The interval must be at least one millisecond and no more than half the duration;
the duration cannot exceed thirty minutes. Your `TaskRenewalSource` reloads the
current execution revisions and prerequisite chain for the supplied claim. It can
shorten the requested duration when the child has a tighter deadline.

The worker must implement `RenewingClaimedTaskWorker`. The engine adapter does.
It calls the supplied activation function only after confirming fresh child
creation, so renewal cannot change the revision still needed by dispatch or
child admission. Until activation, the watchdog enforces the original expiry.
Each confirmed renewal must be an exact, live successor received before the last
acknowledged expiry. Invalid or historical receipts, lost acknowledgements,
revocation and clock rollback cancel the worker and require reconciliation.

The loop cancels pending renewal operations and waits for them before releasing
the local slot. Both host ports must honor cancellation. Shutdown and caller
cancellation stop renewal too. The overall tick, plan and task deadlines still
apply; renewal never extends those ceilings.

Individual provider and tool calls retain their own authorization leases. Task
renewal does not extend those leases or resume a suspended run. Host grant services,
event delivery and installed worker recovery still need qualification.
