---
title: Orchestration
description: Run multiple agents together with sequential, parallel, router, hierarchical and debate strategies, a shared blackboard and handoffs.
---

Cortex orchestration coordinates several agents working together. An
orchestration is a stored config (a strategy plus the participant agents and
their settings) that you run by name. During a run, agents share a blackboard
(the roster and prior contributions) and pass work through recorded handoffs.

## Strategies

| Strategy | Behavior |
|----------|----------|
| `sequential` | Agents run in order; each sees the prior outputs and the final answer is the last agent's. |
| `parallel` | All agents run concurrently on the same input; an optional aggregator agent synthesizes one answer. |
| `router` | A static rule map or a router agent picks one agent to handle the input. |
| `hierarchical` | A manager agent delegates subtasks to workers (JSON plan), then synthesizes the result. |
| `debate` | Debater agents argue over N rounds, then a judge agent renders a verdict. |

## Hierarchical plan validation

The manager must return one JSON array assigning every non-manager participant exactly one nonempty task. Unknown or duplicate workers, extra fields, malformed JSON and partial plans fail before workers start. There is no broadcast fallback. Plans are limited to 256 KiB, each task to 64 KiB and the worker roster to 64 agents.

`plan_repair_attempts` accepts zero or one. A repair is an additional manager run with ordinary runner budgets and a retained run ID. It receives validation diagnostics as JSON data. This setting does not create a shared token budget across agents. Worker errors or missing outputs fail the orchestration and prevent synthesis from concealing partial work.

## Awareness and communication

Every participant sees a roster of the others (name and role) and the running
log of contributions via the blackboard snapshot prepended to its input. When one
agent hands off to another, an `AgentHandoff` plugin hook fires (and is recorded
on the run), so audit and metrics extensions observe the collaboration.

## Settings

```json
{
  "max_concurrency": 4,
  "plan_repair_attempts": 0,
  "rounds": 2,
  "manager": "lead",
  "judge": "referee",
  "aggregator": "summarizer",
  "router_agent": "dispatcher",
  "router_rules": { "refund": "billing", "bug": "support" },
  "model": "smart"
}
```

Each strategy reads only the settings it needs; the rest are ignored.

## Create and run over HTTP

These routes exist when you mount the `api` module through `extension.WithRoutes`. The paths use the default `/cortex` base path, and your scope middleware has to run first.

```bash
# Create a debate orchestration
curl -X POST http://localhost:8080/cortex/v1/orchestrations -H 'Content-Type: application/json' -d '{
  "name": "should-we-ship",
  "strategy": "debate",
  "participants": [
    {"agent_name": "optimist", "role": "debater"},
    {"agent_name": "skeptic", "role": "debater"},
    {"agent_name": "referee", "role": "judge"}
  ],
  "settings": {"rounds": 2, "judge": "referee"}
}'

# Run it
curl -X POST http://localhost:8080/cortex/v1/orchestrations/should-we-ship/run \
  -H 'Content-Type: application/json' \
  -d '{"input": "Should we ship the feature this week?"}'
```

The run returns a summary:

```json
{
  "run_id": "orch_01...",
  "status": "completed",
  "strategy": "debate",
  "output": "...the judge's verdict...",
  "duration_ms": 4213
}
```

Run history is available at `GET /cortex/v1/orchestration-runs` (with `limit` and `offset`) and
`GET /cortex/v1/orchestration-runs/:id`.

## In Go

```go
// Persist a config once...
cfg := &orchestration.Config{
    ID:       id.NewOrchestrationConfigID(),
    Name:     "research-team",
    Strategy: orchestration.StrategySequential,
    Participants: []orchestration.Participant{
        {AgentName: "researcher", Role: "worker"},
        {AgentName: "writer", Role: "worker"},
    },
}
if err := eng.CreateOrchestration(ctx, cfg); err != nil {
    return err
}

// ...then run it by name. The scope comes from ctx.
orun, err := eng.RunOrchestration(ctx, "research-team", "Summarize CRDTs")
```

`RunOrchestration` returns an `*orchestration.Run` with the result. `eng.ListOrchestrationRuns` and `eng.GetOrchestrationRun` read the history.

## Bounded replanning proposals

Use `planning.ProposeReplan(snapshot, policy)` to choose a response to stalled
work. It returns `continue`, `wait`, `reconcile`, `propose` or `stop`, with a
bounded reason and digests of the exact graph, snapshot and normalized policy.
The helper performs no I/O and never declares a task complete.

Build a schema-version-one `planning.ProgressSnapshot` from the current sealed
plan, retained progress observations and `execution.BudgetStore.GetBudgetSnapshot`.
Every attempt and conflict binds the current plan digest. An older graph's
observations are rejected. Failure fingerprints should group equivalent failures
using host-defined categories, without retaining private error messages. Set
`Advanced` only for new accepted artifacts or retained checks; a model's claim
that it made progress is insufficient.

The default policy allows two replanning attempts. Equivalent failures trigger
a proposal after two attempts; three attempts without progress also trigger one.
Idle or waiting work triggers after five minutes, and thirty seconds of deadline
reserve triggers an earlier proposal. You can configure these thresholds within
the finite bounds exposed by `ReplanPolicy.Normalize`: at most sixteen replans,
256 observations and twenty-four hours for either duration setting.

The account's replan allowance must not exceed the policy's `MaxReplans`.
Outstanding holds count against that allowance. If you raise the policy limit,
the existing immutable account still constrains it. Unknown usage and graph
revisions cannot reset the account. See [shared capacity](/docs/execution/assurance#share-capacity-across-workers)
for reservation and settlement rules.

Unresolved effects take priority over new work, including after a deadline.
Other decisions check conservative shared capacity and absolute deadlines before
requesting another proposal. A paused task's deadline keeps advancing. Contradictory
evidence, repeated failures and stalled progress can request a revised graph,
but they do not authorize retries, bypass approval or cancel running work.

Automatic execution still needs scheduler integration. Under current host
authorization, reserve one replan unit and the estimated proposal resources
before invoking a model. Retain the charge when a proposal fails or is rejected;
refund only usage that trusted evidence establishes was unused. A reservation
alone does not grant fresh invocation permission. Apply any resulting graph
through `planning.ApplyRevision` and the existing expected-revision store commit,
which preserve acceptance criteria and reject expanded authority or budgets.
The helper does not wire these execution steps into `RunOrchestration`.

## Retain partial usage charges

When you settle a reservation with incomplete usage, set `Settlement.Minimum`
to the authenticated observed lower bounds. Each unknown dimension retains the
larger of its allocation and that minimum. For example, a 100-token allocation
with 250 observed tokens and a missing receipt still charges at least 250 tokens.
Known dimensions use their exact reported amount, which cannot fall below the
minimum. Both known usage and minimums require an attributed receipt.

If an observed sum exceeds `int64`, set its `Settlement.Overflow` bit and retain
`math.MaxInt64` as its minimum. The account preserves that overflow and refuses
new admission, including when a single leaf overflowed. Branch closure cannot
report its own minimum or overflow; child charges carry them to the root.
Token-only policies do not accept monetary charges.

These fields preserve accounting evidence. They do not authenticate a provider
bill or prove that no further spending can occur. Keep the reservation open
until your host can authorize final settlement against current evidence.

## Schedule durable task admissions

Use `coordination.NewScheduler` when your host supplies the current plan state,
worker resolution, guarded claim admission and a claimed-task worker. Each
`Tick(ctx, planID)` attempts at most one ready task, in plan definition order.
Your context must carry the exact scope. The scheduler reloads the plan and
current verification state after local capacity becomes available, then resolves
the worker and asks `TaskClaimAdmitter` to reserve ownership and shared capacity.

The local queue admits scopes in round-robin order and keeps FIFO order within
each scope. Defaults are four concurrent ticks, one per exact scope and 64 queued
ticks. `MaxConcurrent` can be at most 256, `MaxPerScope` cannot exceed it, and
`MaxQueued` can be at most 4096. These are process limits. Durable admission still
controls shared capacity across scheduler instances.

`TickTimeout` defaults to one minute and covers queueing, preparation and worker
execution together. It cannot exceed thirty minutes. The worker context is also
bounded by the plan and task deadlines. Without `Renewal`, the original claim
expiry also bounds it. With renewal, a watchdog cancels at the last confirmed
expiry. Cancellation
propagates from the caller, so attach the parent run's cancellation to that context.
You must still fence the parent's persisted state and current grants at dispatch
and at each provider or tool call.

A worker is called only after a confirmed fresh, validated claim receipt. An
ambiguous write or historical receipt returns `ErrSchedulerReconciliationRequired`
without invoking it. Preserve and reconcile the durable request and receipt before
trying to dispatch; a scheduler restart does not grant permission to repeat work.
The source must reconstruct task states from retained records and current authorized
bindings. Missing states mean pending, but the claim transaction rechecks prerequisites
and ownership even when the source snapshot is stale.

Your `ClaimedTaskWorker` must use guarded dispatch and the prepared task runtime.
Return when a task suspends or enters asynchronous verification so its local worker
slot becomes available. This does not settle its shared allocation, extend its
deadline or mark it successful. Only verified task acceptance establishes success.
A nil `Tick` result may also mean that no task was ready.

You can use `eng.NewTaskWorker(engine.TaskWorkerConfig{Resolver: resolver,
Dispatch: dispatchAdmitter})` as the claimed-task worker. Configure the engine's
`TaskRunAdmitter` and `TaskCallGuard` first. Your resolver supplies an immutable
prepared agent, private input, accepted assignment, current parent revision and
stable reserved child identity. It resolves definitions only; provider and tool
calls belong to the engine runtime.

The adapter checks that dispatch names the exact admitted claim, then requires a
fresh guarded dispatch receipt. It calls `PrepareTaskRun` and `RunPreparedTask`,
so scanning, private input capture, guarded child creation, call journaling and
verification follow the existing runtime path. An old `Fresh` flag cannot replay
dispatch. If preparation or child creation fails after dispatch was recorded,
reconcile the retained identities before continuing. The adapter does not accept
the task output or settle shared usage when the run verifies successfully.

Call `Shutdown(ctx)` before closing the stores or worker services. Shutdown rejects
new ticks, cancels queued and owned work, then waits for callbacks to return. If your
shutdown context expires, the scheduler stays stopped and you can call `Shutdown`
again to wait for drainage. A callback that ignores cancellation keeps its slot
until it returns. The scheduler never releases durable ownership or refunds an
uncertain allocation just to finish shutdown.

Use the optional engine lifecycle integration below to poll scoped plans. Task
execution still uses the prepared runtime; `RunOrchestration` and the suspension
sweeper do not infer new plans. Concrete host adapters, expired-claim recovery,
settlement and installed worker crash/restart qualification remain separate work.

### Renew dispatched ownership

Use `coordination.NewTaskClaimRenewer` with a `TaskRenewalStore`, current grant
fence and authorizer when you need to extend ownership of a task-bound child.
`TaskRenewalRequest` binds the exact claim, parent and child revisions, current
assignment, complete prerequisite chain, worker actor and reason. Keep the request
for recovery if the call fails.

`RenewTaskExecution` locks the execution records and checks the current plan,
assignment, capture provenance and shared reservation before extending the claim.
The renewal cannot exceed the parent, child, assignment or verification deadline.
Cancelled, failed or incomplete children are rejected. Paused children and completed
runs awaiting acceptance can retain ownership under current host authorization;
this does not grant permission to resume, repeat a call or accept an output.

The renewed claim and metadata event intent commit together. Only a confirmed
first write returns `Fresh: true`. An identical retry returns the original receipt
with `Fresh: false`, including after a lost acknowledgement. That historical
receipt may already be expired. Preserve the last acknowledged local expiry and
stop work when renewal is uncertain; reconcile before continuing. Renewal does
not replenish shared capacity or reset any deadline.

To renew while a scheduler worker runs, set `SchedulerConfig.Renewal` to a
`TaskRenewalConfig` with your source, guarded renewer, duration and interval.
The interval must be at least one millisecond and no more than half the duration;
the duration cannot exceed thirty minutes. Your `TaskRenewalSource` reloads the
current execution revisions and prerequisite chain for the supplied claim. It can
shorten the requested duration when the child has a tighter deadline.

The worker must implement `RenewingClaimedTaskWorker`. The engine adapter does.
It calls the supplied activation function only after confirming fresh child
creation, so renewal cannot change the revision still needed by dispatch or
child admission. Until activation, the watchdog enforces the original expiry.
Each confirmed renewal must be an exact, live successor received before the last
acknowledged expiry. Invalid or historical receipts, lost acknowledgements,
revocation and clock rollback cancel the worker and require reconciliation.

The loop cancels pending renewal operations and waits for them before releasing
the local slot. Both host ports must honor cancellation. Shutdown and caller
cancellation stop renewal too. The overall tick, plan and task deadlines still
apply; renewal never extends those ceilings.

Individual provider and tool calls retain their own authorization leases. Task
renewal does not extend those leases or resume a suspended run. Host grant services,
event delivery and installed worker recovery still need qualification.


### Run scheduling with the engine lifecycle

Use `engine.WithTaskScheduling` when the engine should own plan discovery and
worker shutdown. Supply `TaskSchedulingConfig.Worker` with the same work resolver
and guarded dispatch used by `NewTaskWorker`. Its `Service` field is a
`coordination.TaskServiceConfig`; leave `Service.Scheduler.Worker` unset because
the engine supplies its prepared-runtime adapter. The engine validates the
configured task-run admitter and call guard after all options have been applied.
You can pass the option through Forge's `extension.WithEngineOption`.

Your `TaskPlanSource.ListScheduledPlans` returns scoped plan identities in pages.
It authorizes discovery under the host service identity, and each resulting tick
rechecks admission. A scope or saved plan ID grants no execution permission. The
source must honor cancellation and eventually return an empty `Next` cursor so
later passes revisit earlier identities. Discovery never invokes an agent or tool.

The service polls one page per interval, starting immediately on `Engine.Start`.
Defaults are a one-second interval, a five-second discovery timeout and 64
in-flight ticks. A page holds at most 256 identities and never exceeds the
remaining local capacity. Pages are detached and checked for scope, plan ID,
duplicate entries, size and cursor validity before any tick starts. Scope bytes
must be valid UTF-8 and fit the page budget before JSON encoding. The same
scope/plan pair cannot have two active ticks in one service instance. Discovery
also limits in-flight ticks per scope to `MaxPerScope`, so queued plans from one
busy scope cannot consume every discovery slot. Skipped identities are revisited
on later source passes. The page starting position rotates across complete source
passes so a fast first plan does not always take its scope slot. Durable claims
still arbitrate between processes.

`Start` preserves context values for your host service identity and gives polling
its own cancellation handle. Cancelling the startup request does not stop the
engine. `Stop(ctx)` cancels discovery and all queued or executing ticks, then joins
their callbacks before emitting the shutdown hook. If the deadline expires, it
returns an error and remains in the stopping state. Keep the stores available and
call `Stop` again. A new start is rejected until the previous work has drained.
The Forge extension also retains its started state after a timed-out stop.

`TaskSchedulingStatus` reports whether scheduling is configured, lifecycle state,
in-flight tick count and failure count. Failures are reported through the engine's
existing error-type logger. Discovery errors and malformed pages are retried on
later polls; an uncertain task invocation still requires durable reconciliation.
Restarting the service resets discovery to the first page but preserves all claims,
call journals, output acceptance requirements and shared reservations.

### Close a call journal for recovery

Use `Engine.NewRunCallSealer(fence, authorizer)` to close the engine's journal
under your current host authority. You can also construct
`execution.NewRunCallSealer(store, fence, authorizer)` directly. Pass a
`RunCallSealRequest` with the exact scope, run ID, authenticated actor and reason
to `Seal`. The guarded operation has a thirty-second deadline, which your host
ports and storage must honor.

The seal and call admission serialize on the same durable database row. Once the
seal is acknowledged, `BeginRunCall` and built-in effect admission reject every
slot or operation for that run with
`ErrRunCallsSealed`, including historical attempts. An empty journal can be
sealed before a delayed worker reaches its first call. The prepared task runtime
then stops before invoking the provider. There is no reopen operation.

This gives bounded recovery scans stable membership. It does not prove that
admitted calls have finished. Late local returns and provider receipts remain
writable, and their consistency must be rechecked before adoption or settlement.
Use call-lease controls to stop already admitted work; a journal seal cannot cancel
an external operation. Claim, run and shared-budget state remain unchanged.

The host implements `RunCallSealFence.WithRunCallSeal` and
`RunCallSealAuthorizer.AuthorizeRunCallSeal`. Hold current exact-run authority
through the synchronous callback and authenticate the actor on every attempt,
including retries. Identical requests return the retained seal. A changed actor,
reason or other binding conflicts. Errors can follow a committed write, so repeat
the same authorized request instead of assuming closure failed.

The built-in stores support journals created before sealing was introduced. All
writers must run the sealing protocol before you rely on it; an older writer can
bypass the barrier. Admission now requires a transaction-capable store, including
a replica set or supported sharded deployment for MongoDB. Missing transaction
support fails closed. Keep seals for at least as long as their call records and
possible delayed workers.

### Bind a tool effect to its guarded call

`EffectExecutor.Execute` retains the runtime's `RunCallRequest` inside the
`EffectRequest`. Your adapter's receipt must hash that complete request. Keep it
for recovery, including the original call, operation key and attempt ID.
`NewEffectToolHandler` passes this metadata through automatically.

For guarded tools, your store must implement `BoundEffectStore`. Fresh admission
checks the exact retained tool call, its deadline and its unfinished local return.
Admission, local completion and run sealing serialize on the same database guard.
The executor also bounds dispatch by both the effect and call deadlines. A
hand-built context carries correlation only; your current authorization and the
adapter's external write checks still control permission.

Use `Reconcile` with the retained bound request after worker replacement. It can
record terminal proof after sealing without re-executing the tool. Calling
`Execute` with a bound request requires matching runtime metadata, and sealed
runs reject admission even for an existing operation. A legacy unbound effect
cannot be attached to a call later, so a missing binding is unresolved recovery
information, not proof that a tool had no effects.

All built-in effect admission requires transaction support, including ordinary
operations without a task call. Upgrade every writer before relying on this
barrier, and retain both journals while external outcomes remain possible.

### Read one consistent recovery snapshot

Use `execution.RunRecoverySnapshotStore.SnapshotRunRecovery(ctx, seal)` when you
need all retained call and effect evidence for one sealed run. The built-in stores
read the journals under the same transaction guard used by admission, local
completions and terminal receipt writes. Pass the exact retained seal and scope.
An absent or changed seal fails.

The snapshot includes local returns, independent provider receipts, bound effects
and legacy effects with no call binding. Its digest changes when late evidence
arrives. Missing receipts stay missing, and contradictory observations remain
available for your recovery policy to reject. `Validate` checks shape, membership
and integrity; you still need authenticated proof, worker quiescence and current
authority before adopting a result.

Reads have a thirty-second deadline, a combined limit of 4,096 call/effect entries
and a 16 MiB encoding limit. Oversized journals fail without returning partial
evidence. Errors and ambiguous transaction acknowledgments also return no
snapshot. Authorize discovery in your host before calling this storage API.

Upgrade every writer before relying on this guarantee. Provider and effect
receipt writes now require transaction support, including a replica set or
supported sharded deployment for MongoDB. Late receipts remain writable after
sealing, so a later adoption transaction must recheck the snapshot digest while
holding the journal guard. This API does not change task ownership or settle
reserved capacity.

### Recover effects from a sealed run

Set `EffectExecutorConfig.AuthorizeScan` to authorize exact-run discovery under
your recovery service identity. Then call
`RecoverSealedPage(ctx, EffectRecoveryPageRequest{Seal: seal, Limit: 64})`.
The executor's store must provide `BoundEffectStore`, `EffectDiscoveryStore` and
`RunCallSealStore`. All deployed effect writers must honor the seal.

Follow `NextAfter` until it is empty, then start a fresh pass to revisit uncertain
operations. Each page rechecks current scan authority and the exact retained seal
before discovery and after reconciliation. It uses `RecoverPage` for validation,
current per-operation authorization and the existing read-only adapter path.
The thirty-second deadline includes queueing, authorization, storage and probes;
your callbacks must honor cancellation. Concurrent scans and operations have
separate limits, both set by `MaxConcurrent`.

An error returns no cursor, even if earlier receipts were committed. Retrying
that page reads the receipts already retained. Uncertain outcomes remain visible
and allow traversal to continue; an unavailable or denied operation fails the
page. Legacy unbound operations are included too. A terminal receipt still does
not establish a missing task-call binding, task success or usage settlement.

### Reconcile an interrupted provider call

Use `execution.NewProviderReconciler` with your `ProviderRecoveryConfig` and call
`Reconcile(ctx, originalRequest)` for a journaled complete or stream invocation.
Supply the engine's durable store as `Store`. SQLite, PostgreSQL and MongoDB
implement `ProviderCallReceiptStore`. For a sealed run, use
`ReconcilePage(ctx, ProviderRecoveryPageRequest{Seal: seal, Limit: 64})` to discover
and reconcile one bounded journal page. Keep this host-owned loop separate from
claim expiry.

You must supply every host boundary:

- `Adapter.ReconcileProviderCall` queries authoritative state for the original
  operation. It must never generate, resend or execute it. A partial stream,
  transient lookup miss or unavailable proof remains uncertain.
- `Authorize` checks the caller before lookup and again before persistence.
- `Authenticate` verifies the receipt against retained dispatch and routing
  evidence, including the original provider, account, operation, adapter revision,
  result encoding and any known usage. Current agent configuration cannot prove
  where an earlier call went. If that binding is unavailable, return an error.
- `Fence.WithProviderCallFence` holds your current authority and routing revision
  guards through its synchronous commit callback. A no-op guard does not provide
  this guarantee. The callback must run exactly once before the guard returns.

Receipts retain a proof reference and digest, without credentials or result bytes.
Their request digest binds the entire frozen `RunCallRequest`. A succeeded receipt
uses the original call's result digest encoding. Failed and not-accepted receipts
have no result digest. Not-accepted proof must establish that delayed delivery
cannot later cause acceptance; a lookup returning no result is insufficient.

Only explicitly known tokens and USD micros count as authenticated usage. Unknown
usage stays unknown, including after proven non-acceptance. Recovery does not
settle budgets, release reservations, accept output or authorize another call.
Those operations need their own guarded checks.

Stored proof is immutable. Identical writes replay safely and conflicting proofs
return an error. Recovery reauthenticates stored proof without querying the provider
again, including after a lost storage acknowledgment. Local return observations
remain separate: a late disagreement preserves both records and makes recovery
fail. Compare the latest journal again before any later adoption.

Defaults are four concurrent operations and a thirty-second timeout, including
slot wait. `MaxConcurrent` accepts 1 to 4096; `Timeout` accepts one millisecond to
thirty seconds. Your adapter, store and guards must honor cancellation. Cortex
keeps a slot until the callback returns and does not detach timed-out work.

### Scan a sealed run

Set `AuthorizeScan` to check current read and recovery permission for the exact
sealed run. Page scanning requires this callback and a store implementing
`RunCallSealStore`; single-call reconciliation does not. The scanner checks your
retained seal and authorization before reading a page and again before returning
its counts. Each provider call also passes through the existing per-call guards.

Start with `After` empty. Pass the returned `NextAfter` into the next request until
it is empty, then begin a new pass when you need to revisit unresolved calls.
`Limit` accepts 1 to 256. The scanner validates the entire page's scope, run,
record bindings and cursor order before querying any provider. `Timeout` bounds
the whole page, including queue wait. `MaxConcurrent` limits active pages and
provider operations independently, so a queued page cannot consume the slot its
own provider lookup needs.

The counts have different meanings. `Terminal` includes authenticated provider
success, failure and proven non-acceptance. `Unresolved` needs another lookup or
external evidence. `ToolCalls` needs separate effect reconciliation. An empty
cursor means you reached the end of the journal, even if some calls remain
unresolved. These counts do not settle usage or accept the task.

An error returns no cursor. Earlier proof writes may still have committed, so
retry the same page. Saved receipts are reauthenticated without another provider
query. A late local return that contradicts provider proof fails the scan while
preserving both records. Recheck those records before adoption or settlement;
the page is an observation, not an atomic recovery decision.

### Run provider recovery with the engine

Pass `engine.WithProviderRecovery(coordination.ProviderRecoveryServiceConfig)`
before `Start`. Set `Recovery` to your provider recovery configuration and supply
an authorized `TaskPlanSource` as `Discovery`. The recovery store must also expose
`ListTaskClaims` and `RunCallSealStore`. Built-in stores provide these capabilities.
You can use `coordination.NewProviderRecoveryService` directly when you own the
lifecycle outside the engine.

Discovery must authorize plan and claim reads under your service identity and
include plans with outstanding claims after cancellation or completion. Each
pass validates a full claim page, then scans sealed runs in `ClaimRecovering`.
Active claims are left alone. Unsealed runs are revisited on a later pass; use the
guarded sealer separately when your authority permits closing admission.

Defaults are four concurrent plan passes, one per exact scope, 64 claims or calls
per page and a one-second interval between pages. `PageTimeout` defaults to five
seconds for claim and seal reads. `Recovery.Timeout` bounds each provider page.
A plan keeps its slot through all pages. A run-specific error does not block
later claims: the pass continues and reports its first error when it ends, without
retaining an unbounded list of errors. Cancellation or an invalid claim page stops
the pass immediately.

`ProviderRecoveryStatus` reports local running, stopping, active and failure
counters. The engine cancels scheduling, claim expiry, provider and effect recovery before
waiting for any of them to drain. A timed-out `Stop` leaves work owned and blocks
restart until it finishes. Forge preserves its started state on that path too.
Restart begins discovery again and reauthenticates retained proof. The service
never executes an agent or tool, accepts a task, releases ownership or settles a
shared reservation.

The subprocess tests kill a real fixture worker before a provider reply or after
local completion, reopen SQLite, expire ownership with an injected clock, seal
the journal and start lifecycle recovery. A second engine repeats recovery after
another reopen. They check that recovering ownership, run, call records and budget
state remain unchanged while authenticated fixture proof is retained.
This qualifies the persistence path with fixture authority. Installed provider
adapters and governed continuation still need separate qualification.

### Run effect recovery with the engine

Pass `engine.WithEffectRecovery(coordination.EffectRecoveryServiceConfig)` before
`Start`, or use `coordination.NewEffectRecoveryService` when you own the lifecycle.
For Forge, pass the engine option through `extension.WithEngineOption`.
`Recovery` contains your `EffectExecutorConfig`; both `AuthorizeScan` and the
per-operation `Authorize` callback are required. The store also needs
`ListTaskClaims`, `RunCallSealStore`, `BoundEffectStore` and `EffectDiscoveryStore`.

Supply authorized plan discovery that includes outstanding claims even when a
plan is cancelled or completed. The service traverses recovering claims only,
leaves unsealed runs for a later pass and uses `RecoverSealedPage` for each effect
page. Its claim validation, paging and fairness implementation is shared with
provider recovery. A failed run does not starve later claims.

Defaults match provider recovery: four plans in flight, one per exact scope,
64 entries per page, five-second claim/seal reads and one second between pages.
Effect pages use `execution.MaxEffectDuration`; `Recovery.MaxConcurrent` must be
set and bounds scan and probe concurrency. Registration slices are copied when
you construct the service so later caller edits cannot change a restart.

`EffectRecoveryStatus` reports local lifecycle counters. `Stop` cancels every
engine task service before waiting for any one service, and a drain timeout keeps
work owned until its callbacks return. Engine and Forge lifecycle tests cover
that path. The crash fixture kills a worker after its adapter fsyncs an external
write but before it returns, then recovers the exact bound request through a new
engine and SQLite connection. A second recovery pass reads the retained receipt
without another mutation. Claims, local call returns, task results and shared
reservations stay unchanged. Installed adapters and the guarded claim adoption described below still
need separate qualification.

### Adopt a verified result after lease expiry

Use `coordination.NewTaskRecoveryAdopter(store, fence, authorizer)` with a built-in
store and explicit `TaskRecoveryFence` and `TaskRecoveryAuthorizer` ports. Call
`Adopt` with a `TaskAcceptanceRequest` whose `Recovery` field identifies your
quiescence proof. The claim must already be recovering, and the original child
run must have a committed verifier result and submitted assignment. Ordinary
`TaskAcceptor.Accept` rejects recovery requests.

Your proof binds the exact recovering claim digest, retained run seal and complete
`RunRecoverySnapshot` digest. Include an issuer, revision, retained proof reference
and digest, observation time and adoption expiry. `Freeze` checks this metadata;
your authorizer authenticates its contents against the original dispatch identity,
provider/account routing and effect receipts. It must establish permanent shutdown
of the original worker incarnation and all its tools, including delayed delivery.
A seal, expired lease or empty journal cannot establish that shutdown.

Hold current grants, source revisions and the quiescence guarantee through the
fence's synchronous callback. Authenticate the actor and the complete prerequisite
chain. The guarded operation has a thirty-second deadline, including host callbacks.
Retrieve external proof before entering storage; no network call should run inside
the database transaction. All journal writers must use the guarded protocol.

Storage locks the current plan, child run and journal, checks the snapshot again,
and validates the retained assignment, result and prerequisite evidence. Every
model call needs terminal provider proof consistent with any local return. Every
effect needs a terminal receipt and its original guarded call binding. Legacy
unbound effects require separate adjudication. A changed snapshot, unresolved
operation, stale claim or expired proof rejects adoption without completing ownership.

The transaction writes the completed claim, acceptance receipt and metadata outbox
intent together. `Claim.RecoveryDigest` retains the proof digest; the original
lease expiry, worker identity, fence and run ID stay intact. Adoption does not
invoke work, fabricate local returns or settle shared reservations.

Retry an uncertain commit with the identical request ID and contents. You still
need current host access, but an acknowledged historical receipt remains readable
after the proof's adoption window expires. That window limits when adoption may
commit; it does not limit the promised worker shutdown. When you consume the
accepted output as a dependency, storage rechecks its journal digest and current
verifier evidence. Late contradictory or changed evidence prevents that use.

Real SQLite, PostgreSQL and MongoDB tests exercise these transactions and denial
paths with fixture proofs. Concrete host authenticators, installed recovery flows
and process-crash qualification of adoption remain integration work.

### Run adoption with the engine lifecycle

Pass `engine.WithTaskAdoption(coordination.TaskAdoptionServiceConfig{...})` before
`Start`, or use `coordination.NewTaskAdoptionService` directly when you own the
lifecycle. You supply the durable store, authorized plan discovery, snapshot
read authorization, a `TaskRecoveryResolver`, and the same recovery fence and
authorizer used by `TaskRecoveryAdopter`. Forge hosts can pass the option through
`extension.WithEngineOption`.

Discovery must authorize plan, claim and seal reads under the service identity.
The service visits sealed recovering claims and calls `AuthorizeScan` before
reading their full snapshots. The resolver receives detached original claim and
snapshot metadata. Return a fully bound acceptance request with retained proof,
or `nil, nil` while proof or verified output is unavailable. Do not dispatch work
from resolution. A resolved request still passes through recovery authentication,
fencing and the atomic current-evidence checks described above.

Defaults are four concurrent plan passes, one per scope, 64 claims per page and
a one-second polling interval. Claim/seal reads have a five-second default timeout.
`AttemptTimeout` covers snapshot authorization, snapshot reading, resolution and
adoption together; it defaults to thirty seconds and cannot exceed that duration.
All callbacks must honor cancellation. An error on one claim does not prevent
later claims from being visited, and pending claims remain available to later passes.

`TaskAdoptionStatus` reports local lifecycle counters. Startup context values
preserve your service identity, while the engine owns cancellation. `Stop` cancels
all task services before draining any of them. If a callback outlives the stop
deadline, the service stays in the stopping state and rejects restart until it
returns. A resolver returning a request after cancellation cannot submit it to
adoption storage.

Restart begins discovery again. Completed claims are skipped, and uncertain
commit receipts remain available through the acceptance store. This service does
not deliver the acceptance outbox. Delivery requires a host-authorized outbox
consumer.

Local engine integration tests exercise adoption and restart against SQLite,
PostgreSQL and MongoDB. They use fixture authority ports. You still need concrete
host proof validation and deployment qualification before enabling this service
for real workers.

### Inspect combined usage

The built-in stores implement `coordination.TaskUsageSnapshotStore`. After you
authorize the read, pass `SnapshotTaskUsage` the current recovering/completed claim
token, retained journal seal and expected journal digest. The store locks the plan,
run and journal, reads every verifier job for that run, and returns a detached
snapshot. A changed claim or journal, a failed transaction, or cancellation returns
no snapshot. The read is bounded to thirty seconds, 256 verifier jobs and sixteen
MiB of encoded evidence. Oversized history fails instead of being truncated.

`coordination.SummarizeTaskUsage` totals usage fields from provider
receipts and verifier completions, including failed work and earlier attempts.
`Observed` is a lower bound when a dimension is missing from `Known`. Missing
receipts and unmetered jobs never imply free work. Overflow saturates the affected
dimension and removes it from `Known`; local token estimates cannot replace
provider evidence. `OpenJobs` identifies verifier work that has not reached a
terminal state.

This is an observation of retained records. You still need to authenticate their
provenance and pricing, close future verifier admission, establish billing finality
and revalidate the exact evidence when settling. The snapshot and summary do not
refund capacity or authorize additional work. Tool and external-effect fees are
outside this provider/verifier summary.

### Close verifier admission before settlement

After task acceptance and terminal verifier jobs, pass the exact usage request and
snapshot digest to `coordination.NewTaskUsageCloser(...).Close`. You supply a
current host authorizer and synchronous authority fence. The built-in store
rechecks ownership and all retained evidence under the same plan, run and journal
guards, then writes a permanent closure receipt. An open verifier job, changed
snapshot or lost authority prevents closure.

Closure blocks new job enqueue, job claims, lease renewal and metered verifier
dispatch for that run. All enqueue paths share the check. Historical enqueue
acknowledgments and evidence reads remain available; they grant no new work.
Use `GetTaskUsageClosure` to inspect the retained receipt. Identical closure retries
return `Fresh: false`; a different closure request conflicts. An error may follow
a commit, so retry the original request after an uncertain acknowledgment.

This transition does not stop an external call already dispatched, authenticate
its final bill, or refund any reservation. Late observations remain available for
reconciliation. Settlement still needs final billing authority and a fresh check
of the complete evidence. Reverification after closure needs a new run and budget.

### Close unsuccessful task usage

For a failed, cancelled or incomplete child whose claim is recovering, set
`TaskUsageClosureRequest.Termination` from the saved run's revision, state and
completion time. Read these values from storage, including the persisted timestamp
precision. The run must have no committed result reference or passed verification
status. The call journal must already be sealed and every verifier job terminal.

The same guarded closer checks the original dispatch and current run under the
plan, run and journal transaction. A different run revision, completion time,
worker or claim blocks closure. Running, paused and completed runs cannot use this
mode. Accepted tasks continue to omit `Termination`.

Closure and settlement leave the claim in recovery. They do not accept an answer,
release task ownership or permit another attempt. You can invoke this path directly
or enable `UnsuccessfulRuns` on the managed settlement service below. Governed
ownership retirement and retry remain separate integration work.

### Settle task usage

Use `coordination.NewTaskUsageSettler(store, fence, authorizer).Settle(ctx, request)`
after closing verifier admission. Your request pins the accepted or recovering claim, current
sealed journal and complete usage digest, closure receipt, original reservation
and billing proof. Refresh the usage snapshot before requesting that proof: late
observations can arrive after closure, and settlement checks the exact current
evidence again.

For an unsuccessful run, fresh settlement also rechecks the closure's terminal
run binding. A run changed after closure cannot settle against that old revision.
The billing requirements and conservative handling of unknown charges apply to
unsuccessful work too.

The store holds the plan, run and journal guards while it derives provider and
verifier charges and commits both accounting and the guarded receipt. It requires
the reservation created by `AcquireBudgetedTaskClaim`; an independently created
or already settled reservation cannot be adopted. Known unused capacity can be
refunded. Missing usage retains the allocation or observed minimum, whichever is
larger, and overflow continues to block admission. Steps, tool calls, fan-out and
replan capacity remain charged. Token-only reservations make no monetary claim.

You supply the billing authenticator. It must check original provider accounts
and routing, every verifier attempt, the pinned pricing revision, and the proof's
binding to the scope, ownership, closure, usage and reservation. Known charges
must be final. Unknown charges need an enforced upper bound no larger than the
retained charge, including delayed work. Other work cannot add unaccounted fees
to a refunded dimension. If you cannot establish those facts, leave the
reservation open. A digest or fixture proof reference is not billing evidence.

The synchronous fence holds current host authority through the transaction.
Proof windows last at most thirty minutes, and each settle attempt is bounded
to thirty seconds. The store checks proof expiry again after its writes, before
returning from the transaction callback. Host authority must remain valid through
commit. These ports do not fetch provider bills or qualify a live deployment.

`GetTaskUsageSettlement` reads the historical receipt. An identical guarded retry
still requires current host authorization, then returns the original receipt with
`Fresh: false`, including after a lost acknowledgment or cancellation following
commit. A changed request conflicts. Historical retries do not require the old
proof window to remain open and do not replace settled accounting with later
observations. Preserve the proof and source receipts for reconciliation.

### Run settlement with the engine lifecycle

Pass `engine.WithTaskSettlement(coordination.TaskSettlementServiceConfig{...})`
before `Start`, or use `coordination.NewTaskSettlementService` directly. Supply
`Store`, `Discovery`, `AuthorizeScan`, `ClosureActor`, `ClosureFence`,
`ClosureAuthorizer`, `Resolver`, `Fence` and `Authorizer`. You can pass the engine
option through Forge's extension lifecycle too.

To include unsuccessful work, set `UnsuccessfulRuns` to a scoped
`TaskSettlementRunReader`, such as your built-in Cortex store. The service then
interleaves accepted-history pages with current-claim pages, using independent
cursors under the same plan concurrency and shutdown limits. A failed page in
one traversal does not prevent the other from progressing. Nil preserves
accepted-only discovery.

Recovering claims need an existing call seal. Accepted-task sealing ports cannot
seal them. After `AuthorizeScan`, the service reads current run metadata and closes
usage only for failed, cancelled or incomplete runs with a valid terminal binding.
Running, paused and completed runs wait. The closure and settlement stores recheck
the observed metadata under their guards before writing.

To seal ordinary accepted runs automatically, also supply `CallSealFence` and
`CallSealAuthorizer`. Both are required together, and `Store` must implement
`TaskCallSealStore`. `ClosureActor` identifies this caller too, but the call seal
has its own authorization before the store reads the claim and run. Without these
ports, unsealed runs wait for a later pass.

The guarded sealer checks the exact completed claim, its acceptance record and the
current completed run's committed result while holding the plan, run and journal
guards. Mismatched claim history or a changed run prevents closure. A replacement
claim can own a later plan revision while the old accepted run is sealed.
Recovery adoption already needs
its own journal seal and does not use this ordinary-completion path. Closure
prevents new calls, including delayed historical admission attempts; previously
admitted calls can still finish and write their observations.

You can also call `coordination.NewTaskCallSealer(store, fence, authorizer)`
directly. Pass a `TaskCallSealRequest` with the claim token, full claim digest and
run seal request. A retry rechecks current authority and retained accepted ownership before returning
the matching journal seal. An error can follow a committed seal, so retain the
original request when an acknowledgment is lost.

The service pages accepted claims by acceptance ID, including earlier ownership of
the same task after a replacement claim is acquired. `Store` must implement
`AcceptedClaimStore.ListAcceptedTaskClaims`. Each entry retains its matching
acceptance, preceding ownership revision and original dispatch. The service uses
the old run's existing or newly authorized seal. It checks
scan authority before reading budgets, usage or settlement receipts, then closes
verifier admission through `TaskUsageCloser` and asks your resolver for billing
proof against the exact snapshot, closure and original allocation. Unbudgeted
claims, open verifier jobs and a resolver returning nil wait for a later pass.
No capacity is refunded while proof is pending.

`ResolveTaskUsageSettlement` receives detached metadata and returns a
`TaskUsageSettlementRequest`. It must honor cancellation and resolve proof without
executing or retrying task work. The service checks the returned bindings, then
calls the guarded settler. The settlement fence and authorizer still control the
write. If a receipt already exists, the service retries its original request under
current authorization without requesting another bill, including after restart
or a lost acknowledgment.

Defaults are four concurrent plan passes, one per exact scope, 64 entries per page,
five seconds per page or seal read, and one second between page rounds. With
`UnsuccessfulRuns`, each round visits one page from each unfinished traversal.
A complete
settlement attempt defaults to thirty seconds; `AttemptTimeout` accepts one
millisecond to thirty seconds. Optional call sealing has its own attempt with the
same bound. Discovery retains its separate timeout. Callbacks
must return before `Stop` reports drainage. A timed-out stop preserves service
ownership and prevents restart until the callbacks finish. `TaskSettlementStatus`
reports running/stopping state, active passes and failures without billing data.

Your discovery source must retain completed or cancelled plans with outstanding
debt. Within each discovered plan, traversal covers accepted history even when a
later revision replaces ownership. Accounting reads that historical claim and
settles its original reservation without changing the replacement claim or its
capacity. Missing acceptance, ownership or dispatch records fail the pass. Keep
them until accounting and retention requirements are satisfied. Recovering claims
still require current ownership; this history path grants no retry or execution
authority. Sealing does
not establish worker quiescence or authenticate provider bills. Those host
integrations and their live qualification remain required.

### Sweep expired claims

Use `coordination.NewClaimSweeper(store, clock)` to expire one page of claims in
an authorized scope. Pass a `ClaimListRequest` with a plan ID and a limit from 1
to 256. The store must implement `ClaimExpiryStore`; the built-in claim stores do.
Discovery includes tasks removed by replanning.

`Sweep` checks the full page before writing. An expired held claim becomes
released. An expired dispatched claim becomes recovering and keeps its run ID
and fence. Each write compares the observed revision inside the store transaction,
so a concurrent renewal cannot be overwritten by a stale sweep.

Continue with `ClaimSweepPage.NextTaskID` while it is nonzero. When it is zero,
the pass has ended; start the next pass from the beginning so live claims and
revision conflicts are checked again. Counts describe acknowledgments in that
call. They do not distinguish a new write from a historical receipt.

On an error, retry the same page from fresh storage observations. No continuation
cursor is returned because earlier writes may have committed. Cancellation stops
further writes and preserves those committed records. You can own the polling
loop or install the lifecycle service below.

Recovery still needs authenticated provider and effect receipts before a retry,
continuation or acceptance. Claim expiry does not settle usage, refund shared
capacity, complete a task or authorize another external call.


### Run claim recovery with the engine lifecycle

Pass `engine.WithClaimRecovery(coordination.ClaimRecoveryConfig{...})` to let the
engine own discovery and expiry. Supply `Store`, `Clock` and `Discovery` explicitly.
The store needs `ClaimExpiryStore`; discovery uses `TaskPlanSource`. Include plans
with outstanding claims even when their parent is cancelled or completed. You can
pass this option through Forge's `extension.WithEngineOption`, or use
`coordination.NewClaimRecoveryService` directly.

The service shares scheduling's bounded discovery, identity checks and scope
limits. Defaults are four concurrent plan passes, one per exact scope, 256 claims
per page, and five seconds for each storage page. `Interval` defaults to one second
and controls both discovery polls and the delay between claim pages. `PageSize`
accepts 1 to 256, `PageTimeout` accepts one millisecond to one minute, and
`MaxInFlight` and `MaxPerScope` accept 1 to 4096. Discovery keeps its own timeout.

Each plan pass starts at its first claim and advances until it reaches the end or
fails. It keeps its local slot between pages. Limits bound simultaneous work and
individual page calls, not the total size or duration of a plan's history. On
restart or error, a later pass begins again and reads retained outcomes. Existing
released or recovering claims are not expired a second time. You must keep the
source's pages finite and honor cancellation in storage callbacks.

Engine lifecycle calls are serialized through shutdown notification. A caller
waiting for another lifecycle call can cancel its own wait. Lifecycle hooks must
return before another Start or Stop can proceed.

`Engine.Stop` signals both scheduling and recovery before waiting for either to
drain. A timeout preserves the stopping state and suppresses shutdown hooks;
retry Stop before disposing stores. `RequestStop` on either standalone service
only signals cancellation. It does not replace the join performed by Stop.
`ClaimRecoveryStatus` reports configuration, running/stopping state, active plan
passes and failures without exposing scope values or run content.

This service moves expired dispatches into recovery. It does not reconcile an
external provider, retry an invocation, accept task output or settle shared usage.
Those operations still need their own authorized evidence and transactions.


### Process-crash coverage

The SQLite crash matrix starts a separate task-worker process and kills it after
one of four durable boundaries: a held claim, committed dispatch intent, entry to
a journaled provider call, or completion of local execution and verification.
The parent reopens the database, advances a controlled lease clock and runs the
recovery lifecycle through a new engine.

You can run it with:

```bash
GOWORK=off go test -race -count=1 ./engine -run '^TestClaimRecoveryAfterWorkerProcessCrash$'
```

The checks require unused claims to release and dispatched claims to enter
recovery, preserving their run ID, fence, history and charged reservations.
An interrupted call retains an empty completion. A completed local run retains
its result, but neither state grants task acceptance or another invocation.
Historical claim admissions and call-journal entries cannot authorize replay.

This matrix covers process death and SQLite persistence with a fixture provider
and controlled clock. It does not qualify a deployed provider, remote worker,
PostgreSQL or MongoDB process failure, or late external completion receipts.
