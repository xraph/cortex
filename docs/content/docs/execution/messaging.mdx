title: Agent Messaging
description: Agents addressing each other directly with FIPA-ACL messages, a durable ask that survives a restart, and a mailbox for everything else.
---

Orchestration coordinates agents through shared state: a blackboard every
participant reads and writes, inside one run somebody started. Messaging is the
other half. An agent addresses a peer by name, says what kind of thing it is
saying, and either carries on or waits for the answer. No orchestration has to
exist for any of it.

Turn it on with `engine.WithA2A`. Nothing appears without it: no tools in any
agent's list, no rows in any messaging table, no behaviour you did not ask for.

```go
eng, err := engine.New(
    engine.WithStore(st),
    engine.WithA2A(a2a.Options{
        HopCeiling:     8,
        Workers:        4,
        DefaultReplyBy: 5 * time.Minute,
        SweepInterval:  30 * time.Second,
    }),
)
```

## Three tools

Your agents get three new tools, and the whole feature is what they do.

`agent_send` posts a message and returns immediately. Use it to tell somebody
something, confirm, refuse, or hand work along. Nothing waits.

`agent_ask` asks one or more peers a question and suspends the asking run until
the answers come back. They arrive as that tool call's result, so from the
model's side it reads like any other tool that took a while. The wait is a row
in your database rather than a goroutine, so it survives a restart. Asking
several agents at once is how you run a tender, which is its own section below.

`agent_inbox` drains the messages that arrived while the agent was busy.
Reading marks them read, so each message comes back once.

## Speech acts

Every message carries a FIPA-ACL performative, and cortex routes on it. There
are 22 of them, and they fall into three groups.

Directives start a run. `request`, `request-when`, `request-whenever`,
`query-if`, `query-ref`, `cfp`, `propose` and `accept-proposal` all demand an
answer, so the recipient runs and its output becomes the reply.
`accept-proposal` is in this group rather than with the informatives because in
Contract Net it is the message that makes the contractor do the work.

Informatives land in the inbox. `inform`, `inform-if`, `inform-ref`,
`confirm`, `disconfirm`, `agree`, `refuse`, `failure`, `not-understood`,
`reject-proposal`, `subscribe`, `proxy` and `propagate` queue for the recipient
to read on its own time. Nobody spawns a run to be told something.

Two of those are worth knowing about. `agree` means "I took the job and I am
still working", so it does not un-pause a waiting ask. `refuse` and `failure`
do. And `proxy` and `propagate` are carried and delivered, but cortex will not
forward them on an agent's behalf: forwarding is a policy decision with an
obvious abuse shape, so build it over the inbox if you want it.

`cancel` is control. It closes the conversation and un-pauses everyone
waiting on it with a failure they can read, rather than leaving them to sit
until their deadline.

## Putting work out to tender

When you do not know who is best placed to do something, ask everyone and
let them tell you. That is Contract Net, the oldest task-allocation
protocol in multi-agent systems, and cortex speaks it with the tools you
already have.

Ask several agents at once and your run waits for the whole field:

```
agent_ask(
  to: ["fast-reviewer", "slow-reviewer", "busy-reviewer"],
  performative: "cfp",
  protocol: "fipa-contract-net",
  content: "who can review the migration today?"
)
```

The run resumes when everyone has answered, or when the deadline passes
with whoever did. Every proposal and every refusal comes back together:

```json
{
  "complete": true,
  "replies": [
    {"sender": "fast-reviewer", "performative": "propose", "content": "I can, by 3pm"},
    {"sender": "slow-reviewer", "performative": "propose", "content": "I can, by 9pm"},
    {"sender": "busy-reviewer", "performative": "refuse",  "content": "not today"}
  ]
}
```

Then the agent picks, and awards:

```
agent_send(to: ["fast-reviewer"], performative: "accept-proposal", content: "yours, by 3pm")
agent_send(to: ["slow-reviewer"], performative: "reject-proposal", content: "thanks anyway")
```

Cortex never picks the winner. Choosing a contractor is a judgement, and
an agent is what makes it. If you want the work back rather than just an
acknowledgement, award with `agent_ask` instead: `accept-proposal` is a
directive, so the winner runs and its result comes back as your answer.

Two behaviours are worth knowing. A refusal counts as an answer, so one
agent declining does not end a round the others are still thinking about.
And a participant that never answers at all is ordinary rather than
exceptional: the deadline resolves your ask with `complete: false` and
whoever did reply, and you carry on with what you got.

Hosts driving a tender from Go rather than through an agent's own
reasoning have `a2a.ContractNet` and `a2a.CollectTender`.

## Who can talk to whom

An address is an agent name inside the sender's scope. Cortex enforces the
scope boundary structurally, the same way it does everywhere else, and it
refuses an address that names no agent you can reach.

Whether two agents that share a scope may talk is your policy, and it goes
through the seam you already have. `agent_send`, `agent_ask` and `agent_inbox`
are ordinary tool calls, so your `ToolAuthorizer` sees them like any other:

```go
func (p policy) Authorize(ctx context.Context, s cortex.Subject, call llm.ToolCall) error {
    if call.Name == "agent_ask" && !p.mayAsk(s.AgentID, call) {
        return errors.New("this agent may not ask others for work")
    }
    return nil
}
```

Returning `cortex.ErrRequiresApproval` works here too, which gives you
agent-to-agent messaging that pauses for a person to approve.

## What stops a runaway

Two agents can message each other forever, so every conversation carries a hop
budget. Each derived message increments the count, and delivery past the
ceiling is refused with a `failure` back to the sender. `HopCeiling` defaults
to 8.

Asks also carry a deadline. If nobody answers in time, the ask resolves into a
timeout failure and the asking run continues. That is deliberate: cortex's own
suspension sweep fails a run nobody answered in time, which is the wrong verb
here. A peer that went quiet is something the asking agent can react to, and
killing the run throws that away.

## When a process dies

Whatever was in flight is picked up by the next one. A run waiting on a
peer is a row rather than a goroutine, so it resumes where it stopped. A
message that was queued but never carried is redriven at startup. And a
message a dead worker had claimed is put back in the queue once its claim
goes stale, which `DeliveryClaimTTL` sets and which defaults to fifteen
minutes.

That default is generous on purpose. A remote delivery holds its claim
while the peer is polled, and reclaiming one somebody is still carrying
would deliver the same message twice.

## When things go wrong

A peer's problem reaches the asker as something it can read, never as a crash.
The recipient's run failed, the hop budget ran out, the deadline passed, the
conversation was cancelled: each of those un-pauses the asker with a `failure`
carrying the reason.

Anything cortex can refuse, it refuses before suspending: an unknown recipient,
an agent addressing itself, a closed conversation, a store write that did not
land. Those come back as a tool error and the run carries on. A run suspended
on a message that was never sent would be a run nothing could ever resume.

## Reading it back

In Go, `eng.ListConversations`, `eng.GetConversation`, `eng.ListMessages`, `eng.AgentInbox` and `eng.SendMessage` cover it. When you mount the `api` module through `extension.WithRoutes`, the same is available over HTTP under the base path (default `/cortex`):

```
GET  /cortex/v1/a2a/conversations         every conversation in scope
GET  /cortex/v1/a2a/conversations/:id     one conversation with its transcript
GET  /cortex/v1/agents/:name/inbox        what is waiting for an agent
POST /cortex/v1/agents/:name/messages     send an agent a message
```

A reply counts only when it comes from an original recipient and addresses the
original asker in the same conversation. The pending ask's saved message fixes
that recipient set. Reusing a reply token on another message or conversation
cannot replace it. Duplicate replies count once, including when the original
request repeated a recipient. Timeout and cancellation results use the same
checks when collecting partial answers.

Your host must authenticate the sender before calling `Send`. A matching address
and correlation token establish message membership; they do not verify who
submitted the message or whether its answer is correct.

## Hooks

Three plugin hooks fire alongside the ones you already have: `MessageSent`,
`MessageDelivered` and `MessageRefused`. `AgentHandoff` is untouched and still
means what it always did, because an orchestration handoff and an agent
addressing a peer are different events.


## Isolate orchestration traffic

Set `a2a.BusConfig.OrchestrationID` when you build a bus for one team. The
SQLite, PostgreSQL and MongoDB stores persist that ID on messages, conversations,
deliveries and pending asks. A zero ID selects global traffic. It never means
all teams.

For direct storage access, use `a2a.NewRoutingStore(store, teamID)`. The returned
store fixes the routing partition while preserving the caller's scope,
cancellation and deadline. IDs, inbox reads, peer-context lookup, claims and
updates all remain inside that partition. Queue discovery and stale-delivery
reclaim can cross scopes, but cannot cross orchestration partitions. Expired-ask
queries still require a host scope.

A bus fixes its partition at construction, including when its supplied store
was previously bound to another team. Reopening a bus with the same ID restores
access to its retained queue. Background delivery restores each row's scope
before claiming it. A global bus cannot consume a team's queue.

Custom stores must implement `a2a.RoutingBackend` and enforce
`a2a.RoutingOrchestration(ctx)` on every messaging operation before reporting
support. The returned value is backend routing metadata, not participant
authorization. Unsupported stores reject nonzero orchestration IDs.

SQL migration `20261025000001` preserves existing rows in the global partition
and can replay after its schema changes committed without their migration
record. Its downgrade is refused because removing the partition would expose
private traffic globally. MongoDB reads documents without the field as global
traffic; new writes always persist the field.

The prepared-team integration below supplies captured-roster routing,
shared-budget admission and authorized recovery. A storage partition alone does
not authorize remote peers, provide an isolated tool environment or make stale
delivery replay safe for external effects.

## Freeze a local participant roster

Pass `BusConfig.Roster` with the team's exact scope and captured agent identities:

```go
roster := &a2a.Roster{
    Scope: scope,
    Participants: []a2a.RosterParticipant{
        {Name: "planner", AgentID: plannerID},
        {Name: "reviewer", AgentID: reviewerID},
    },
}
```

Supply a nonzero `OrchestrationID` too. The bus accepts 1 to 256 participants,
rejects repeated names or agent IDs, and copies the roster at construction.
Remote addresses are not supported in a roster. Sender, receiver and reply-to
addresses must belong to it. Inbox reads, held-ask release and queued delivery
recheck those restrictions before exposing content or invoking a runner.

Use `ParticipantAddress(ctx, agentID)` to resolve a captured agent's original
name without reading its current stored name. Your host must first authenticate
the invoking run and its agent identity. The roster does not authorize a caller
to impersonate another member, pin executable agent versions or grant capacity.
Keep those checks in the prepared runner and host authorization path.

Normal message calls require the exact captured scope. Background queue reads,
reclaim and expired-ask discovery use that same scope even with an unscoped
lifecycle context. Another scope using the same orchestration ID keeps its queue
and pending asks. The bus restores each discovered ask's scope before claiming it.

A roster requires `ScopedRoutingBackend`, implemented by all three built-in
stores. Custom backends must honor `RoutingDiscoveryScope(ctx)` on queue reads,
reclaim reads and writes, and expired-ask queries before reporting support.
Without a roster, routing retains its existing discovery scope rules.

This is a bus-level identity restriction. Use `WithPreparedTeamMessaging` below
to bind it to prepared execution and durable continuation.

## Reserve directive execution before dispatch

Use `BusConfig.ReservedRunner` with an orchestration ID when your runner needs
durable admission. Supply either `Runner` or `ReservedRunner`. Reserved buses
require a store implementing `a2a.DeliveryRunBinder` and
`a2a.ReservedReplyStore`; all three built-in backends support them. Your runner implements `cortex.ReservedAgentRunner`, the
same contract exposed through aliases in `orchestration`.

`ReserveAgent` allocates bounded capacity and returns a unique child ID plus an
`Execute` callback. It must not call a model or execute tools. The bus binds
that ID to the claimed delivery before calling `Execute`. The callback must
start that exact child at most once. Your runner still owns frozen-roster
authorization, shared-budget admission and linkage to the parent orchestration.
The bus copies the admission values before invoking storage or execution
callbacks, so changing the returned reservation cannot change the bound ID.

Each claim has a unique token. Binding and delivery updates reject a stale
token, and binding can succeed only once. Reclaim checks the token again when
it writes, so a worker cannot reclaim a newer claim from an earlier query.
Once a delivery has a run ID, timeout-based reclaim leaves it alone. You must
reconcile the run and any external effects before deciding how to recover it.

If reservation returns an identity with an error, the bus records the identity
and refuses execution. Cancellation after reservation follows the same rule.
A failed binding, including a lost acknowledgment, also prevents execution.
`a2a.DeliveryAdmissionError` exposes `RunIdentity()` and `DeliveryIdentity()`
for reconciliation while its public error text omits private diagnostics.
Neither identity grants permission to retry. Mismatched execution IDs retain
the reserved ID and record the unexpected ID as a failed delivery; their
output is withheld. Reserved execution failures produce a generic peer reply.

A reserved child returning only `cortex.ErrOrchestrationWaiting` stays bound in
`delivering`. The bus publishes no terminal reply and leaves the sender's ask
pending. Repeated drains and timeout reclaim cannot dispatch that child again.
If the result also contains a failure, it follows the failure path. Both A2A and
orchestration use `cortex.IsOrchestrationWaiting` to classify wrapped and joined
errors consistently. Deferred recipient recovery observes a later completion and
commits its reply without executing the child again. The prepared-team integration
drives that recovery while its coordinator owns the team.

SQL migration `20261025000002` adds claim tokens and supports replay after an
unrecorded schema change. MongoDB accepts missing tokens on legacy records;
new claims always receive a token. Stop older dispatchers before upgrading:
older binaries do not enforce these fences. SQL downgrade is refused.

This admission contract does not enable prepared-team messaging by itself.
Enable the engine integration below to connect frozen participant routing,
parent linkage and durable suspension continuation.

## Atomic reserved replies

A reserved recipient's completion, reply envelope, queued reply delivery and
conversation hop charge commit in one transaction. The retained
`a2a.ReservedReply` receipt binds the delivery, child run and reply identities.
An identical retry returns that receipt without another message or hop charge.
Changed content, outcome or execution binding fails.

If the commit acknowledgment is lost, a fresh bus can drain the retained reply
without running the recipient again. `GetReservedReply` lets you inspect the
commit; it grants no execution or resume authority. A transaction error returns
no receipt, even when the database committed the write. Lifecycle hooks are not
a durable event outbox and can be missed after an ambiguous acknowledgment.

Native buses also use `AtomicMessageStore.RecordMessage` to serialize ordinary
message recording with conversation hop admission. Closed conversations and
exhausted hop limits reject new replies without completing the original delivery.
That bound delivery needs reconciliation; the bus does not bypass the limit with
a direct resume. Identical recorded-message retries consume no extra hop. Stop
older dispatchers before upgrading, since their separate conversation updates can
overwrite concurrent hop counts. Custom stores without this capability retain
the legacy ordinary-message path, but cannot run reserved dispatch.

These transactions require a MongoDB replica set or another deployment supporting
transactions. SQLite and PostgreSQL use native transactions. No provider calls or
run resumes occur inside database transactions.

The queued reply survives a restart before ask resolution. Retained ask outcomes
and resume admissions bridge the later claim-to-resume steps. An acknowledged
start permits execution once; a possibly started execution still requires
reconciliation.

## Retained ask outcomes

Native buses use `a2a.AskResolutionStore` to claim a pending ask and retain its
selected tool-result payload in one transaction. Peer answers, deadline expiry
and cancellation use the same path. The receipt includes the original ask
binding, exact JSON payload, content digests and seal time. The payload supports
up to 256 reply items and 4 MiB of encoded JSON; the complete retained record is
also bounded. Oversized or malformed outcomes leave the ask unclaimed.

An identical seal retry returns the existing receipt with `Fresh` false. A
competing outcome receives `ErrAskAlreadyClaimed`. Changed ask identity fails.
A transaction error returns no receipt, including after a lost commit
acknowledgment. The committed receipt remains available through
`GetAskResolution`. `ReadPendingAsk` includes claimed asks, while
`ListAskResolutions` pages retained outcomes in one exact scope and routing
partition. Its default page size is 64 and its maximum is 256. Treat its cursor
as opaque.

The bus invokes its resumer only after a fresh seal acknowledgment. Reading a
receipt or repeating an identical seal does not invoke it again. If resume
fails, the selected answer remains available, but the receipt does not say
whether resume started or finished. The engine's separate admission and start
records support the guarded recovery path below. Prepared teams use the same
records through their private routing partition and current coordinator.

When timeout or cancellation cannot read the source message and collected
answers, the native path returns the error and keeps the ask pending. It does
not substitute a partial result. Legacy claims without retained outcomes cannot
be adopted. Custom stores without this optional capability retain the earlier
claim-and-resume behavior and its recovery limitations.

## Correlate answers with the paused questions

The native engine persists each held question's `reply_with` token in its
suspension's pending call before releasing the question. The token identifies
that question even if a later model response reuses the same tool-call ID.
`a2a.ResolutionResumer` receives the retained outcome and checks it against these
stored tokens. The legacy run-ID-only resumer cannot answer a correlated pause.

If one step asks several questions, the first answer stays in storage. Each new
answer checks the retained outcomes for all pending questions, and the engine
resumes only when they are all present. A fresh engine can read the earlier
answers. Assembly is bounded to 256 pending questions and 4 MiB of combined
encoded results; the run's publication checks still apply to each result.

Before reading those outcomes, the engine captures the suspension ID and run
revision. Both must still match when it claims the pause. Replacement, revision
changes, missing bindings and failed evidence reads leave the run paused. A
later question never inherits an earlier question's answer just because its
tool-call ID matches.

Drain existing agent-reply pauses on their compatible workers before upgrading.
Older pauses have no question token, and this path refuses to infer one. Custom
stores without retained outcomes keep their legacy behavior. A store that
provides retained outcomes must also provide versioned suspension claims and
durable resume admission.
Drain older messaging dispatchers too. They ignore the correlation field and
must not service new correlated pauses during a mixed-version rollout.

This correlates normal delivery, including several answers arriving across an
engine restart. Reading history alone does not authorize another execution.

## Recover an interrupted reply

Use the host recovery entry point with the run ID, original suspension ID and
a callback that checks your current service identity's permission for that run:

```go
recovered, err := eng.RecoverAgentReply(ctx, runID, suspensionID, authorizeRecovery)
```

The context needs the run's exact scope. Permission is checked before reading
private input, before starting, and before every provider or tool call. This is a
host API; Cortex does not expose it as a model tool or an unauthenticated route.
If some questions still lack answers, the returned run remains paused.

Native stores commit a `ResumeAdmission` with the paused-to-running transition.
It retains the exact encoded input, suspension digest and expected run revision.
A separate `ResumeStart` transaction grants execution once. Only its fresh,
acknowledged result carries the suspension to execute. The engine reuses the
normal resume checks and loop after that grant.

Recovery can continue after a lost answer-seal acknowledgment, a lost admission
acknowledgment or a crash before the start transaction. If a start record already
exists, recovery returns `suspension.ErrResumeAlreadyStarted` and executes
nothing. That record means execution may have started, even when the original
worker never received its acknowledgment. Inspect the run and effect evidence;
do not clear the record to force another attempt.

`suspension.ResumeAdmissionStore` exposes reads bound to both run and suspension
IDs. Its history is exact-scope, defaults to 64 records and caps pages at 256.
Admission input is bounded to 8 MiB, including JSON escaping. Treat it as private
execution material. Neither admission nor start observations carry execution
authority.

Changed run revisions, replaced or edited suspensions, expired pauses and wrong
scope fail before a start grant. Expired admitted work and execution that may
already have started still need host reconciliation. For private prepared-team
asks, recovery also requires an active coordinator lease. A run authorization
callback alone cannot replace that lease.

### Run recovery in the background

Configure discovery with the exact scopes your host service owns. The native
SQLite, PostgreSQL and MongoDB stores implement `suspension.ReplyDiscoveryStore`:

```go
source, err := coordination.NewScopedAgentReplySource(
    replyDiscoveryStore, scopes, authorizeScopeDiscovery,
)
if err != nil {
    return err
}
eng, err := engine.New(
    engine.WithStore(st),
    engine.WithLLM(client),
    engine.WithA2A(a2a.Options{}),
    engine.WithAgentReplyRecovery(engine.AgentReplyRecoveryConfig{
        Service: coordination.AgentReplyRecoveryConfig{Discovery: source},
        Authorize: authorizeRunRecovery,
    }),
)
```

Start and stop the engine through its normal lifecycle. Startup context values
carry your host service identity; canceling the startup request does not stop
the service. `Stop` cancels discovery and active attempts, then waits for them
to return. A timed-out stop leaves the service stopping, so keep its store and
provider dependencies alive until a later stop succeeds.

Defaults are four concurrent runs, one per scope, one-second polling,
five-second discovery and one-minute attempts. You can configure those bounds;
attempts cannot exceed thirty minutes. Discovery pages contain at most 256 run
IDs and never load answer bodies or continuations. The scoped source detaches
at most 256 distinct scopes and rechecks discovery permission after each query.

Recovery rechecks the run's current state, scope and suspension before entering
the same guarded resume path used by explicit recovery. Waiting questions stay
paused. Completed runs are skipped. A retained start receipt produces
`ErrResumeAlreadyStarted`, and an expired admission produces
`ErrSuspensionExpired`; your `ReportError` handler can route these to host
reconciliation. Polling never clears either condition or retries uncertain
execution. Error reporting must return promptly and callbacks must honor
cancellation.

`AgentReplyRecoveryStatus` reports whether the service is configured and its
local active/failure counters. These counters contain no run content or scope
values. The host still supplies current authorization and installs the service;
adding `WithA2A` alone does not enable background recovery.

## Complete a deferred recipient's reply

A reserved recipient can pause while its original delivery remains `delivering`.
After the child finishes through its authorized resume path, use
`Bus.RecoverRecipient` to publish the retained outcome:

```go
receipt, err := bus.RecoverRecipient(ctx, deliveryID, authorizeDeliveryRecovery)
```

The context needs the delivery's exact scope. Configure `RecipientObserver` on
the same partitioned bus as `ReservedRunner`. The observer reads the original
child's durable state and returns `RecipientWaiting`, `RecipientSucceeded` or
`RecipientFailed`. It must validate the captured participant, run identity,
prepared provenance and current permissions. A read error stays an error and
leaves the delivery pending; it must not be converted into a failed-child result.

For prepared teams, your observer adapter can call
`Engine.ObservePreparedRecipient(ctx, request, authorizeRunObservation)`. This
host API restores the original team snapshot and checks the child, scope,
participant, parent linkage, budget reservation and usage before returning an
outcome. It needs no LLM client. It rechecks host permission before returning
output, reads only the run's published output, and does not change its verification
status. Terminal observations can read settled reservations; paused children
still need an unsettled reservation to resume. Closed or expired team authority
remains a reconciliation condition.

Recovery never reserves, executes or resumes the child. Waiting returns an empty
receipt. A terminal result uses the same atomic reply commit as immediate
delivery: the original delivery, reply message, hop charge, reply queue entry and
receipt change together. Failed-child replies contain a generic failure message;
private diagnostics are discarded.

Permission is checked before reading the delivery and again after observing the
child. Concurrent callers receive the same committed reply, with one fresh
acknowledgment. If the commit acknowledgment is lost, a fresh bus can read that
receipt and drain the retained queue without observing or executing the child
again. Lifecycle hooks remain best effort, so receipt recovery does not replay
them as though they were a durable event log.

### Discover deferred replies automatically

Set `RecipientRecovery` when you construct a reserved bus with a captured roster:

```go
config.RecipientRecovery = &a2a.RecipientRecoveryConfig{
    AuthorizeDiscovery: authorizeTeamRecovery,
    AuthorizeDelivery:  authorizeDeliveryRecovery,
    BatchSize:         32,
    AttemptTimeout:    5 * time.Second,
    ReportError:       reportRecoveryError,
}
bus, err := a2a.NewBus(config)
// Handle err before starting the bus.
err = bus.Start(ctx)
// Call bus.Stop() during shutdown and wait for it to return.
```

Your discovery callback authorizes the team's current service access, including
reclaiming stale unbound deliveries. The delivery callback authorizes each
specific reply recovery. Both callbacks and the recipient observer must honor
cancellation. Keep the error reporter bounded so shutdown can join it.

SQLite, PostgreSQL and MongoDB implement `a2a.RecipientDiscoveryStore`. Its reads
select only delivery IDs in the exact scope and routing partition, with an
exclusive cursor and a limit from 1 to 256. Completed deliveries, queued work and
claims without a bound child are excluded. No message content is loaded during
discovery. The bus checks discovery permission before and after the query, then
checks each delivery's permission through `RecoverRecipient`.

`Start` launches one recovery worker alongside dispatch. Each pass uses the
captured roster scope, reclaims stale unbound deliveries and scans one page of
bound recipients. It advances past waiting and failed observations, then returns
to the beginning after reaching the end. This lets later children finish even
when an earlier child remains paused. Restarting begins a fresh traversal;
retained replies and delivery claims still control publication and dispatch.
`Stop` cancels and joins the worker. Existing `SweepInterval` and
`DeliveryClaimTTL` options control polling and abandoned-claim recovery.

With `Synchronous: true`, you drive the passes through
`bus.RecoverRecipients(ctx, after)`. The returned page contains counts and a
`Next` cursor, without child output. A per-delivery error can accompany a page
that made progress, so retain its cursor when continuing. A discovery error
returns an empty page. You still drive stale-claim recovery and `Drain` explicitly
in synchronous mode.

This lifecycle recovers saved replies. Prepared teams drive the synchronous bus
through the coordinator integration below.


## Enable private prepared-team messaging

Configure the built-in messaging tools and current host permissions together:

```go
eng, err := engine.New(
    engine.WithStore(store),
    engine.WithLLM(client),
    engine.WithA2A(a2a.Options{}),
    engine.WithPreparedTeamMessaging(engine.PreparedTeamMessagingConfig{
        AuthorizeTeam: authorizeTeam,
        AuthorizeRun:  authorizeTeamRun,
    }),
)
// Handle err before preparing or running a team.
```

`AuthorizeTeam(ctx, teamID)` checks current permission to operate the team in the
context's exact scope. `AuthorizeRun(ctx, teamID, runID)` checks permission for
its individual child. Both must honor cancellation. Child authorization runs
before provider and tool calls, including after a resume. It also runs during
admission, when the assigned child ID may not yet have a stored run row. Base
that decision on current host grants and the assigned team identity; do not
require the child row to exist first.

Without this option, prepared teams still reject messaging tools. Configuration
also fails when the store lacks scoped private routing, recipient discovery,
atomic reserved replies, retained ask outcomes or versioned resume admissions.
The three native stores implement these contracts. MongoDB needs transactions.

Each prepared team gets a synchronous private bus with the original participant
names and agent IDs, the exact captured scope and the orchestration ID. Renaming
a live agent does not change its captured address. `agent_send`, `agent_ask` and
`agent_inbox` resolve this bus from the validated invocation. Global traffic,
other teams, remote addresses and agents outside the roster remain inaccessible.
Private buses use the default A2A limits; options for the global bus are not
copied into them. Rosters support at most 256 participants.

Recipient execution reserves from the same team account and links the child to
the parent before starting it. Additional recipients consume fan-out, tool,
step and token capacity. Messaging cannot enlarge that account. The coordinator
drives queued delivery, expired asks, terminal recipient observation and retained
answer recovery before replaying strategy work and before completing the parent.
Nested asks use the same coordinator and bounded account.

When a recipient needs an external tool result, the parent stays waiting. Your
host may resume that child through the normal authorized resume path. To continue
the parent automatically afterward, configure `WithOrchestrationRecovery` with
current team authorization and a scoped discovery source. Recovery notices queued
private replies, terminal recipients and admitted answers awaiting their first
start. It reacquires coordinator ownership before dispatch or ask continuation.
It does not automatically supply external tool results.

Every restart restores the original prepared team and continuation. A global
reply-recovery worker cannot assume the private coordinator's authority. An
