---
title: Runs, Steps & Tool Calls
description: How Cortex tracks agent execution with runs, reasoning steps and tool invocations.
---

Every agent execution is tracked as a Run containing Steps and ToolCalls, so you can see afterwards how an agent reasoned through a problem. `eng.RunAgent` and `eng.StreamAgent` create them for you.

## Run

A Run represents a single execution of an agent:

```go
type Run struct {
    cortex.Entity
    ID           id.AgentRunID
    AgentID      id.AgentID
    SessionID    id.SessionID
    Scope        cortex.Scope
    State        State
    Input        string
    Output       string
    Error        string
    StepCount    int
    TokensUsed   int
    StartedAt    *time.Time
    CompletedAt  *time.Time
    PersonaRef   string
    Metadata     map[string]any
}
```

### Run states

Runs follow a state machine with 9 states:

| State | Description |
|-------|-------------|
| `created` | Run has been created but not started |
| `running` | Run is actively processing |
| `completed` | Execution reached a final answer; verification may still be unchecked |
| `incomplete` | Execution stopped at a limit or without a valid final answer |
| `failed` | Run terminated with an error |
| `cancelled` | Run was cancelled through `CancelRun` |
| `paused` | Run is suspended, waiting for an approval or an external tool result |
| `ready` | A decision or the external results are recorded, and the run waits for `ContinueRun` |
| `reclaimable` | The worker holding the run let go of it or stopped renewing its lease, and the run waits for `ContinueRun` |

### State transitions

```
running → completed
        → incomplete
        → failed
        → cancelled
        → paused → running (after Resume, or ResolveCheckpoint on a store without ready runs)
                 → ready → running (ContinueRun)
                         → cancelled
                 → failed (rejected checkpoint or expired suspension)
                 → cancelled
```

The engine creates runs directly in `running`. `created` exists for runs you create yourself with `eng.CreateRun`. `eng.CancelRun` accepts a running, paused, ready or reclaimable run, and answers `cortex.ErrInvalidState` for anything else.

### Continuing a run from a job

A run doesn't have to continue in the request that answered it. `eng.DecideCheckpoint` and `eng.ProvideResults` write the decision or the results, move the run to `ready` and return without calling the model. `eng.ContinueRun` picks it up later, from a background job on any replica:

```go
// In the HTTP handler: quick, no model call.
err := eng.DecideCheckpoint(ctx, cpID, checkpoint.Decision{Approved: true, DecidedBy: "ops@example.com"})

// In the job, under the run's scope: runs the approved call and the rest of the loop.
r, err := eng.ContinueRun(ctx, runID)
```

`plugin.RunReady` fires when a run becomes ready, with the run's scope on its `ctx`, so it's the natural place to queue that job. `ContinueRun` runs the tool under the principal that started the run, not the job's. It needs a store that implements `run.ContinuationStore`; the built-in SQLite, PostgreSQL and MongoDB stores all do. A store without it gets `cortex.ErrContinuationUnavailable`. See [Suspension](/docs/concepts/suspension#continuing-from-a-job) for the full rules.

`ContinueRun` refuses a run that isn't ready with `cortex.ErrRunNotContinuable`. The error also matches `cortex.ErrRunLeased` when the run is running, and `cortex.ErrRunAlreadyDone` when it has ended, in which case you get the run back too.

See [Execution outcomes and safety](/docs/execution/assurance) for verification, publication and compatibility semantics.

## Step

A Step represents a single reasoning step within a run:

```go
type Step struct {
    cortex.Entity
    ID          id.StepID
    RunID       id.AgentRunID
    Scope       cortex.Scope
    Index       int
    Type        string
    Input       string
    Output      string
    TokensUsed  int
    StartedAt   *time.Time
    CompletedAt *time.Time
    Metadata    map[string]any
}
```

Steps are numbered sequentially (Index 0, 1, 2, ...) and track token usage per step.

## ToolCall

A ToolCall represents a single tool invocation within a step:

```go
type ToolCall struct {
    cortex.Entity
    ID          id.ToolCallID
    StepID      id.StepID
    RunID       id.AgentRunID
    Scope       cortex.Scope
    ToolName    string
    Arguments   string
    Result      string
    Error       string
    StartedAt   *time.Time
    CompletedAt *time.Time
    Metadata    map[string]any
}
```

## Hierarchical model

```
Run (arun_...)
  ├── Step 0 (astp_...)
  │     ├── ToolCall (tcall_...)
  │     └── ToolCall (tcall_...)
  ├── Step 1 (astp_...)
  │     └── ToolCall (tcall_...)
  └── Step 2 (astp_...)
```

## Store interface

```go
type Store interface {
    CreateRun(ctx context.Context, run *Run) error
    GetRun(ctx context.Context, runID id.AgentRunID) (*Run, error)
    UpdateRun(ctx context.Context, run *Run) error
    ListRuns(ctx context.Context, filter *ListFilter) ([]*Run, error)
    CountRuns(ctx context.Context, filter *ListFilter) (int64, error)

    CreateStep(ctx context.Context, step *Step) error
    ListSteps(ctx context.Context, runID id.AgentRunID) ([]*Step, error)

    CreateToolCall(ctx context.Context, tc *ToolCall) error
    ListToolCalls(ctx context.Context, stepID id.StepID) ([]*ToolCall, error)
}
```

### List filter

```go
type ListFilter struct {
    AgentID string
    State   State
    Exact   bool
    Limit   int
    Offset  int
}
```

Scope arrives on the context, not in the filter. Every `ListRuns` call is already
narrowed to the caller's scope before `AgentID` and `State` are applied. `Exact` narrows
the read to rows stored at precisely the caller's scope depth instead of everything
beneath it.

## API routes

These exist when you mount the `api` module through `extension.WithRoutes` (paths shown with the default `/cortex` base path):

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/cortex/v1/agents/:name/run` | Run an agent and wait for the result |
| `POST` | `/cortex/v1/agents/:name/stream` | Run an agent and stream events over SSE |
| `GET` | `/cortex/v1/runs` | List runs in the caller's scope (`limit`, `offset`) |
| `GET` | `/cortex/v1/runs/:id` | Get a specific run |
| `POST` | `/cortex/v1/runs/:id/cancel` | Cancel a running, paused, ready or reclaimable run |

The list route doesn't filter by agent. Use `eng.ListRuns` with `AgentID` for that. Steps and tool calls have no routes; read them with `eng.ListSteps` and `eng.ListToolCalls`.
