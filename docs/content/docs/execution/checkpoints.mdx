title: Checkpoints
description: Human-in-the-loop control that pauses a run for approval before a tool call goes ahead.
---

Checkpoints give you human-in-the-loop control: a run pauses before a tool call and waits for someone to approve it.

## Structure

```go
type Checkpoint struct {
    cortex.Entity
    ID        id.CheckpointID
    RunID     id.AgentRunID
    AgentID   id.AgentID
    Scope     cortex.Scope
    Reason    string
    StepIndex int
    State     string   // "pending" or "resolved"
    Decision  *Decision
    Metadata  map[string]any
}
```

## Decision

When a checkpoint is resolved, it receives a Decision:

```go
type Decision struct {
    Approved  bool      // whether to proceed
    DecidedBy string    // who made the decision
    Reason    string    // explanation
    DecidedAt time.Time
}
```

## Lifecycle

1. During a run, a `ToolAuthorizer` escalates a tool call by returning
   `cortex.ErrRequiresApproval`, or `cortex.ApprovalRequired` when it has a
   reason to give and a deadline of its own
2. The run suspends, and a checkpoint is created with state `pending`. Its
   `Reason` names the calls, each with the authorizer's reason when there is
   one
3. A human reviews the checkpoint through `Engine.ListPendingCheckpoints` or the
   REST endpoint
4. The human resolves it with a Decision (approve or reject)
5. An approval moves the run to `ready`, records the decision, and the run
   continues and finally dispatches the call. A rejection fails the run, with
   the decision's `Reason` on `run.Error`

```
Run (running) -> Checkpoint created (pending) -> Run (paused)
                                                 |
                                Decision made -> Run (ready) -> Run (running) [approved]
                                              -> Run (failed)                 [rejected]
```

`eng.ResolveCheckpoint` does all of it and returns when the run does.
`eng.DecideCheckpoint` stops at `ready`: it records the decision without
calling the model, `plugin.RunReady` fires, and you continue the run later with
`eng.ContinueRun`, typically from a background job:

```go
if err := eng.DecideCheckpoint(ctx, cpID, checkpoint.Decision{Approved: true, DecidedBy: "ops@example.com"}); err != nil {
    return err
}
// Later, in a job that carries the run's scope:
r, err := eng.ContinueRun(jobCtx, runID)
```

With `engine.WithRejectionsReturnToModel()`, a rejection goes through `ready`
too: the model reads `rejected by <DecidedBy>: <Reason>` as each call's result
and the run carries on. A decision on a checkpoint whose deadline has passed is
`cortex.ErrSuspensionExpired`, and the checkpoint stays pending for the sweeper.
See [Suspension](/docs/concepts/suspension#continuing-from-a-job) for the
details.

A checkpoint left undecided expires with its run. The deadline is the
approval's own TTL, or the engine's suspension TTL when it gave none, and once
it passes the sweeper fails the run and resolves the checkpoint with
`DecidedBy: "cortex"`. Set the TTL on the approval when one decision needs
longer than the rest:

```go
return cortex.ApprovalRequired{Reason: "production deploy", TTL: 7 * 24 * time.Hour}
```

To tell people a checkpoint is waiting on them, implement
`plugin.RunSuspended`. It fires once the run is paused, and its `Notice`
carries the checkpoint ID and the deadline.

The loop only started creating checkpoints in v1.11.0. Before that the entity,
the store and these endpoints all existed and nothing ever wrote a row. See
[Suspension](/docs/concepts/suspension) for the mechanism underneath, including
what an approval hands back to the engine and what happens when nobody answers.

## Store interface

```go
type Store interface {
    CreateCheckpoint(ctx context.Context, cp *Checkpoint) error
    GetCheckpoint(ctx context.Context, cpID id.CheckpointID) (*Checkpoint, error)
    Resolve(ctx context.Context, cpID id.CheckpointID, decision Decision) error
    ListPending(ctx context.Context, filter *ListFilter) ([]*Checkpoint, error)
    CountPending(ctx context.Context, filter *ListFilter) (int64, error)
}
```

`Resolve` writes a decision only on a pending checkpoint. Once one is recorded
it stays: a second `Resolve` returns an error wrapping `cortex.ErrInvalidState`,
which is what lets two people deciding at once end up with exactly one record.
A custom store has to keep that rule.

On the engine, use `eng.ListPendingCheckpoints`, `eng.CountPendingCheckpoints`, `eng.GetCheckpoint`, `eng.ResolveCheckpoint(ctx, cpID, decision)` and `eng.DecideCheckpoint(ctx, cpID, decision)`. Decide through the engine, not the store: the engine is what continues or fails the run.

### List filter

```go
type ListFilter struct {
    RunID  string
    Limit  int
    Offset int
}
```

As with runs, scope arrives on the context rather than the filter.

## API routes

These exist when you mount the `api` module through `extension.WithRoutes` (paths shown with the default `/cortex` base path):

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/cortex/v1/checkpoints` | List pending checkpoints |
| `POST` | `/cortex/v1/checkpoints/:id/resolve` | Resolve a checkpoint |
