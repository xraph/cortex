Cortex is organized as a set of focused Go packages. The `engine` package is the central coordinator. All other packages define interfaces, entities, and subsystem logic that compose around it.

## Engine construction

`engine.New` takes option functions and returns `(*engine.Engine, error)`:

```go
eng, err := engine.New(
    engine.WithStore(pgStore),           // composite store.Store
    engine.WithLLM(llmClient),           // without it, runs echo their input
    engine.WithConfig(cortex.Config{     // override the defaults
        DefaultModel:    "gpt-4o",
        DefaultMaxSteps: 30,
    }),
    engine.WithExtension(auditExt),      // lifecycle hooks
    engine.WithMetrics(metrics),         // a go-utils metrics sink; Forge passes its own
    engine.WithLogger(logger),           // a go-utils log.Logger; defaults to a no-op logger
)
```

The other options are `WithSafety`, `WithKnowledge`, `WithTool`, `WithExternalTool`, `WithToolAuthorizer`, `WithA2A`, `WithSuspensionTTL`, `WithSuspensionSweepInterval` and `WithSuspensionSweepLimit`. The store, LLM client, safety scanner and knowledge provider are all interfaces, so you can swap any of them for your own implementation.

## Agent run flow

When you call `RunAgent` (or `StreamAgent`), the engine:

1. Loads the `agent.Config` by name from the store.

2. Builds the system prompt from `prompt.Section` values: one for the agent's own instructions (`SystemPrompt` or its `Sections`), one for the persona's `Identity` when `PersonaRef` is set, one per `SystemPromptFragment` of the skills in `InlineSkills`, one per knowledge source those skills reference (when a knowledge provider is configured), and one per `prompt_injection` influence of the traits in `InlineTraits`.

3. Walks the run scope's ancestry, applies the `prompt.Overlay` found at each rung broadest first, and assembles the result in order. Overlays can also change the model, temperature, max tokens and tool list. See [Prompt Composition](/docs/concepts/prompt-composition).

4. Runs the ReAct loop, creating a `run.Step` for each reasoning step and a `run.ToolCall` for each tool invocation. A tool call can be denied or held for approval by your `ToolAuthorizer`, and a call to an external tool suspends the run until you `Resume` it.

5. Updates the `run.Run` with the final state, output, token usage and timing, saves the conversation to the session, and fires plugin hooks along the way (`OnRunStarted`, `OnStepStarted`, `OnToolCalled` and so on).

The persona's skill and trait assignments, behaviors, cognitive style, communication style and perception are stored, but a run doesn't read them yet. Trait influences other than `prompt_injection` aren't applied either, and `ReasoningLoop` is recorded on the run without changing the loop: ReAct is the only one.

## Scope isolation

`cortex.WithScope(ctx, scope)` puts a scope on the context. Cortex never interprets what a scope level means: you declare your own ordered hierarchy (workspace, org, tenant, app, whatever you need) as a `cortex.Scope`, and Cortex only matches on it.

- Store: every scope-guarded query filters by the caller's scope, and rejects a zero scope with `cortex.ErrNoScope` instead of matching everything.
- Engine: passes the context's scope through to every store call.
- API: your own middleware calls `cortex.WithScope` on the request context before it reaches Cortex. The REST layer doesn't make one up.

A caller who passes an agent ID from outside their scope gets `ErrAgentNotFound` back from the store, the same as for an ID that doesn't exist.

## Plugin system

Extensions implement the `plugin.Extension` base interface (just `Name() string`) and then opt in to specific lifecycle hooks by implementing more interfaces:

```go
type Extension interface {
    Name() string
}

// Opt-in hooks (implement any subset):
type RunStarted interface {
    OnRunStarted(ctx context.Context, agentID id.AgentID, runID id.AgentRunID, input string) error
}
type RunCompleted interface { /* ... */ }
type ToolCalled interface { /* ... */ }
type MessageSent interface { /* ... */ }
// ... 21 hook interfaces in total
```

The `plugin.Registry` sorts extensions by hook at registration time, so an emit only walks the extensions that implement that hook. Errors from hooks are logged and never propagated. Three hooks, `PersonaResolved`, `BehaviorTriggered` and `CognitivePhaseChanged`, are defined but the engine never fires them.

Built-in extensions:

- `observability.MetricsExtension`: deprecated and records nothing; the engine records its own metrics through `engine.WithMetrics`
- `audithook.Extension`: turns lifecycle events into an audit trail
- the `sentinel` module: evaluation through Sentinel
