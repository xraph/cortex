Cortex is a Go library for building AI agents. You define an agent from a system prompt and tools, and when you want more structure you describe it with **skills**, **traits**, **behaviors** and a **persona**, the same building blocks that make people unique. Cortex runs the agent through a ReAct loop with tool calling, conversation memory, human-in-the-loop checkpoints and runs that suspend and resume.

Cortex is a library, not a service. You bring your own LLM provider, database and HTTP server, and Cortex provides the agent orchestration plumbing.

## The Human Model

Cortex models AI agents the way you would describe a person:

| Aspect | What it represents | Go type |
|--------|-------------------|---------|
| Skill | What the agent can do (prompt fragment, tools, knowledge) | `skill.Skill` |
| Trait | Who the agent is (personality dimensions) | `trait.Trait` |
| Behavior | What the agent does habitually (trigger and action) | `behavior.Behavior` |
| Cognitive Style | How the agent thinks (phase-based reasoning) | `cognitive.Style` |
| Communication Style | How the agent talks (tone, formality, verbosity) | `communication.Style` |
| Perception | How the agent sees (attention filters) | `perception.Model` |
| Persona | The whole person (composes all of the above) | `persona.Persona` |

All seven are stored, scoped and served by the engine and the REST API. At run time the engine applies the persona's identity, the prompt fragments and knowledge of the skills an agent lists, and the prompt influences of the traits it lists. Behaviors and the three styles are stored but not applied to runs yet. [The Human Model](/docs/human-model/overview) has the details.

## What it does

- Declarative personality: define agents from composable skills, traits and behaviors instead of one long hand-written prompt.
- Persona composition: bundle an identity, skills, traits, behaviors and styles into a reusable persona, and point an agent at it with one field.
- Multi-agent orchestration: coordinate several agents with five strategies (sequential, parallel, router, hierarchical, debate). Agents share a blackboard, see a roster of collaborators, and hand work off to one another.
- Agent messaging: agents send each other FIPA-ACL style messages, and an ask suspends the asking run until a peer replies.
- Cloning: copy an agent or persona under a new name with `CloneAgent` or `ClonePersona`. Leave the name empty and Cortex picks one.
- Execution tracking: every run is stored as a Run with Steps and ToolCalls, so you can see the whole reasoning chain afterwards.
- Human in the loop: your `ToolAuthorizer` can hide tools, deny calls, or pause a run at a checkpoint until someone approves.
- Suspend and resume: a run that waits for an external tool result or an approval is a stored row, not a blocked goroutine.
- Host-defined scope: every entity belongs to a scope you define (tenant, workspace, app, whatever you need), and every store call checks it.
- Plugin system: 21 lifecycle hook interfaces for metrics, audit trails and custom processing. An extension implements only the ones it cares about.
- Conversation memory: sessions keep conversation history per agent.
- Three stores: PostgreSQL, SQLite and MongoDB, all on Grove, with migrations registered in Go.
- Forge integration: a `forge.Extension` that builds the engine, provides it through DI and runs migrations on start. The REST API (59 routes) lives in the separate `api` module, and you mount it with `extension.WithRoutes` when you want it.

## Design philosophy

**Library, not service.** Cortex is a set of Go packages you import. You control `main`, the database connection and the process lifecycle.

**Declarative over imperative.** You describe who an agent is. Skills define capabilities, traits shape personality, behaviors encode habits, and Cortex assembles the system prompt from the parts it applies today.

**Interfaces over implementations.** Every subsystem defines a Go interface, so you can swap a storage backend, LLM client, safety scanner or knowledge provider.

**Scoped by design.** `cortex.WithScope` puts a scope on the context and every store call enforces it. Cortex never interprets what a scope level means: you define your own hierarchy (workspace, org, tenant, app) and Cortex just matches on it.

**TypeID everywhere.** All entities use type-prefixed, K-sortable, UUIDv7-based identifiers (`agt_`, `skl_`, `trt_`, `bhv_`, `prs_`, `arun_` and so on).

## Quick look

```go
package main

import (
    "context"
    "log"

    "github.com/xraph/forge"
    "github.com/xraph/grove"

    "github.com/xraph/cortex/engine"
    cortexext "github.com/xraph/cortex/extension"
    "github.com/xraph/cortex/store/postgres"
)

func setup(ctx context.Context, db *grove.DB) {
    // Create the store.
    pgStore := postgres.New(db)
    if err := pgStore.Migrate(ctx); err != nil {
        log.Fatal(err)
    }

    // Build the Cortex engine.
    eng, err := engine.New(
        engine.WithStore(pgStore),
    )
    if err != nil {
        log.Fatal(err)
    }
    _ = eng

    // Or let a Forge app build it for you:
    app := forge.NewApp(forge.AppConfig{
        Name: "agents",
        Extensions: []forge.Extension{
            cortexext.New(cortexext.WithStore(pgStore)),
        },
    })
    _ = app
}
```

`db` is a `*grove.DB` opened with Grove's `pgdriver`. [Getting started](/docs/getting-started) walks through a complete program.
