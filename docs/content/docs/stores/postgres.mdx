The `store/postgres` package provides a production-ready implementation of the composite `store.Store` interface using PostgreSQL with the [Grove ORM](https://github.com/xraph/grove) and `pgdriver`.

## Setup

```go
import (
    "github.com/xraph/grove"
    "github.com/xraph/grove/drivers/pgdriver"
    _ "github.com/xraph/grove/drivers/pgdriver/pgmigrate"

    "github.com/xraph/cortex/store/postgres"
)

// Open a PostgreSQL connection through Grove's pgdriver.
drv := pgdriver.New()
if err := drv.Open(ctx, "postgres://user:pass@localhost:5432/cortex?sslmode=disable"); err != nil {
    log.Fatal(err)
}
db, err := grove.Open(drv)
if err != nil {
    log.Fatal(err)
}

s := postgres.New(db)
if err := s.Migrate(ctx); err != nil {
    log.Fatal(err)
}
```

The blank `pgmigrate` import registers Grove's migration executor for PostgreSQL, which you need when you run grove migrations through the executor registry yourself. `store/postgres` imports `pgmigrate` as well, so `Migrate` works with or without it. If you run Cortex as a Forge extension, the extension can build this store for you from a `*grove.DB` in the container and migrates it on start.

## Internals

| Aspect | Detail |
|--------|--------|
| Driver | Grove ORM with `pgdriver` (PostgreSQL) |
| Migrations | Registered in Go in `migrations.go`, run by `Migrate` |
| Transactions | Database-level ACID transactions |
| Scope | Up to three levels, in indexed `scope_l0`/`scope_l1`/`scope_l2` columns plus a `scope_canon` string. A `scope_extra` JSONB column exists for deeper levels, but `cortex.WithScope` refuses a scope deeper than three, so nothing reaches it today |

Every one of the first thirteen tables carries `app_id` (and `cortex_runs`, `cortex_memories`,
`cortex_checkpoints` and `cortex_orchestration_runs` also carry
`tenant_id`) as a read-only holdover from before `Scope` (see
[Multi-tenancy](/docs/concepts/multi-tenancy) for why they aren't dropped
yet). Nothing in the normal read/write path touches either column
anymore (`scope_l0`/`scope_l1`/`scope_l2` plus the `scope_canon` string
are what every scoped query actually filters on), but the v1.8.0
migration itself does still read `app_id`/`tenant_id` off unscoped rows,
feeding them to your `cortex.Rescoper` so it can reconstruct a `Scope`
for data written before v1.8.0. See the
[rescope guide](/docs/guides/v1.8-rescope) for the full mechanics.
`cortex_orchestration_configs` and `cortex_orchestration_runs` get the
same `scope_l0`/`scope_l1`/`scope_l2`/`scope_canon` columns as every
other table here; orchestration was the last entity converted, not one
left out of the conversion.

## JSONB columns

Complex nested structures are stored as JSONB columns:

- Skill tools and knowledge: `tools JSONB`, `knowledge JSONB`
- Trait dimensions and influences: `dimensions JSONB`, `influences JSONB`
- Behavior triggers and actions: `triggers JSONB`, `actions JSONB`
- Persona styles: `cognitive_style JSONB`, `communication_style JSONB`, `perception JSONB`
- All entities: `metadata JSONB`

## Migrations

Migrations are written in Go in `store/postgres/migrations.go`, compiled into your binary, and applied when you call `Migrate()`. You don't need an external migration tool. The `.sql` files under `store/postgres/migrations/` aren't loaded by anything, so editing them changes nothing.

## Migrations with several replicas

You can call `Migrate` from every replica at boot. They take turns. The first one to get there runs the migrations, the rest wait until it's done, and then they find nothing left to apply. You won't see "migration lock is held by another process" from a replica that simply started a second late.

The turn-taking is a session-level advisory lock with the key `-918477416930547652`, the FNV-1a 64-bit hash of `github.com/xraph/cortex/store/postgres.Migrate` read as a signed integer. It's a key of cortex's own because grove's migration lock uses key 1 for every group on a database, so sharing it would make cortex wait on (or block) migrations that have nothing to do with it. `Migrate` takes the lock on one dedicated connection and holds it for the whole call: grove creating `grove_migrations` and `grove_migration_locks`, the cortex migration group, then the legacy rescope and the default-session backfill. It releases the lock on that same connection before handing it back to the pool.

A replica that's waiting retries `pg_try_advisory_lock` with a pause that starts at 50ms and grows to a second. It doesn't block in `pg_advisory_lock`, and that's deliberate: a blocked call keeps its snapshot open, several cortex migrations build indexes with `CREATE INDEX CONCURRENTLY`, and that waits for every older snapshot to finish, so the replica holding the lock would end up waiting on the ones queued behind it.

In practice:

- `Migrate` waits for as long as your context allows. Give it a deadline or cancel it and it returns an error that matches `context.DeadlineExceeded` or `context.Canceled`, with no lock request left behind. Once a replica holds the cortex lock, grove waits up to five minutes for key 1 if something else holds it.
- It takes two connections from the pool at once, one for the cortex lock and one that grove's executor uses for key 1. pgdriver sizes its pool from `driver.WithPoolSize`, which is 10 unless you set it and wins over any `pool_max_conns` in the DSN. Give it a pool of one and `Migrate` waits five seconds for a second connection, then fails with an error saying it needs two.
- Session-level advisory locks need a real session. Run `Migrate` against Postgres directly or through PgBouncer in session mode, not transaction mode. Grove's own lock has the same requirement.
- Other grove users on the database don't take the cortex lock. On a fresh database one of them can create grove's tracking tables at the same moment as a cortex replica, and Postgres fails the loser with `42P07` or `42710`. `Migrate` retries that up to five times with a short pause, which is long enough for the tables to exist.

### Running the cortex group in your own migration pass

If your host runs every grove group in one central pass and turns off the extension's migration (Loomplane does this with `WithDisableMigrate`), add `postgres.Migrations` to that pass. The group creates every table cortex needs on its own.

The cortex lock isn't taken in that case, so keeping the pass safe across replicas is up to you. Grove's key 1 keeps the migrations themselves apart. On a fresh database you'll also want to retry `42P07` and `42710` around the pass, the same way `Migrate` does, because grove creates its tracking tables before it takes key 1.

The rescope and the session backfill that `Migrate` runs after the group only change rows written before v1.8.0. On a database that never held those you can leave them out. If yours did, call `Migrate` once with `cortex.WithRescoper` and your `cortex.Rescoper`. It's safe to run while your pass is running: `Migrate` holds the cortex key while it waits for key 1, and your pass never asks for the cortex key, so neither ends up waiting on the other.

## Usage with engine

```go
eng, err := engine.New(
    engine.WithStore(s),
)
```

## When to use

- Production deployments: durable, ACID-compliant storage with connection pooling.
- Multi-instance deployments: all application instances share the same database.
- Teams already using PostgreSQL: you reuse the infrastructure you have.
